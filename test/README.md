## Свежий стенд: сброс баз и seed (М7.3)

Приёмка вехи — «полный набор зелёный на свежем стенде из `develop`». Прогон на загрязнённом
стенде приёмкой не является: остатки прошлых запусков (треки, геозоны, объекты, чаты, заявки,
материалы) наборы видят как ЧУЖИЕ данные, и падения выглядят как дефекты продукта.

```bash
# 1. Сброс к известному состоянию: стоп сервисов → пересоздание 9 баз → миграции → seed → MinIO
bash scripts/reset-stand.sh            # спросит подтверждение
bash scripts/reset-stand.sh --force    # без вопроса (для скриптов)
bash scripts/reset-stand.sh --keep-minio

# 2. Поднять стенд заново (контейнеры, 9 сервисов, nginx-веб-контур :8080/:8081)
bash ~/.cleaning-ops/stand.sh up

# 3. Dev-серверы клиентов — если UI-набор идёт не через nginx (:8080/:8081), а через vite
bash ~/.cleaning-ops/stand.sh web     # :5173 админка, :5174 портал

# 4. Приёмка: оба проекта, два прогона подряд (воспроизводимость)
cd test
pnpm exec playwright test --project=api
pnpm exec playwright test --project=web
pnpm exec playwright test --project=api
pnpm exec playwright test --project=web
```

Что делает `scripts/reset-stand.sh` (подробности — в шапке скрипта): останавливает девять
сервисов; `DROP DATABASE ... WITH (FORCE)` + `CREATE DATABASE` для девяти баз (имена берутся из
`.env`, те же, что в CI-джобе); включает `postgis` в базе gps; применяет `prisma migrate deploy`
в каждом сервисе (включая SQL-view отчётов М7.1 и CHECK-ограничение М7.3 на `Chat.objectId`);
сеет пользователей из `test/fixtures/users.json`; чистит объекты MinIO (файлы после сброса баз —
сироты). Сервисы скрипт НЕ поднимает: это отдельный шаг (`stand.sh up`).

Стенд без демо-данных — это ожидаемо: демо-объекты («БЦ Ромашка» и прочее) живут в машинной
обвязке, а не в каноне проекта; при необходимости их возвращает `~/.cleaning-ops/demo-seed/seed.mjs`.

### Окружение: JIT Postgres под эмуляцией (иначе прогон падает не по своей вине)

На Apple Silicon amd64-образ postgres работает под qemu-user, и включённый JIT превращает чтение
SQL-view отчётов М7.1 в 15-секундный залп: `staff_geofence_totals` при `jit=on` — 14,7 с
(193 функции LLVM), при `jit=off` — 9 мс. ВМ colima профиля `default` — 2 ГиБ без swap, поэтому
всплеск заканчивался OOM-kill backend'а Postgres («Server has closed the connection» → 500 у
сервисов): на `--project=web` это давало 2 «чужих» падения за прогон. В
`infra/docker/docker-compose.yml` для сервиса `postgres` зафиксирован `command: ["postgres", "-c",
"jit=off"]`. CI не затронут (там postgres — сервис-контейнер со своей конфигурацией). Второй
вариант лечения, если понадобится JIT: поднять память ВМ до 6 ГиБ (`colima stop && colima start
--vm-type vz --cpu 4 --memory 6` — ровно то, что предполагает `~/.cleaning-ops/stand.sh`).

**Счётчики приёмки М7.3 (свежий стенд, два полных прогона подряд):** `--project=api` — 119 passed
/ 1 skipped / 0 failed (оба раза), `--project=web` — 45 passed / 0 failed / 0 skipped (оба раза).
Единственный пропуск — тест rate limit 429: он требует боевого лимита логинов, а стенд поднимается
с поднятым лимитом (`E2E_RATE_LIMIT=1` включает его точечно). После двух прогонов на стенде
остаётся ровно состояние seed: 4 пользователя, `Chat = 0`, `gps_tracks = 0`, `geofences = 0`,
`objects = 0`, `tickets = 0`, `Material = 0`, `MaterialMovement = 0`, `ConsumedOperation = 0`,
`Schedule = 0`, `notifications = 0` — то есть наборы и UI убирают за собой всё.

### e2e ядра домена (М2.9)

Дополнительно к auth-набору нужны **core-service** (`:3003`), **file-service** (`:3002`) и
**MinIO** (`:9000`); web-admin для этого набора не требуется.

```bash
# сервисы (каждый со своим окружением)
(cd backend/core-service && node dist/main.js)      # PORT=3003, FILE_SERVICE_URL=http://localhost:3002
(cd backend/file-service && node dist/main.js)      # PORT=3002

# прогон
cd test
node node_modules/@playwright/test/cli.js test --project=api test/e2e/api/core.api.spec.ts
```

Переменные окружения (все необязательные, дефолты — локальный стенд):

| Переменная | Дефолт | Назначение |
|---|---|---|
| `E2E_API_URL` | `http://localhost:3001` | auth-service: выдача access-токенов |
| `E2E_CORE_URL` | `http://localhost:3003` | core-service (объекты, этажи, помещения, техкарты, маршруты) |
| `E2E_FILE_URL` | `http://localhost:3002` | file-service (загрузка файлов и привязки) |

**Чем отличается от auth-прогона.** auth-набор ходит через `baseURL` проекта (`E2E_API_URL`),
ядровый набор обращается к двум сервисам по абсолютным адресам `E2E_CORE_URL`/`E2E_FILE_URL`,
поэтому смена `E2E_API_URL` его не затрагивает. Стенд для ядра — три сервиса плюс Postgres и
MinIO; логин по-прежнему нужен только auth-service.

**Что покрывает `e2e/api/core.api.spec.ts` (20 тестов).**

- Сквозной цикл: объект → 2 этажа → план (загрузка в file-service + привязка `FLOOR_PLAN` +
  `POST /api/floors/:id/plan-url`) → 3 помещения с координатами внутри плана → техкарта с 3
  операциями и материалами → `reorder` операций → маршрут с 3 точками → `reorder` точек →
  проверка `totalEstimatedTimeMin` и порядка точек → удаление точки с пересборкой `orderIndex` →
  статусная модель маршрута (DRAFT ↔ ACTIVE → ARCHIVED, из архива выхода нет). Второй тест
  покрывает multipart-загрузку плана **через core** (`POST /api/floors/:id/plan`) с пробросом
  токена в file-service.
- Негативные кейсы: 401 без токена и с мусорным токеном (core и file), 403 для OPERATOR/CLIENT на
  запись, 404 на несуществующие id, 409 на дубликат номера этажа (в объекте и в другом объекте —
  не конфликт), 400 на координаты вне плана (и на PATCH), 400 на координаты без плана, 400 на
  неполный/чужой/пустой/дублирующий список `reorder`, 400 на удаление объекта с активным
  маршрутом, 400 на помещение с другого этажа, 400 на невалидное тело и на недопустимый тип файла.
- Плоский список маршрутов (М4): `GET /api/routes` отдаёт `{ items, total }`, фильтры `objectId`
  (маршруты всех этажей объекта) и `floorId` (одного этажа) реально сужают выдачу — маршрут чужого
  объекта в неё не попадает, а `take`/`skip` режут страницу, не меняя `total`; `take` вне 1..100 → 400.
- RBAC: матрица чтения/записи по ADMIN, SUPERVISOR, OPERATOR, CLIENT; SUPERVISOR умеет писать,
  но удалять объект может только ADMIN; file-service — загрузка всем, удаление ADMIN/SUPERVISOR.
- Идемпотентность: `afterEach` удаляет созданные техкарты и объекты (каскадом этажи, помещения,
  маршруты, точки), тесты — свои файлы. Отдельный тест проверяет, что после уборки не остаётся
  ни объекта, ни этажа, ни помещения, ни маршрута. Две засеянные техкарты («Влажная уборка
  санузла») набор не трогает.

**Ограничение по лимиту входа.** auth-service пускает 5 логинов/мин на IP, причём квота общая на
весь стенд. Ядровый набор делает 4 логина (по одному на роль, токены кэшируются в
`helpers/core.ts`); если квота уже израсходована другим набором, хелпер один раз пережидает окно
(60 с) и повторяет попытку — тест остаётся зелёным, но прогон удлиняется. Чтобы прогон был
предсказуемо быстрым, поднимайте auth-service с `THROTTLE_LOGIN_LIMIT=1000
THROTTLE_GLOBAL_LIMIT=10000` (как в примере выше): при боевых 5/мин и auth-, и ядровый набор
упираются в 429.

### e2e сценария М2.7 в браузере (М2.9)

Отдельный набор `e2e/web/core.ui.spec.ts` (проект `web`) автоматизирует **ручной приёмочный
сценарий М2.7** — это прямое требование плана: «e2e-сценарий М2.7 автоматизирован в Playwright».
В отличие от ядрового набора он идёт через браузер и проверяет интерфейс, а не контракты API.

Нужны **все** сервисы: auth (`:3001`), file (`:3002`), core (`:3003`), MinIO (`:9000`) и
web-admin (`:5173`, vite dev — он проксирует `/api` по сервисам).

```bash
# web-admin
(cd frontend/web-admin && node node_modules/vite/bin/vite.js)

# прогон
cd test
node node_modules/@playwright/test/cli.js test --project=web test/e2e/web/core.ui.spec.ts
```

**Что покрывают 4 теста.**

- Сквозной цикл целиком через интерфейс: создать объект в списке (серверный поиск подтверждает
  запись) → добавить этаж → загрузить план файлом (`POST /api/floors/:id/plan` уходит в
  file-service) → нарисовать три помещения **протягиванием рамки** по плану → собрать маршрут из
  этих помещений → переставить точку кнопкой «Ниже» → сохранить порядок. Порядок и
  `totalEstimatedTimeMin` дополнительно сверяются запросом к API, а `orderIndex` проверяется на
  плотность (0,1,2) — так тест ловит и «сохранилось не то», и «сохранилось не до конца».
- Редактор операций техкарты: создание техкарты, две операции, сумма времени, переупорядочивание
  с немедленным сохранением (у техкарт нет отдельной кнопки сохранения порядка, в отличие от маршрутов).
- Защита маршрутов: `/objects`, `/routes`, `/tech-cards` без входа уводят на `/login`.
- RBAC: у оператора нет пунктов «Маршруты» и «Техкарды» в меню, а прямой заход на `/routes`
  возвращает на дашборд.

**Две ловушки интерфейса, на которые опирается тест** (обе выяснились прогоном):

1. Помещение создаётся **рамкой**, а не кликом, и после каждого создания экран сбрасывает режим
   рисования — перед новой рамкой режим включается повторно, а открытая карточка помещения
   закрывается (иначе следующий drag попадает по панели, а не по плану).
2. Кнопки «↑/↓» у сортируемых строк — соседи содержимого строки внутри `<li>`, а не его потомки:
   искать их нужно в `[data-testid^="sortable-row-"]`, а не в `operation-row-<id>`.

Фикстуры: `fixtures/files/floor-plan.png` (1200×800) и `photo-ok.png` (1600×900), генерируются
`node scripts/fixtures/make-file-fixtures.cjs <каталог>` (нужен `sharp` из `backend/file-service`).

### Уборка тестовых пользователей (auth)

`DELETE /api/users/:id` в auth-service запись **не удаляет**: он ставит `isActive=false` и
отзывает refresh-токены (`users.controller.ts`). Из-за этого после каждого прогона auth-набора
на стенде оставались неактивные `e2e-*` и `pin-e2e-*` (к моменту появления уборки их накопилось
по пять штук каждого вида).

Поэтому `e2e/web/auth.api.spec.ts` снимает созданные им записи сам, тем же SQL-приёмом, что и
`helpers/operations.ts` (`cleanupAuthUsers`):

- `afterEach` удаляет пользователей текущего теста **по id** (точечно, засеянные роли не трогаются);
- `afterAll` один раз подчищает остатки прошлых прогонов **по префиксам e-mail** (`e2e-`,
  `pin-e2e-`, `rbac-`), в том числе после падения в середине файла;
- отдельный тест фиксирует сам контракт: строка есть в `cleaning_ops.users` → `DELETE` оставляет
  её (деактивация) → SQL-уборка убирает её. Проверка идёт строго по id своих пользователей:
  глобальные счётчики строк на общем стенде недопустимы.

Настройки подписок (`notification_preferences`) лежат в БД уведомлений и не каскадируются при
удалении в auth-БД — они снимаются тем же вызовом.

### Что важно знать про эти тесты

**UUID только v4.** DTO gps-service требуют `@IsUUID('4')`: «нулевой» id вида
`00000000-0000-0000-0000-...` не проходит валидацию и даёт **400**, а не 404. В наборах
используются v4-идентификаторы (`00000000-0000-4000-8000-...`).

**Своя площадка на каждый тест.** gps-service ищет БЛИЖАЙШУЮ геозону в радиусе 1000 м,
поэтому две геозоны в одной точке сделали бы `check` недетерминированным. Тесты строят
геозону через `uniqueGeofenceCell(index)` — квадрат ~66×66 м со сдвигом от «шумных»
координат стенда, а тесты внутри файла разведены по `index`.

**Уведомления приходят асинхронно.** События идут через RabbitMQ, поэтому набор нигде не
«спит» фиксированно: он опрашивает `GET /api/notifications` с таймаутом
(`waitForNotification`, до 15–20 с). Создание заявки сразу с исполнителем эмитит ДВА события
(`ticket.created` и `ticket.assigned`) — это две in-app записи `NEW_TICKET`, поэтому
проверки считают прирост, а не абсолютное «ровно одно».

**Уборка и её границы.** `helpers/operations.ts` помнит созданное (геозоны, треки вместе с
их явными timestamp, устройства, уведомления, заявки, свежих пользователей) и сносит это в
`afterEach`; один раз на процесс `sweepOrphanNotifications()` чистит осиротевшие уведомления
(записи пользователей, которых больше нет в auth). Засеянные роли (`admin@`, `operator@`,
`supervisor@`, `client@`), объекты ядра и чужие геозоны набор не трогает. Два теста
(`GPS: уборка`) проверяют саму уборку: до неё строки прогона есть в БД, после — нет.

**RBAC берётся из контроллера**, а не из предположений: `POST /api/tickets` — ADMIN,
SUPERVISOR, CLIENT (OPERATOR → 403); `POST /api/tickets/emergency` — любая
аутентифицированная роль; `PATCH /:id/status` — ADMIN, SUPERVISOR, OPERATOR;
`POST /:id/assign` — ADMIN, SUPERVISOR; комментарии — без `@Roles`.

**Скоупинг ручных проходов (задача A2).** `POST /api/schedule/generate` и
`POST /api/schedule/check-missed` принимают необязательные `scheduleId` и `eventId` (`eventId`
приоритетнее). Это не удобство, а условие честного прогона на общем стенде: без области один
ручной проход переводил бы в `MISSED` чужие смены. Набор `e2e/api/schedule-scope.api.spec.ts`
проверяет и сужение, и обратную совместимость: вызов без параметров по-прежнему обрабатывает все
смены (тест убеждается в этом на своей смене, а не глобальным счётчиком). Несуществующий id → 404:
опечатка не должна выглядеть как выполненный проход. Генерация в этом наборе всегда сужена
`scheduleId` — смены чужим графикам стенда не создаются. «Соседняя смена того же дня» получается
естественно: график с двумя исполнителями даёт на дату две смены.

**Дефект push оффлайн-получателям.** Chat-service (`notification-push.client.ts`) отправляет
push оффлайн-получателям вызовом `POST {NOTIFICATION_SERVICE_URL}/api/notifications/internal/chat-message`
с типом `CHAT_MESSAGE`, но такого эндпоинта (и такого типа уведомления) в notification-service
нет: вызов отвечает 404, chat-service пишет один warning и продолжает. Доставка сообщения в чат
от этого не страдает (REST/WS-путь завершён), но оффлайн-получатель не получает ни push, ни
in-app записи. Тест фиксирует ФАКТИЧЕСКИЙ контракт (404 на внутреннем эндпоинте + отсутствие
записи с нашим `chatId` у получателя), а не ожидаемое поведение. Чтобы включить push, достаточно
добавить эндпоинт и тип `CHAT_MESSAGE` в notification-service — правок в chat-service не требуется.

**Дефект М7.3: 500 на `POST /api/chat/chats` (ticket-чат второй заявки одного объекта).**
`Chat.objectId` имеет ГЛОБАЛЬНЫЙ уникальный индекс (`Chat_objectId_key`), а ticket-чат писал в
это поле объект заявки. Вторая заявка того же объекта получала `P2002` на этом индексе; ветка
обработки гонки искала чат по `ticketId`, не находила и отдавала 500 «No Chat found». Воспроизводится
детерминированно: object-чат на объекте + ticket-чат по заявке того же объекта → 500. Исправлено
в продукте: ticket-чат больше не заполняет `objectId` (поле закреплено за object-чатами),
`findUniqueOrThrow` в ветках гонки заменён на поиск с проверкой, миграция
`20261002090000_m73_chat_objectid_only_object` чистит legacy-строки и ставит CHECK-ограничение
`Chat_objectId_only_object_check`. Тест «Чаты: OBJECT» держит регрессию: ticket-чат и object-чат
одного объекта сосуществуют.

**Уборка.** У chat-service нет DELETE ни для чата, ни для сообщения, поэтому набор помнит
созданные чаты и сообщения и сносит ровно их SQL-ом (`docker cp` + `psql -f` в
`cleaning_ops_chat`, `helpers/chat.ts`); заявки и свежие пользователи снимаются существующими
хелперами `helpers/operations.ts`. Чат удаляется целиком только если он СОЗДАН этим прогоном
(direct-чат идемпотентен и мог быть создан другим набором), свои сообщения — по id. Тест
«уборка» проверяет и обратную сторону: посторонний чат, не поставленный на уборку, остаётся.

| чужой объект | `?objectId=<чужой>` → `portal-forbidden` с заголовком «Нет доступа к объекту» (а НЕ «Объект не подключён»), данных чужого объекта нет ни в тексте, ни в разметке; контроль — без параметра тот же клиент видит свой объект |
| создание заявки | `portal-ticket-create` → шторка → заявка в `portal-ticket-list` и в `GET /api/tickets` под тем же клиентом (`createdBy` = клиент); ПЕРЕД созданием проверяется, что портал показывает объект ЭТОГО теста (иначе заявка ушла бы на чужой объект, а падение выглядело бы как «заявка не найдена в tickets-service») |
| отчёт | `/reports?tab=materials`: расход через API (IN+OUT), число из строки «Итого» совпадает с `GET /api/materials/report` |
| чат | `portal-chat-input`/`portal-chat-send` → сообщение в `portal-chat-thread` и в REST chat-service у второго участника |
| сквозной цикл | заявка из портала → менеджер (ADMIN) видит её в админке `/tickets` и отвечает в `ticket-chat` → ответ виден клиенту в портале; чат заявки дополнительно читается клиентом через REST |
| уборка | объект, заявка, чат, материал и их строки в БД прогона сняты |

**Требования к стенду:** auth `:3001`, core `:3003`, tickets `:3005`, materials `:3007`,
chat `:3009`, web-admin `:5173` и портал `:5174` (`E2E_PORTAL_URL`), PostgreSQL через
`docker exec` (уборка и SQL-тест). Портал в мобильном вьюпорте (`devices['iPhone 13']` в самом
файле), админские шаги цикла — отдельным контекстом с десктопным вьюпортом: контексты,
созданные через `browser.newContext()`, наследуют опции `use` файла, и админка в 390 px ломает
клик по строке таблицы.

**Область видимости объекта (важно).** У пользователя нет `objectId`: портал сопоставляет
`Object.clientName` с ФИО/email (`useObjectScope`), поэтому набор создаёт объект клиента с
`clientName = fullName` («Заказчик»), а «чужой» объект называет без подстроки «заказчик», чтобы
сопоставление заведомо не срабатывало. Тест различает две ветки отказа (`forbidden` —
«Нет доступа к объекту» и `unassigned` — «Объект не подключён») и проверяет, что при чужом id
портал показывает отказ, а без параметра — свой объект.

**Ограничение продукта, зафиксированное набором.** Портал рендерит только DIRECT-чаты
(`ChatPage`/`useChatResolution` фильтруют `type === 'direct'`), поэтому ответ менеджера в
TICKET-чате заявки в `portal-chat-thread` попасть не может: клиенту в портале доступен один канал
— DIRECT-чат. В сквозном тесте ответ в чат заявки идёт через UI админки (как требует М5.6), а
«клиент видит ответ в портале» проверяется в DIRECT-канале; доступность клиенту самого ответа в
чате заявки подтверждается REST-ом (клиент — участник заявки, `createdBy`).

**Хрупкость скоупа объекта (наблюдение М7.3, требует решения архитектора).** «Свой объект» портал
определяет эвристикой по `Object.clientName` (`useObjectScope`, правила: точное совпадение →
вхождение подстроки → первый по `id`). Следствие, пойманное набором: ЛЮБОЙ объект, в чьём
`clientName` встречается «Заказчик» (например, объекты других наборов с `clientName`
«ООО «E2E Заказчик»»), становится кандидатом, и портал может показать ЧУЖОЙ объект — тогда заявка,
созданная в портале, уходит не туда, и тест «заявка видна через API» падает не по своей причине.
Пока это лечится гигиеной стенда (наборы убирают за собой объекты) и проверкой в тесте
(«портал показывает ИМЕННО наш объект»), но по сути это UI-уровень доступа к чужому объекту:
кандидат в ADR — серверная привязка пользователя к объекту вместо сопоставления по имени.


**Замечание к фронтенду.** `data-testid="portal-report-total"` в вёрстке портала нет: итог
расхода лежит в строке «Итого» таба «Материалы» (`portal-report-materials`), и тест читает число
оттуда. Правка — во фронтенде, вне зоны QA.

## e2e отчётов М7.1 (read-модели) — и его единая точка входа

`e2e/api/reports.api.spec.ts` (15 тестов) проверяет READ-слой четырёх сервисов: расход материалов
(materials), выполнение заявок (tickets), контроль персонала (schedule), геозоны и маршруты (gps),
KPI-сводки и доступ (401 без токена; в М7.3 добавлен негативный кейс «чужой/несуществующий
`objectId` → пустой отчёт с нулевыми итогами»). Агрегаты отчёта сверяются с фактом, созданным через
публичный API, — «по виду похоже» не принимается.

**Единая точка входа (приёмка М7.1 п.3).** Каждый запрос идёт через прокси-адаптер, который
маршрутизирует `/api/...` по девяти сервисам. Адаптеров два, оба — таблица префиксов:
nginx стенда `:8080` (`E2E_GATEWAY_URL`) и таблица `SERVICE_ROUTES` в
`frontend/web-admin/vite.config.ts` (`:5173`). Спека выбирает адаптер в `beforeAll`, проверяя
живость: анонимный `GET /api/materials/reports/summary` обязан ответить **401** (значит, запрос
дошёл до сервиса; статика nginx и SPA-fallback dev-сервера на неизвестный `/api` отдают 200 с
`index.html`). Порядок: `E2E_GATEWAY_URL` → `:8080` → `:5173`. Это нужно для CI: джоба `e2e`
поднимает dev-серверы и nginx там нет, поэтому без второго адаптера проверка «через точку входа» в
CI не выполнялась бы вовсе. Если живо ни одного адаптера, `beforeAll` падает с подсказкой, что
поднять, — молчаливого пропуска нет.
