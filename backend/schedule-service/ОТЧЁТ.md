## 2. Схема БД и миграция

`Schedule`: `objectId?`, `routeId?`, `name`, `recurrence` (Json: `{frequency: daily|weekly|monthly, days[], dayOfMonth?, time: "HH:mm"}`), `assignees String[]`, `isActive`, timestamps.

`ScheduleEvent`: `scheduleId`, `date`, `plannedStart`, `status` (enum `PLANNED/CHECKED_IN/CHECKED_OUT/MISSED`), `userId?`, `checkInAt/checkOutAt`, `checkInLat/Lng`, `checkOutLat/Lng`, `ticketId?`, `checkOutReason?` (пометка причины авто-закрытия).

**Уникальность:** `@@unique([scheduleId, date, userId])` — ровно то, что требует задание.
Обоснование: идемпотентной должна быть и cron-генерация, и ручной `POST /generate`, поэтому защита
живёт в БД, а не только в коде; `userId` входит в ключ, т.к. у графика несколько `assignees` — на
каждого своя смена. Ограничение Postgres: `NULL` в уникальном индексе не конфликтует сам с собой,
поэтому смены без исполнителя (график с пустым `assignees` — их порождает только ручной вызов)
дополнительно дедуплицируются проверкой `findFirst` в `generateForSchedule`; генерация всегда
создаёт смену с конкретным `userId`. Индексы: `date`, `(userId,date)`, `(status,plannedStart)`, `isActive`, `objectId`.

**Миграция применена:**
```
$env:SCHEDULE_DATABASE_URL='postgresql://admin:***@localhost:5432/cleaning_ops_schedule?schema=public'
node node_modules/prisma/build/index.js migrate dev --name init_schedule --skip-seed
→ Applying migration `20260915181239_init_schedule`, схема в sync
```

## 4. Логика М4.4–М4.5 (решения и обоснования)

- **UTC-время.** `date` — полночь UTC дня, `plannedStart = date + recurrence.time` (UTC). Обоснование:
  модель не хранит часовой пояс объекта, а e2e/тесты должны быть детерминированы; перевод в
  локальную зону — задача клиента. Задокументировано в `recurrence.ts`.
- **Recurrence-фильтр:** daily — каждый день; weekly — `days` в ISO (1=Пн…7=Вс, как «Пн–Пт [1..5]»
  из BACKEND_SCHEDULE.md); monthly — по числу месяца (`dayOfMonth`, при отсутствии — `days[0]`;
  без числа месяца график пропускается, иначе monthly молча выродился бы в daily).
  Битое/неполное правило не роняет проход: график пропускается, причина попадает в `errors[]`.
- **Генерация + заявка:** смена создаётся сразу после проверки существующих; при наличии
  `objectId` и исполнителя запрашивается `POST {TICKET_SERVICE_URL}/api/tickets`
  (`type=planned`, `priority=normal`, `assigneeId`, `description` с именем графика) и сохраняется
  `ticketId`. Идемпотентность: проверка `findFirst` + уникальный индекс. Если ticket-service
  отказал по конкретной смене — смена остаётся с `ticketId=null`, ошибка идёт в `errors[]`, а
  **следующий проход до-создаёт заявку (backfill)**. Если ticket-service недоступен *до* записи
  смен — `502` и проход прерывается: «смены без плановых заявок» противоречат смыслу М4.4.
- **Check-in:** смена ищется по `(scheduleId, userId из токена, сегодня UTC)`; нет смены — 404 с
  названием графика. Геозона проверяется через
  `GET {GPS_SERVICE_URL}/api/gps/geofences/:userId/check?lat=&lng=` с **токеном самого пользователя**
  (проброс из `Authorization`). Выбор обоснован: служебный токен нужен только там, где
  пользовательского нет вообще (cron/заявка), а проброс не добавляет логина в auth-service на
  каждый check-in и не ломает check-in при недоступности auth-service. Результат: `inside=true` →
  `CHECKED_IN` + `checkInAt/lat/lng`; `inside=false` → **403 «Вы находитесь вне зоны объекта»**
  (отметка не ставится); недоступность/ошибка/нарушение контракта gps → **502**, не 500.
  Повторный check-in идемпотентен и не ходит в gps; закрытая смена → 409.
- **Check-out:** идемпотентен, `lat/lng` необязательны, без check-in → 400. Закрывает смену.
- **Неявки:** `ScheduleEvent` в `PLANNED`, `plannedStart <= now`, `checkInAt = null`, `userId != null`
  → `updateMany` с условием `status=PLANNED AND checkInAt IS NULL` (защита от гонки с ручным
  check-in) → `MISSED` + эмиссия `schedule.missed_checkin` в `cleaning-ops.events`. Повторный проход
  видит `MISSED` и событие не публикует — срабатывание ровно один раз обеспечивается данными, а не
  таймером. Payload: `{userId, scheduleId, objectName, eventId, objectId, plannedStart, detectedAt}`
  — аддитивное расширение `ScheduleMissedCheckinEvent` из shared (все поля shared-контракта
  сохранены; совместимость проверена `tsc`). `objectName` берётся из core-service служебным токеном,
  при недоступности — подставляется `objectId` (не критично для уведомления).
- **Авто check-out:** смена `CHECKED_IN` без `checkOutAt`, у которой с `plannedStart` прошло
  `SCHEDULE_AUTO_CHECKOUT_MINUTES` (15) → `CHECKED_OUT` + `checkOutReason`. Отсчёт от `plannedStart`,
  а не от «конца смены»: длительность смены моделью не задаётся (расписание хранит только начало) —
  обоснование в `configuration.ts`; закрытые вручную смены не затрагиваются.
- **Cron-проходы (без Bull/Redis, как эскалация в ticket-service):** два `setInterval` —
  генерация (по умолчанию раз в сутки, срабатывает в `SCHEDULE_GENERATE_HOUR_UTC`, по умолчанию 00:00 UTC)
  и проверка неявок + авто check-out каждые `SCHEDULE_MISSED_CHECKIN_INTERVAL_MS`. Проход
  идемпотентен, повторный вход пропускается, ошибки не роняют процесс; состояние доступно в `/scheduler/state`.
  Bull не взят: таймеры материализованы в данных, перезапуск сервиса ничего не теряет, e2e не нужен Redis.
- **ServiceTokenProvider:** `POST {AUTH_SERVICE_URL}/api/auth/login` (`SERVICE_AUTH_EMAIL/PASSWORD`),
  кэш в памяти с учётом `exp` JWT (запас 30 с), защита от штормов параллельных логинов, `invalidate()`
  и **перелогин ровно один раз** при 401 от ticket-service; недоступность auth → 503 с понятным текстом.
- **Устойчивость:** недоступность gps/ticket/RabbitMQ не даёт 500 — `EventsPublisher` возвращает
  `false` с warning (HTTP-ответ не страдает), gps → 502, ticket → 502 на `/generate` и «смена без
  ticketId + backfill» на частичный сбой.

## 8. Что осталось и риски

- **Notification-service пока не консьюмит `schedule.missed_checkin`** — очередь
  `notification.schedule.missed_checkin` из `shared/constants/events.ts` заведена контрактом, но
  consumer относится к М5/М6. Событие реально уходит в exchange (проверено).
- **Имя объекта** в событии требует рабочего auth-service (служебный токен) и core-service; при их
  недоступности поле деградирует до `objectId` (warning в логах), событие всё равно уходит.
- **Пароль seed-оператора** (`operator`) неизвестен, поэтому живой сценарий создаёт
  временного OPERATOR через auth-service и деактивирует его. Это не правка чужой зоны, а работа через API.
- **Число месяца для monthly** задаётся полем `dayOfMonth` (аддитивное расширение контракта, т.к. в
  задании для recurrence перечислены только `frequency/days/time`); поддерживается и старый вариант
  через `days[0]`.
- **Cron генерации** — суточный проход с фильтром по часу UTC; если сервис стартует позже настроенного
  часа, генерация произойдёт только на следующем проходе (на стенде это лечится `POST /generate`).
  Для e2e на быстрых таймерах есть `SCHEDULE_CRON_ENABLED=false`, чтобы фоновой cron не мешал сценарию.
- **Часовой пояс** расписания — UTC по решению выше; при появлении требования «время объекта»
  потребуется поле таймзоны у объекта/графика (сейчас его нет ни в core, ни в контракте М4.4).
