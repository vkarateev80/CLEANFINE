## 1. Цель и рамки

Построить систему управления клининговыми работами «Cleaning Ops» точно по уставу:

- **4 клиента:** Flutter-приложение оператора (iOS/Android, offline-first), Web Admin (React, «толстый»), Web Client-портал заказчика («тонкий»), дизайн-система.
- **9 микросервисов backend** (NestJS): auth, core, tickets, gps, files, materials, schedule, chat, notifications.
- **Инфраструктура:** PostgreSQL 16 + PostGIS, Redis, RabbitMQ, MinIO, Docker/K8s/Terraform, GitHub Actions, Prometheus/Grafana.
- **Качество:** unit > 80%, e2e (Playwright), нагрузка (k6), UAT.
- Правила командной работы, git-конвенции, код-стиль, статус-таблица — из устава.

Рамки плана: **только построение системы.** Продакшн-релиз — конец М7. Каждая фаза заканчивается работающим, тестируемым срезом (Definition of Done) и обновлением статус-таблицы в README.

## 3. Карта зависимостей и стратегия

### 3.1 Граф зависимостей сервисов (стрелка = «зависит от»)

```
auth ─────────────► (пользователи/роли нужны всем сервисам и клиентам)
files ─► MinIO     (планы этажей → core; фото → tickets/mobile; аватары → auth; вложения → chat)

core ─► files (планы этажей), auth
gps  ─► core (объекты → геозоны), auth (сотрудники)
tickets ─► core (объекты), auth (исполнители), gps (SOS: ближние в 500 м), notification (события)
schedule ─► core (объекты/маршруты), auth, gps (check-in по геозоне), tickets (автосоздание заявок), notification
materials ─► core (техкарты/операции), tickets (событие operation.completed), notification (низкий остаток)
chat ─► auth, files (вложения), notification (push оффлайн)
notification ─► RabbitMQ, Firebase(мок), auth (токены устройств)

web-admin  ─► API всех сервисов + дизайн-система
web-client ─► auth (роль CLIENT), core (статус объекта), tickets, chat
mobile     ─► auth (PIN/биометрия), core (маршрут/чек-лист), tickets (SOS), gps (трекинг),
               files (фото), chat, notification (push), materials (списание по событиям)
```

### 3.2 Контракт событий (RabbitMQ) — фиксируется в М0, далее не меняется без review архитектора

- Exchange: `cleaning-ops.events` (topic), dead-letter: `cleaning-ops.events.dlq`.

| Routing key | Продюсер | Потребитель | Поля (минимум) |
|---|---|---|---|
| `ticket.created` | ticket-service | notification-service | `ticketId, assigneeId, description` |
| `ticket.assigned` | ticket-service | notification-service | `ticketId, assigneeId` |
| `ticket.emergency` | ticket-service | notification-service | `ticketId, type, objectName, floor, lat, lng` |
| `ticket.overdue` | ticket-service | notification-service | `ticketId, minutesOverdue` |
| `ticket.operation.completed` | ticket-service (endpoint из М3, вызов из mobile М6) | material-service | `operationId, ticketId, objectId, completedAt` |
| `geofence.exit` | gps-service | notification-service | `userId, employeeName, objectId, timestamp` |
| `material.low` | material-service | notification-service | `materialId, materialName, objectId, objectName, quantity` |
| `schedule.missed_checkin` | schedule-service | notification-service | `userId, scheduleId, objectName` |

### 3.3 Стратегия: вертикальные срезы + параллельные дорожки агентов

Устав описывает 14 параллельных агентов; «план на всё сразу» невозможен без порядка. План разбит на 8 фаз-милестоунов (М0–М7), каждая = **вертикальный срез**, который можно показать и протестировать целиком. Внутри фазы агенты работают параллельно по своим директориям (дорожка A — backend, B — frontend/дизайн/mobile, C — DevOps/QA), синхронизация — через общие контракты (G2).

Порядок фаз выведен из графа зависимостей 3.1:

1. **М0** — фундамент (без него ничего не собирается);
2. **М1** — вход: дизайн-токены + auth (без пользователей и ролей не работает ни один сервис);
3. **М2** — ядро домена: core + files (объекты/маршруты/техкарты — база всех остальных доменов);
4. **М3** — оперативка: tickets + gps + notifications (SOS-вертикаль, ядро ценности продукта);
5. **М4** — планирование и учёт: schedule + materials (замыкает «план → заявка → списание»);
6. **М5** — коммуникации: chat + портал клиента;
7. **М6** — мобильное приложение оператора (все API к этому моменту стабильны);
8. **М7** — отчёты, нагрузка, UAT, продакшн-инфраструктура.

  *Проверка:* `flutter analyze`, `flutter test` зелёные; чек-лист приёмки мобильного (Устав → Агент Mobile): авторизация/PIN/биометрия/маршрут/чек-лист/SOS/чат/оффлайн/GPS/фото работают.

**Definition of Done М6:** оператор выполняет полную смену на телефоне: PIN-вход → маршрут по плану → чек-листы с фото → материалы списаны на сервере; SOS отправляется в один тап; оффлайн-операции синхронизируются; push доходят (мок в dev). Статус: Mobile App 🟢.

### М7 — Отчёты, качество, продакшн

**Цель:** аналитика для управления, доказанное качество (нагрузка, e2e, UAT) и продакшн-инфраструктура; финальный релиз и статус-таблица 🟢.

**Агенты:** Frontend Web (отчёты), DevOps (prod-инфра), QA (нагрузка/e2e/UAT), все агенты (исправления).

#### Задачи

- [ ] **М7.1 — Отчёты и дашборд (CQRS-read)**
  По решению №4: SQL views + read-репозитории: расход материалов (объект/период/материал — из materials), выполнение заявок (количество/время цикла/просрочки — из tickets), контроль персонала (check-in/out, геозоны, маршруты — schedule+gps), сводный дашборд KPI. Web Admin `Reports`: таблицы + графики Recharts (дашборд, отчёты за период, экспорт CSV).
  *Проверка:* e2e — отчёт по расходу соответствует движениям М4; дашборд открывается < 2 с (LCP).

- [ ] **М7.2 — Нагрузочное тестирование (k6)**
  Сценарии по эталону QA-агента (п.3): `tickets.js` (листинг заявок: 50→100 rps, порог p95 < 500 мс, ошибок < 1%), `auth.js` (burst-логин с rate-limit), `gps-track.js` — приём 1000 точек/с (чек-лист GPS), `schedule-gen.js` (пик генерации в 00:00). Профилирование PostGIS-запросов (EXPLAIN на GIST-индексах М3.1). Результаты — в `test/performance/results/`, отчёт в `docs/`.
  *Проверка:* пороги k6 выполняются; узкие места зафиксированы и исправлены (индексы/кэш Redis).

- [ ] **М7.3 — Полный e2e-набор (Playwright)**
  Все happy-path вертикалей: auth, объекты/маршруты, заявки/SOS (со сжатыми таймерами), материалы/графики, портал клиента, чат; негативные: RBAC, недоступность чужого объекта. Отчёты тестов в `test/reports/`, прогон в CI (workflow М0.6, job e2e с dev-стендом).
  *Проверка:* полный набор зелёный на свежем стенде из `develop`.

- [ ] **М7.4 — UAT и исправления** (Агент QA, цели 5–6)
  UAT-чек-листы по ролям: оператор (М6-сценарий), бригадир (назначение, контроль), администратор (объекты/графики/отчёты), клиент (портал); приёмочные сценарии на prod-like окружении; регистрация дефектов → `bugfix/`-ветки; критические баги закрыты до релиза.
  *Проверка:* протокол UAT подписан (чек-листы + результаты в `docs/`).

- [ ] **М7.5 — Prod-инфраструктура (DevOps)**
  Terraform (`main.tf`, `variables.tf`, `outputs.tf`); K8s-манифесты по образцу устава (Агент DevOps, п.3): namespace, deployments (3 реплики core, остальные по нагрузке), services, ingress, configmaps, secrets (SecretKeyRef — код в уставе); HPA по CPU; API-gateway (Traefik/Kong: SSL, rate limiting, auth proxy — архитектура README); SSL (Let's Encrypt); бэкапы `scripts/backup.sh` + cron (PG: pg_dump + MinIO), восстановление проверено; мониторинг: Prometheus (метрики сервисов `/metrics`), Grafana-дашборды, Alertmanager (правила: 5xx, задержки, диск) — файлы по структуре агента DevOps.
  *Проверка:* `kubectl apply` на staging-кластере проходит; прогон восстановления из бэкапа; алерт срабатывает на тестовой ошибке.

- [ ] **М7.6 — Финальный смоук и релиз**
  Полный сквозной сценарий на prod-like окружении (клиент → заявка → оператор mobile → материалы → отчёт); обновление `docs/README.md`: статус-таблица → 🟢 по всем компонентам; релизная ветка `release/1.0.0` → merge в `main` (code review + CI, G3/G4); тег `v1.0.0`.
  *Проверка:* смоук зелёный; статус-таблица в README вся 🟢; релиз на `main`.

**Definition of Done М7:** отчёты и дашборд работают; нагрузочные пороги выполнены; e2e-набор и UAT пройдены; продакшн-инфраструктура развёрнута с мониторингом и бэкапами; релиз v1.0.0 на `main`; статус-таблица устава полностью 🟢.
