## 1. Назначение

Приложение должно работать **весь рабочий день без сети** и не терять ни одного действия оператора.
Раздел описывает:

1. **что кэшируется** (чтобы экраны открывались без сети);
2. **что попадает в очередь** и в каком порядке уходит;
3. **как приложение узнаёт о сети** без отдельной библиотеки связности;
4. **как ведут себя таймеры, фото и GPS** в оффлайне;
5. **как выглядит индикатор** и что видит оператор в очереди.

Правило номер один: **экран сначала рисует кэш, потом сеть**. Ни один экран не показывает пустоту
только потому, что запрос не прошёл, — если данные есть локально, они показываются с пометкой
«Данные от {HH:mm}».

## 4. Очередь действий

### 4.1. Виды действий

| `kind` | Что это | API | Идемпотентность | Приоритет |
|---|---|---|---|---|
| `sos` | аварийная заявка: (1) upload фото → (2) `POST /api/tickets/emergency` → (3) `attach` фото | ticket-service, file-service | ⚠️ нет на сервере; локальный `clientRequestId` | 1 (первым) |
| `operation_complete` | завершение операции техкарты | `POST /api/tickets/:id/operations/:operationId/complete` | ✅ `@@unique([ticketId, operationId])`, ответ `alreadyCompleted` | 2 |
| `point_skip` | пропуск точки маршрута (причина) | `POST /api/tickets/:id/comments {text}` | ⚠️ нет (комментарий можно продублировать) | 3 |
| `chat_message` | сообщение в чат | WS `message:send` (или REST-фолбэк) | ⚠️ нет (нет `clientMessageId` на сервере — [`chat.md`](./chat.md) п. 11.1) | 4 |
| `logout` | отзыв refresh-токена после локального выхода | `POST /api/auth/logout {refreshToken}` | ✅ идемпотентен по смыслу | 5 |
| `gps_batch` | не запись очереди, а буфер: точки из `gps_points` отправляются batch’ами | `POST /api/gps/track` | ✅ повтор точки не критичен (дубли допустимы: трек — поток) | 6 |

**Что НЕ ставится в очередь** (требует сети осознанно):

| Действие | Почему |
|---|---|
| `check-in` / `check-out` | сервер проверяет геозону (`gps-service`), отметка «задним числом» из очереди исказила бы учёт рабочего времени |
| загрузка аватара, смена PIN/пароля, настройки уведомлений | серверные операции профиля, не влияют на смену; при оффлайне показывается «Нет соединения. Попробуйте позже» |
| чтение (смены, маршрут, заявки, чаты) | читается из кэша; при его отсутствии — состояние ошибки с «Повторить» |

### 4.2. Поля записи очереди

```
{
  id:              "5f1c…"                 // локальный uuid v4 → ключ UI, лог
  kind:            "operation_complete"    // см. 4.1
  payloadJson:     "{ticketId, operationId, completedAt, photoUrl, requiresPhoto, totalOperations}"
  idempotencyKey:  "op:<ticketId>:<operationId>"  | "sos:<clientRequestId>" | "chat:<clientId>"
  status:          "pending" | "sending" | "failed" | "synced"
  attempts:        0…10

}
```

## 5. Синхронизация

### 5.1. Как приложение узнаёт о сети (без `connectivity_plus`)

`connectivity_plus` в зависимостях нет (`mobile/README.md`, табл. зависимостей) — и это осознанно
задокументировано как открытый вопрос (п. 10.1). До решения используется наблюдение по фактам:

1. **Онлайн-сигнал:** любой успешный HTTP-ответ `dio` (в том числе `GET /api/auth/me`) → `online = true`.
2. **Оффлайн-сигнал:** `DioException.connectionError`/`connectionTimeout`/`receiveTimeout` → `online = false`.
3. **Опрос при непустой очереди:** каждые 30 с, пока `pending_actions` содержит `pending`/`failed`,
   отправляется публичный `GET /api/files/health/ping` (без токена, отвечает `{status, minio}`) —
   безопасная «проба», не требующая авторизации и не создающая данных.
4. **Триггеры вне опроса:** выход приложения на передний план (`AppLifecycleState.resumed`),
   pull-to-refresh, открытие любого экрана с запросом, ручное «Синхронизировать сейчас».

Переход `offline → online` — событие для `SyncService`: запускается проход очереди.

### 5.2. Порядок и правила прохода

1. Проход строго по приоритету (§4.1): сначала **все** `sos`, затем операции, затем пропуски, чат,
   logout.
2. Внутри одного вида — по `createdAt` (FIFO): оператор не может «перескочить» порядок операций.
3. Запись берётся в работу по одной (`status = 'sending'`), при успехе — `synced` + `syncedAt`,
   локальная сущность обновляется серверным ответом (например, `completedOperations`).
4. При ошибке: `attempts += 1`, `lastError` из ответа, `nextAttemptAt = now + backoff(attempts)`,
   статус возвращается в `pending`; после 10 попыток — `failed` (авто-повторов нет, только вручную).
5. Backoff: 1 с → 2 с → 5 с → 10 с → 30 с → 60 с → 300 с (дальше всегда 300 с). Джиттер ±20 %,
   чтобы десятки устройств не били в сервер одновременно.
6. **Ответ `alreadyCompleted: true` — успех**, а не ошибка: операция уже отмечена (например,
   повтор после обрыва), запись переводится в `synced`.
7. **HTTP-ошибки 4xx не ретраятся** (кроме 408/429): 403 «Вы не участник этого чата», 400
   «Для операции требуется фото (photoUrl)», 404 — запись переходит в `failed` с текстом сервера,
   чтобы оператор увидел реальную причину, а не бесконечный ретрай.
8. Порядок операций внутри помещения сохраняется: если операция №2 в `failed`, операция №3 всё
   равно уйдёт (сервер не проверяет порядок), но UI не считает помещение завершённым.

### 5.3. Фото в очереди

| Шаг | Порядок |
|---|---|
| Съёмка | файл кладётся в `photos_dir/{operationId}.jpg` (или `sos_{clientRequestId}.jpg`) |
| Загрузка | перед действием: `POST /api/files/upload {kind: 'photo', userName, takenAt, lat, lng}`; ответ `fileId`/`url` пишется в `checklist_operations.photoFileId/photoUrl` |
| Действие | `operation_complete` с `photoUrl` из кэша |
| Сбой загрузки | запись остаётся `pending` с `lastError`; файл **не** удаляется и не грузится повторно, если `photoFileId` уже есть |
| Сбой действия после успешной загрузки | фото не перегружается, повтор идёт с тем же `photoUrl` |
| Очистка | файл удаляется после `status = 'synced'` |
| Ограничение | на одно помещение — не более 20 фото (≈60 МБ); при превышении показывается «Мало места…» и предлагается очистить кэш |

### 5.4. Таймеры

| Аспект | Правило |
|---|---|
| Идут в оффлайне | да: `startedAtLocal` в drift, отображение считается от wall-clock, а не от тиков `Timer` |
| Перезапуск приложения | таймер продолжается (значение хранится), при возврате показывается актуальное время |
| Что уходит на сервер | только `completedAt` (ISO) — сервер время не проверяет и не хранит начало |
| Норма | превышение `estimatedTimeMin` — только визуальное предупреждение (`warning600`), отправку не блокирует |
| Часовые пояса / перевод часов | при расхождении с серверным временем (`Date`-заголовок ответа) разница > 10 мин показывается предупреждением «Время на устройстве отличается от сервера» — `completedAt` всё равно уходит |

### 5.5. GPS-буфер

| Аспект | Правило |
|---|---|
| Запись точек | каждая точка пишется в `gps_points` **сразу** (даже онлайн) — это единый путь, сеть лишь ускоряет отправку |
| Отправка | batch’ами до 1000 точек (`MAX_TRACK_BATCH`): в движении 10–15 с, статично 60 с; пауза вне смены (`status != CHECKED_IN`) |
| Поля точки | `lat`, `lng`, `accuracy`, `speed`, `battery`, `timestamp` (`TrackPointDto`) |
| Оффлайн | точки копятся; батарея/трафик экономятся: batch отправляется при появлении сети, точки старше 24 ч удаляются без отправки |
| Индикатор | в [`profile.md`](./profile.md) §3.3: «отправлено {N} точек», «в буфере {K}», «Последняя отправка {HH:mm}» |
| Ошибка 403 (чужой userId) | точка удаляется, приложение пишет `lastError` (не должно случаться: `userId` не передаётся — берётся из токена) |

| Ошибки | «Не удалось отправить: {текст сервера}», «Попыток: {attempts}», «Повтор через {N} с», «Мало места: {N} МБ. Очистите кэш.», «Мало места: не удалось сохранить фото», «Время на устройстве отличается от сервера», «Нет соединения. Данные появятся после подключения» |
| GPS | «отправлено {N} точек», «в буфере {K}», «Последняя отправка {HH:mm}» |
| Таймер | те же тексты, что в [`checklist.md`](./checklist.md) §9 |
| Фото | «Фото сохранится и уйдёт при появлении сети» |
| Синхронизация | «Синхронизация: {done} из {total}» |

## 10. Что проверяет widget-тест

1. **Запись в очередь при оффлайне** (требование М6.7): с выключенной сетью завершение операции
   создаёт в `pending_actions` одну запись `kind: 'operation_complete'` со `status = 'pending'`,
   `attempts = 0` и `idempotencyKey = 'op:<ticketId>:<operationId>'`; экран чек-листа показывает
   «Отправляется…», а не ошибку.
2. **Синк меняет статус** (требование М6.7): после включения сети и успешного мок-ответа
   сервера запись получает `status = 'synced'` и непустой `syncedAt`; счётчик в `AppBar`
   уменьшается с «⚡2» до «⚡1».
3. **Ответ `alreadyCompleted: true` — успех**: мок возвращает `alreadyCompleted: true` → запись
   `synced` (не `failed`), повторных попыток нет.
4. **4xx не ретраится**: мок возвращает 403 → запись `failed` с `lastError = 'Вы не участник этого
   чата'`, `nextAttemptAt` не увеличивается, на `/offline` видна кнопка «Повторить».
5. **Индикатор в оффлайне**: при `online = false` и непустом кэше на `/today` виден
   `Key('today_offline_banner')` с текстом «Нет соединения — данные могут быть устаревшими», а
   смены всё равно отображаются.

## 11. Ограничения и открытые вопросы

1. **⚠️ Нет пакета отслеживания связности.** В `mobile/README.md` (таблица зависимостей) нет
   `connectivity_plus`; определение «есть ли сеть» построено на фактах ошибок `dio` и пробе
   `GET /api/files/health/ping` (§5.1). Это работает, но даёт задержку до 30 с на «появление сети».
   Решение: добавить `connectivity_plus` в `pubspec.yaml` (+ строка в `mobile/README.md`) —
   это изменение зависимостей, а не экрана, поэтому зафиксировано здесь как открытый вопрос.
2. **⚠️ Идемпотентности нет у SOS, сообщений чата и комментариев.** Повтор из очереди после обрыва
   связи может создать дубль аварийной заявки, дубль сообщения или лишний комментарий. Гарантия
   есть только у завершения операции (`@@unique([ticketId, operationId])`) и `check-in`/`check-out`.
   Требуется `clientRequestId`/`Idempotency-Key` в `EmergencyTicketDto`, `SendMessageDto` и WS-payload
   ([`sos.md`](./sos.md) п. 10.4, [`chat.md`](./chat.md) п. 11.1).
3. **⚠️ Сервер не хранит прогресс помещения/маршрута.** Локальная отметка «выполнено» не восстанавливается
   при переустановке приложения, если операция не успела уйти на сервер (в лучшем случае
   восстановится по `GET /api/tickets/:id`). Подробности — [`route_map.md`](./route_map.md) п. 11.1,
   [`checklist.md`](./checklist.md) п. 11.1.
4. **⚠️ Оффлайн-вход не определён.** Без сети `POST /api/auth/refresh` и `GET /api/auth/me` не
   работают, значит после истечения access-токена (или перезапуска без валидного токена) приложение
   не пустит оператора в кэш, хотя данные на устройстве есть. Нужно продуктовое решение: доверять
   локальной сессии N часов (например, 12) и синхронизировать после входа
   ([`auth.md`](./auth.md) п. 10.5).
5. **Конфликты между устройствами не разрешаются.** Если тот же оператор (или другой на той же
   смене) отметит операции с двух устройств, сервер сведёт их идемпотентно (`alreadyCompleted`),
   но локальные статусы второго устройства могут разойтись: при следующем онлайне дрифт
   обновляется из `GET /api/tickets/:id`, однако «пропущенные» точки (локальные) не синхронизируются
   вовсе. Полноценного merge нет — это цена отсутствия серверной модели прогресса (п. 3).
6. **Размер очереди не ограничен.** Долгий оффлайн (неделя) с фото может занять гигабайты
   (`photos_dir`). Ограничение «20 фото на помещение» и предупреждение о 200 МБ — паллиатив;
   правильнее ограничить общий объём и уведомлять оператора заранее.
7. **`logout` в очереди — потенциальная утечка.** Если выход сделан оффлайн, refresh-токен остаётся
   валидным на сервере до первой синхронизации. См. [`profile.md`](./profile.md) п. 11.5.
8. **`LocalTickets` из Устава как ориентир.** В `FRONTEND_MOBILE.md` п. 6 показана таблица
   `LocalTickets` (`id`, `type`, `status`, `description`, `createdAt`, `synced`) — в мобильном
   приложении заявки не создаются (кроме SOS), поэтому роль этой таблицы выполняет
   `cached_tickets` + `pending_actions`; сама схема Устава — пример, а не обязательный набор полей.
