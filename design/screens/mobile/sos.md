# 🚨 Экран: Аварийная заявка (`sos`) — DS-002 (М6.5)

> DS-002 → `sos_emergency.fig`; реализация — М6.5 (`lib/features/sos/presentation/pages/sos_page.dart`).
> Код-основа — `docs/agents/FRONTEND_MOBILE.md` п. 5 дословно: `DropdownButtonFormField<EmergencyType>`

> Данные: ticket-service (3005) — `POST /api/tickets/emergency`; file-service (3002) — фото
> (водяной знак на сервере); gps-service (3004) — ближние операторы (внутри ticket-service).
> Источник требований — `ПЛАН.md` М6.5: *«тип аварии, фото (обязательно, с водяным знаком на
> сервере), описание, текущая локация (геолокация → geocoding «помещение/этаж» из core по
> координатам — минимально: координаты), кнопка „🚨 ОТПРАВИТЬ SOS“ → `createEmergency` М3.5;
> обработка ошибок и повтор при оффлайне (см. М6.7)»*.

## 1. Назначение

Дать оператору **один экран**, с которого авария уходит диспетчеру и ближним коллегам за один тап по
кнопке. Аварийная заявка — единственный способ оператора создать заявку: `POST /api/tickets`
(плановая/внеплановая) доступен только `ADMIN`, `SUPERVISOR`, `CLIENT` (`tickets.controller.ts:25`),
а `POST /api/tickets/emergency` открыт всем аутентифицированным ролям — именно потому, что «SOS
отправляет оператор с мобильного» (комментарий в контроллере).

Экран собирает четыре обязательных сведения — тип, фото, описание, координаты — и умеет работать без
сети: заявка и фото кладутся в локальную очередь и уходят при появлении соединения.

### 1.1. Точка входа в навигации

| Что | Значение |
|---|---|
| Маршрут | `/sos` (`fullscreenDialog: true`) |
| Кто открывает | пункт «SOS» таб-бара каркаса на `/today`, `/chats` (включая переписку), `/profile` (`Key('shell_tab_sos')`; до 17.10.2026 — `FloatingActionButton`), иконка 🚨 в `AppBar` маршрута ([`route_map.md`](./route_map.md)) и чек-листа ([`checklist.md`](./checklist.md)), пункт «Аварийная заявка» в шторке точки маршрута |
| Что открывает | при успехе — `Navigator.pop()` на предыдущий экран + snackbar «Заявка отправлена» (по коду Устава) |
| Выход | `BackButton` / жест «назад» / свайп вниз (iOS, `fullscreenDialog`); при заполненной форме — подтверждение «Отменить заявку SOS?» |
| Контекст | `objectId` и `roomId` берутся из текущей смены/маршрута (drift); при открытии из shell без активной смены `objectId` — из последней известной смены, а если её нет — экран блокируется (п. 5, «Нет объекта») |

## 3. Состав блоков

### 3.1. Тип аварии

| Аспект | Решение |
|---|---|
| Контрол | `DropdownButtonFormField<EmergencyCategory>` (`Key('sos_type_dropdown')`), `decoration: InputDecoration(labelText: 'Тип аварии')`, `border: OutlineInputBorder(borderRadius: AppRadius.lg)` |
| Список типов | **⚠️ словаря в API нет** (п. 10.1). Промежуточно — константа приложения `lib/features/sos/domain/emergency_category.dart`: «Прорыв трубы / затопление», «Засор канализации», «Нет электричества», «Повреждение имущества», «Опасность для людей», «Другое» |
| Как тип попадает на сервер | `EmergencyTicketDto` поля типа не имеет, поэтому выбранный тип подставляется **первой строкой описания** в формате `[Тип: Прорыв трубы / затопление]`, далее — текст оператора. Так бригадир видит тип в заявке без изменения схемы |
| Обяз. | да: без типа кнопка отправки не срабатывает (snackbar §4) |
| Значение по умолчанию | нет (пустое) — осознанно: автоматически выбранный «Другое» маскирует реальную причину |

### 3.2. Фото

| Аспект | Решение |
|---|---|
| Контрол | `OutlinedButton.icon(Icons.camera_alt, label: Text('Сделать фото'))` + подпись «обязательно» (`danger600`); после съёмки — `Image.file` на всю ширину (`AppRadius.md`) и `TextButton('Переснять')` |
| Источник | `image_picker.pickImage(source: ImageSource.camera, maxWidth: 1920, imageQuality: 85)` |
| Проверка | ≥1280×720 (лимит file-service); меньше — «Фото слишком маленькое. Снимите заново» |
| Водяной знак | на сервере: `POST /api/files/upload` с `kind: 'photo'`, `userName` = `me.fullName`, `takenAt`, `lat`, `lng`; ответ `watermarked: true` |
| Обяз. | да: без фото отправка не происходит, snackbar «Выберите тип и сделайте фото» |
| Локально | файл копируется в `photos_dir/sos_{clientRequestId}.jpg` до успешной отправки (при оффлайне остаётся там) |

### 3.3. Описание

| Аспект | Решение |
|---|---|
| Контрол | `TextFormField(maxLines: 4, maxLength: 2000)` (`Key('sos_description_field')`), `textCapitalization: sentences` |
| Лимит | 2000 символов — `EmergencyTicketDto.description` (`@MaxLength(2000)`); счётчик символов показываем от 1800 |
| Обяз. | да (сервер: «Опишите аварию») |
| Подсказка | `hintText: 'Что случилось и где'` |

### 3.4. Локация

| Аспект | Решение |
|---|---|
| Контрол | `ListTile(leading: Icon(Icons.location_on), title: Text('Локация'))` (`Key('sos_location_text')`) — как в коде Устава |
| Источник | `geolocator.getCurrentPosition(LocationAccuracy.high)` при открытии экрана (сразу, параллельно с заполнением) + последняя точка из буфера GPS ([`offline.md`](./offline.md) §6) |
| Формат | «{lat}, {lng}» моноширинным (`toStringAsFixed(6)`) + человекочитаемое место из локальных данных маршрута: «{room.name}, {floor.number} этаж» |
| Ожидание | «Определяем местоположение…» (`Key('sos_location_pending')`), таймаут 10 с |
| Отказ в разрешении | «Нет доступа к геолокации. Включите GPS и повторите» (`Key('sos_location_error')`); отправка **невозможна** (п. 10.3) |
| Геокодирование | не выполняется: обратного геокодирования координат в API нет (`ПЛАН.md` М6.5 допускает «минимально: координаты»); «помещение/этаж» берётся из маршрута, если экран открыт из точки |

### 3.5. Кнопка отправки

| Аспект | Решение |
|---|---|
| Вид | `SizedBox(width: double.infinity, child: FilledButton(...))` высотой 56, фон `danger500`, `AppRadius.lg`, текст `«🚨 ОТПРАВИТЬ SOS»` `sizeLG`/`weightBold`, `Colors.white` — геометрия и текст повторяют код Устава |
| Состояние загрузки | `CircularProgressIndicator(color: Colors.white)` вместо текста, кнопка `disabled` (как в Уставе) |
| Проверка перед отправкой | тип и фото обязательны → иначе snackbar «Выберите тип и сделайте фото» (дословно) |
| Повторное нажатие | запрещено во время запроса; после успеха кнопка исчезает (экран успеха) |

### 3.6. Порядок отправки (важно)

`EmergencyTicketDto` не принимает `photoUrl` (п. 10.2), поэтому приложение делает три шага:

```
1) POST /api/files/upload { kind: photo, userName, takenAt, lat, lng }  → UploadedFileView.url, .id
2) POST /api/tickets/emergency {
     objectId, roomId?, description: '[Тип: …] ' + описание,
     lat, lng, objectName?, floor?, radiusM: 500
   } → Ticket & { nearbyOperators }
3) POST /api/files/{fileId}/attach { entityType: 'TICKET', entityId: ticket.id }
```

Шаг 3 необязателен для факта заявки, но именно он связывает фото с заявкой (иначе снимок остаётся в
бакете без сущности). При оффлайне все три шага кладутся в очередь одной записью `kind: 'sos'` с
payload, содержащим локальный путь к фото; синхронизатор выполняет их строго по порядку и при
падении шага 3 не считает заявку неуспешной (заявка уже создана).

Ошибки отправки:

| Случай | Текст | Осталось в форме |
|---|---|---|
| 400 (нет объекта/описания/координат) | текст сервера («Укажите объект», «Опишите аварию») | да, ничего не теряется |
| 400 от file-service (размер/разрешение) | «Фото отклонено: {текст сервера}. Снимите заново» | да, тип и описание сохранены |
| 401 | прозрачный refresh; при неудаче — выход на `/login` | форма сохраняется в черновике |
| 5xx / 502 | «Сервис временно недоступен. Повторите позже» + «Повторить» | да |
| нет сети | «Заявка будет отправлена при появлении сети» + запись в очередь | да |
| любое другое | «Ошибка: {текст}» (формат из кода Устава) | да |

Важно: **недоступность gps-service не мешает созданию заявки** — ticket-service вернёт пустой
`nearbyOperators` (комментарий в `tickets.controller.ts`), и экран успеха покажет
«Оповещены 0 операторов поблизости».

## 8. Данные из API

| Запрос | Тело | Ответ / поля | Использование |
|---|---|---|---|
| `POST /api/tickets/emergency` | `{objectId, roomId?, description, lat, lng, objectName?, floor?, radiusM?}` | 201 `Ticket & {nearbyOperators: [{userId, distanceMeters}]}`; заявка: `id`, `type: 'emergency'`, `priority: 'critical'`, `status: 'new'`, `objectId`, `roomId`, `createdBy`, `description`, `lat`, `lng`, `createdAt`, `reactionDeadline` | создание аварийной заявки |
| `POST /api/files/upload` | multipart `file`, `kind: 'photo'`, `userName`, `takenAt`, `lat`, `lng` | `UploadedFileView`: `id`, `url`, `thumbnailUrl`, `watermarked`, `width`, `height`, `sizeBytes` | фото с водяным знаком |
| `POST /api/files/:id/attach` | `{entityType: 'TICKET', entityId: ticketId}` | `{id}` (идентификатор привязки) | связь фото с заявкой |
| `GET /api/objects/:id` | — | `Object.name` | `objectName` и `floor` в теле заявки (для события `ticket.emergency`) |
| `GET /api/rooms/:id` | — | `Room.name`, `Room.floorId` | текст локации «{room.name}, {n} этаж» |
| `GET /api/notifications?unreadOnly=true` | — | `unreadCount` | не используется на этом экране (для счётчика в шапке shell) |

Права: `POST /api/tickets/emergency` — без `@Roles` (любой аутентифицированный), поэтому SOS доступен
оператору; `POST /api/tickets` (обычная заявка) оператору **запрещён** (403) — в приложении экрана
обычной заявки нет и не должно быть.

## 10. Что проверяет widget-тест

1. **Пустая форма → snackbar** (требование М6.5 дословно): нажатие `Key('sos_submit_button')` без
   типа и фото → `find.text('Выберите тип и сделайте фото')` находит snackbar, мок
   `sosRepository.submitEmergency` **не** вызван.
2. **Успешная отправка**: заполнены тип, фото (мок `image_picker`), описание, координаты → вызов
   `submitEmergency` содержит `description`, начинающееся с `[Тип: `, и `lat`/`lng`; после ответа с
   `nearbyOperators` из 3 записей виден текст «Оповещены 3 оператора поблизости».
3. **Оффлайн → очередь**: при выключенной сети нажатие SOS не показывает ошибку, добавляет запись
   `kind: 'sos'` в `pending_actions` со `status = 'pending'` и локальным `clientRequestId`, а на
   экране появляется «Заявка сохранена и будет отправлена».
4. **Нет координат**: мок `locationService` бросает отказ в разрешении → виден текст «Нет доступа к
   геолокации. Включите GPS и повторите» и `submitEmergency` не вызван (сервер требует `lat`/`lng`).

## 11. Ограничения и открытые вопросы

1. **⚠️ В API нет «типа аварии».** `EmergencyTicketDto` (`ticket.dto.ts:78–128`) содержит только
   `objectId`, `roomId`, `description`, `lat`, `lng`, `objectName`, `floor`, `radiusM` — ни
   `category`, ни `emergencyType`. Словаря типов тоже нет ни в `shared/`, ни в ticket-service. До
   доработки (поле `category` + словарь значений + шаблон события `ticket.emergency`) тип
   передаётся префиксом в описании — это компромисс: аналитика по типам аварий на сервере
   невозможна, а бригадир читает тип в тексте. **Требуется:** `category` в DTO + словарь
   (например, в `shared/types/tickets.ts`) + подстановка в push/payload.
2. **⚠️ Аварийная заявка не принимает фото.** У `EmergencyTicketDto` нет `photoUrl`, в отличие от
   `CompleteOperationDto` (`photoUrl`). Поэтому отправка — три запроса (§3.6), а фото привязывается
   вложением (`ENTITY_TYPES` содержит `TICKET`). Требуется либо `photoUrl` в теле SOS, либо
   атомарный «создать заявку с вложением». Побочный эффект текущего порядка: между созданием
   заявки и привязкой фото есть окно, когда заявка существует без снимка (при оффлайне — до
   синхронизации).
3. **⚠️ Координаты обязательны.** `lat`/`lng` в `EmergencyTicketDto` — `@IsNumber` без
   `@IsOptional` (в отличие от `CreateTicketDto`, где они опциональны). Значит, при отказе в
   геолокации (или на устройстве без GPS) **отправить SOS невозможно** — экран честно блокирует
   отправку (§3.4), но это прямая угроза основному сценарию «авария в подвале без сигнала GPS».
   Требуется сделать `lat`/`lng` необязательными (или добавить флаг «координаты недоступны»).
4. **Нет идемпотентности SOS.** В `EmergencyTicketDto` нет клиентского ключа, а
   `POST /api/tickets/emergency` не проверяет дубликаты: повтор из очереди после обрыва связи
   создаст вторую аварийную заявку. Приложение снижает риск (одна запись очереди на отправку,
   `clientRequestId` как локальный ключ, кнопка блокируется после успеха), но гарантии нет.
   Требуется `clientRequestId`/`Idempotency-Key` на сервере.
5. **Геокодирование не реализовано.** «Помещение/этаж» берётся из активной точки маршрута, а не из
   координат; обратного геокодирования в API нет. Если SOS отправлен вне маршрута, в заявке будут
   только координаты — это соответствует минимуму из М6.5.
6. **Радиус поиска ближних операторов** в спецификации — 500 м (значение по умолчанию gps-service:
   `DEFAULT_NEARBY_RADIUS_METERS = 500`); `radiusM` ограничен 1…5000. Увеличение радиуса для
   «опасности для людей» (например, 2000 м) — продуктовое решение, в М6.5 не заявлено.
7. **Порядок «фото → заявка → attach»** выбран из-за отсутствия `photoUrl` в DTO. Если фото не
   загрузилось, а заявка создана, экран не должен «врать» о полном успехе: в этом случае
   показывается успех с пометкой «Фото не прикреплено — прикрепится автоматически», а запись
   остаётся в очереди до успешного `attach`.
