# 🗺 Экран: Маршрут дня (`route_map`) — DS-002 (М6.3)

> DS-002 → `route_map.fig`; реализация — М6.3
> (`lib/features/route_map/presentation/pages/route_map_page.dart`, `widgets/route_point_marker.dart`).
> Код-основа — `docs/agents/FRONTEND_MOBILE.md` п. 3 (`InteractiveViewer`, `Image.network`,
> `Positioned(left: coordsX, top: coordsY)`, «Следующая точка»).
> Данные: core-service (3003) — маршрут, этаж, помещения; schedule-service (3008) — смена и маршрут
> смены; ticket-service (3005) — факт выполнения операций.
> Источник требований — `ПЛАН.md` М6.3: *«`route_map` по коду п.3: план этажа (InteractiveViewer,
> Image.network с loadingBuilder), точки маршрута поверх плана с координатами помещений (core
> `Room.coords*`), статусы точек, кнопка „Следующая точка“»*; чек-лист приёмки — «Маршрутная карта
> работает», «Оффлайн-режим работает».

## 1. Назначение

Показать оператору **где он и что делать дальше**: план этажа объекта, поверх него — точки маршрута
по координатам помещений, их порядок и статус, и одна главная кнопка «Следующая точка». Экран
работает без интернета: план берётся из локального кэша, точки и статусы — из drift, а сервер нужен
только для первого получения маршрута и для завершения операций (это делает чек-лист).

Экран не строит маршрут и не двигает точки — это админка (`route_builder`, DS-003). Оператор может
только пройти маршрут, пропустить точку с причиной и отметить помещение выполненным.

### 1.1. Точка входа в навигации

| Что | Значение |
|---|---|
| Маршрут | `/route/:eventId` (`eventId` — `ScheduleEventView.id`) |
| Кто открывает | `Key('today_route_button')` с [`home_today.md`](./home_today.md) (при `CHECKED_IN` — «Продолжить», при `PLANNED` — «Маршрут» в режиме просмотра) |
| Что открывает | `/route/:eventId/room/:roomId?ticketId=…&pointId=…` (чек-лист), `/sos` (иконка в `AppBar`) |
| Режимы | `CHECKED_IN` — рабочий (завершение операций разрешено); `PLANNED`/`CHECKED_OUT` — **просмотр** (кнопка «Завершить» не показывается, а чек-лист открывается read-only) |

## 3. Состав блоков

### 3.1. План этажа

| Аспект | Решение |
|---|---|
| Виджет | `InteractiveViewer(minScale: 0.5, maxScale: 3.0, boundaryMargin: EdgeInsets.all(80), constrained: false, child: SizedBox(width: planWidth, height: planHeight, child: Stack(...)))` |
| Изображение | `Image.network(planImageUrl, fit: BoxFit.fill, loadingBuilder: (context, child, progress) => progress == null ? child : const CircularProgressIndicator(), errorBuilder: (…) => planErrorPlaceholder)` — дословно по коду Устава (п. 7, «Ленивая загрузка изображений») |
| Размеры | `SizedBox` строго `planWidth × planHeight` (реальные пиксели изображения из `Floor.planWidth/planHeight`): координаты помещений — **пиксели этого изображения**, поэтому `Positioned(left: coordsX, top: coordsY)` корректен только при совпадении бокса и рамочного размера картинки. `BoxFit.fill` (а не `contain`) — иначе маркеры «уедут» относительно стен |
| Если размеров нет | размеры берутся из `ImageStreamListener` (`Image` с `frameBuilder`, первый кадр даёт `image.width/height`); если и это не удалось — режим «План без размеров» (§2) |
| Кэш | файл `plans_dir/{floorId}.img` (+ `{floorId}.meta.json` с `planWidth/planHeight/planScale`): при первом успешном открытии маршрута план скачивается и кладётся на диск, дальше `Image.file` (оффлайн). Обновление кэша — если `Floor.updatedAt` изменился или бандл смены новый |
| Жесты | двойной тап — зум ×2 к точке нажатия; `InteractiveViewer` даёт pan/pinch; кнопки `[−] [＋]` дублируют зум для работы в перчатках |
| «К текущей точке» | `TransformationController` → `Matrix4.identity()..translate(...)` так, чтобы маркер текущей точки оказался в видимой области с отступом `AppSpacing.xl` |
| Легенда | bottom sheet: ①…⑫ порядок · серый «Ожидает» · синий «В работе» · зелёный «Выполнено» · оранжевый «Пропущено» · контур «Помещение» |

### 3.2. Маркер точки маршрута

| Часть маркера | Реализация | Токены |
|---|---|---|
| Кружок с номером | `Container(width: 28, height: 28, decoration: BoxDecoration(shape: BoxShape.circle, color: statusColor, border: Border.all(color: Colors.white, width: 2)))`, внутри `Text('${orderIndex + 1}')` `sizeXS`/`weightBold` | `AppRadius.full` |
| Область помещения | `Positioned(left: coordsX, top: coordsY, child: Container(width: coordsWidth, height: coordsHeight, decoration: BoxDecoration(border: Border.all(...))))` — тонкий контур, заливка `primary100` только у текущей | `primary500`, `primary100` |
| Текущая точка | пульсация (`AnimatedScale`/`TweenAnimationBuilder` 400 мс, масштаб 1.0↔1.15) + кольцо `primary500` | |
| Размер маркера | 28 dp — **меньше** 48 dp, поэтому маркер имеет невидимый `GestureDetector`-хитбокс 48×48 (`behavior: HitTestBehavior.opaque`) | доступность |
| Нажатие | открывает шторку точки: название помещения, площадь, техкарта, `estimatedTimeMin`, статус, список операций с их статусами, кнопки «Открыть чек-лист» / «Пропустить» | |
| Семантика | `Semantics(label: 'Точка ${orderIndex + 1}, ${room.name}, ${statusLabel}', button: true)` | скринридер |

### 3.3. Статусы точек (локальная модель)

Сервер статус точки **не хранит** (см. п. 11.1). Статус вычисляется на клиенте и живёт в
`route_points` (drift), синхронизируясь с фактом выполнения операций из ticket-service.

| Статус | Значение в коде | Условие | Цвет | Подпись |
|---|---|---|---|---|
| Ожидает | `pending` | все операции техкарты помещения ещё не завершены, точка не текущая | `neutral400` | «Ожидает» |
| В работе | `active` | первая незавершённая точка маршрута в порядке `orderIndex` (это и есть «текущая») | `primary500` | «В работе» |
| Выполнено | `done` | все `operationId` техкарты помещения присутствуют в `GET /api/tickets/:ticketId` → `operations[].operationId`, либо локально отмечено «Завершить помещение» | `success500` | «Выполнено» |
| Пропущено | `skipped` | оператор нажал «Пропустить» и указал причину (`skipped_reason` в drift) | `warning500` | «Пропущено» |

Правила: «текущая» точка — **первая** точка маршрута в статусе `pending` (пропущенные не считаются
текущими); если такая точка уже открыта в чек-листе, она выделяется дополнительно. Кнопка
«Следующая точка» переводит к следующей `pending` точке (не завершая текущую — завершение делает
чек-лист). Если `pending` точек не осталось, кнопка меняется на «Маршрут пройден» и `disabled`.

### 3.4. Нижняя панель и прогресс

| Элемент | Значение |
|---|---|
| «Следующая точка ▸» | основная кнопка: открывает `/route/:eventId/room/:roomId` следующей `pending` точки |
| «Пропустить» | вторичная: bottom sheet с обязательным полем «Причина пропуска» (свободный текст ≥3 символов) + «Пропустить точку»; причина сохраняется локально и уходит в чат заявки комментарием (см. п. 11.2) |
| Прогресс | `LinearProgressIndicator(value: done / total)` + текст «Маршрут: {done} из {total} помещений» |
| Прогресс в таб-строке | `Сегодня {done}/{total}` — виден и на других shell-экранах (тот же провайдер) |

## 5. Таблица состояний

| Состояние | Триггер | Отображение |
|---|---|---|
| Загрузка | первый вход, маршрута в drift нет | скелетон: серый прямоугольник `AppRadius.xl` на всю высоту карты + `CircularProgressIndicator`; ниже — 3 скелетона строк |
| Загрузка плана | `loadingBuilder` изображения | спиннер поверх серого бокса **внутри** `InteractiveViewer` (зум доступен сразу) |
| Пусто (нет точек) | `route.points.length == 0` | `EmptyStateWidget` «Маршрут пуст» + «Обратитесь к бригадиру» |
| Пусто (маршрут не назначен) | `event.routeId == null` | `EmptyStateWidget` «Маршрут не назначен» + кнопка «Назад» |
| Ошибка маршрута | 5xx/сеть и кэша нет | `ErrorStateWidget` «Не удалось загрузить маршрут» + «Повторить» |
| Ошибка плана | `errorBuilder`/404 | серый бокс + «План этажа недоступен» + кнопка «Повторить»; **точки и работа по маршруту остаются доступны** |
| Нет координат | `planWidth/Height == null` | предупреждение `warning600` «Координаты помещений недоступны» + список точек |
| 403 | чужая смена/объект | `EmptyStateWidget` «Нет доступа к маршруту» + «Назад» |
| Оффлайн | нет сети | `OfflineBannerWidget` «Нет соединения — план из кэша, статусы сохранятся локально»; зум и переходы работают; кнопки завершения в чек-листе — в очередь |
| Успех | всё загружено | план + маркеры + текущая точка + прогресс |

## 8. Данные из API

| Запрос | Ответ / поля | Использование |
|---|---|---|
| `GET /api/schedule/events/:eventId` | `ScheduleEventView`: `routeId`, `objectId`, `ticketId`, `status` | «какой маршрут и какая заявка у смены» (из drift, если оффлайн) |
| `GET /api/routes/:id` | `Route` + `points[]` (`id`, `routeId`, `roomId`, `orderIndex`, `estimatedTimeMin`, `room`) + `totalEstimatedTimeMin`. `room` — `Room`: `id`, `floorId`, `name`, `areaM2`, `floorType`, `coordsX`, `coordsY`, `coordsWidth`, `coordsHeight`, `zone`, `techCardId` | точки и координаты маркеров |
| `GET /api/floors/:id` | `Floor`: `id`, `objectId`, `number`, `name`, `planImageUrl`, `planWidth`, `planHeight`, `planScale` | план этажа и размеры бокса |
| `GET /api/tech-cards/:id` | `TechCard` + `operations[]` (`id`, `name`, `orderIndex`, `estimatedTimeMin`, `requiresPhoto`, `requiresQr`) | шторка точки: «Операций: N · ~M мин» |
| `GET /api/tickets/:id` | `TicketDetailEntity`: `operations[]` (`operationId`, `completedAt`, `photoUrl`, `completedBy`), `operationsCompleted` | вычисление статусов `done` |
| `POST /api/tickets/:id/comments` | `{text}` → `TicketComment` | причина пропуска точки (п. 11.2) |
| `GET /api/files/:id` | `UploadedFileView`: `url`, `thumbnailUrl`, `width`, `height` | **не нужен** для плана: план этажа отдаётся готовым URL в `Floor.planImageUrl` |

Порядок загрузки (важен для оффлайна): 1) смена из drift; 2) маршрут из drift → сеть; 3) этаж (план)
из кэша файлов → сеть; 4) `GET /api/tickets/:ticketId` для статусов → локальная отметка «выполнено».

## 10. Что проверяет widget-тест

1. **Отрисовка точек** (требование М6.3 «виджет-тест отрисовки точек»): мок маршрута с 3 точками →
   `find.byKey(Key('route_point_marker_p1'))` и т. д. находят 3 маркера, у маркера `p1` текст «1», у
   `p2` — «2»; центр маркера `p1` в дереве смещён вправо/вниз относительно `p2`, если
   `coordsX/coordsY` больше (проверка координатной привязки через `tester.getCenter`).
2. **Статусы**: точка, все `operationId` которой есть в `GET /api/tickets/:id`, имеет
   `Semantics.label`, содержащий «Выполнено»; первая незавершённая — «В работе».
3. **«Следующая точка»**: нажатие `Key('route_next_button')` вызывает `go` на
   `/route/ev1/room/r2` (следующая `pending` точка), а при отсутствии `pending` кнопка `disabled` и
   текст «Маршрут пройден».
4. **Оффлайн с кэшем**: при выключенном моке сети и наличии файла плана в `plans_dir` (подменённый
   `path_provider`) экран рисует `Key('route_floor_plan_image')` и баннер «Нет соединения — план из
   кэша…», а не состояние ошибки.

## 11. Ограничения и открытые вопросы

1. **⚠️ Прогресс маршрута сервер не хранит.** В API нет ни статуса точки маршрута, ни отметки
   «помещение пройдено»: есть только `TicketOperationCompletion` (по `operationId` внутри заявки).
   Поэтому статусы `pending/active/done/skipped` — **локальная** модель drift, а «done» выводится
   сопоставлением `operationId` техкарты помещения с `GET /api/tickets/:ticketId`. Последствия:
   (а) статус не виден бригадиру; (б) при переустановке приложения прогресс теряется, если операции
   не были отправлены; (в) «пропущено» вообще не существует для сервера. Требуется эндпоинт
   прогресса смены (например, `GET /api/schedule/events/:id/progress` + `POST …/points/:pointId/skip`).
2. **⚠️ Пропуск точки некуда записать.** Единственный «журнал» — комментарий к заявке
   (`POST /api/tickets/:id/comments`, текст вида «Пропущено: Каб. 211 — нет доступа, дверь
   заперта»). Это компромисс: комментарий видит бригадир, но он не привязан к точке и не влияет на
   прогресс. Требуется отметка пропуска на сервере.
3. **Координаты зависят от размеров плана.** `Room.coordsX/coordsY/coordsWidth/coordsHeight` —
   пиксели изображения плана, а `Floor.planWidth/planHeight` заполняются только при загрузке через
   `POST /api/floors/:id/plan-url` с явными размерами (или `POST /:id/plan`). Публичного эндпоинта
   «получить размеры картинки из file-service» нет: `GET /api/files/:id` отдаёт `width`/`height`, но
   `Floor` хранит не `fileId`, а `planImageUrl` — связать их можно только поиском по
   `GET /api/files?bucket=PLANS&entityType=FLOOR_PLAN&entityId=:floorId`. Та же проблема отмечена в
   DS-003 ([`../web-admin/floor_plan.md`](../web-admin/floor_plan.md) п. 10.3). До решения: если
   `planWidth/planHeight` пусты — маршрут открывается в режиме списка.
4. **Альфа-каналы недоступны.** Полупрозрачная заливка «текущего помещения» описана как
   `primary100` (непрозрачный) — токенов с alpha нет (README, пробел 4).
5. **`flutter_map`/OSM не используется** на этом экране: маршрут дня — план этажа (код Устава и
   `ПЛАН.md` М6.3). Если понадобится карта города (check-in по геозоне, позиция оператора),
   это отдельное решение: `flutter_map` есть в зависимостях, но токен Mapbox/тайлы в М6 не заявлены
   (`ПЛАН.md`, R3).
6. **Кэш плана и приватность.** Изображение плана объекта лежит в `plans_dir` открытым файлом;
   очистка — при выходе из аккаунта ([`profile.md`](./profile.md) §6) и при смене объекта.
