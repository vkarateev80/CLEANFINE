# ✅ Экран: Чек-лист помещения (`checklist`) — DS-002 (М6.4)

> DS-002 → `checklist.fig`; реализация — М6.4
> (`lib/features/checklist/presentation/pages/checklist_page.dart`, `widgets/operation_tile.dart`).
> Код-основа — `docs/agents/FRONTEND_MOBILE.md` п. 4 (`isLocked: index > 0 &&
> !checklistState.operations[index - 1].isCompleted`, `requiresPhoto` → `_takePhoto`,
> «Завершить помещение» при `allCompleted`) и `ПЛАН.md` М6.4 («операции техкарты по порядку,
> следующая заблокирована до завершения предыдущей, таймер операции, фото (camera; обязательное при
> `requiresPhoto`) → загрузка в file-service, „Завершить помещение“ → вызов endpoint М3.6»).
> Данные: core-service (3003) — помещение и техкарта; file-service (3002) — фото; ticket-service
> (3005) — факт завершения операции.

## 1. Назначение

Провести оператора по операциям техкарты помещения **строго по порядку** и оставить на сервере
доказательства: время, автор и (где требуется) фото. Экран закрывает три требования М6.4:

1. последовательность — вторая операция недоступна, пока не завершена первая;
2. время — таймер по каждой операции с сравнением с `TechOperation.estimatedTimeMin`;
3. доказательство — обязательное фото (`requiresPhoto`) загружается в file-service, а завершение
   уходит в ticket-service (`POST /api/tickets/:id/operations/:operationId/complete`), после чего
   **сервер сам** списывает материалы через событие `ticket.operation.completed`.

Экран ничего не знает о материалах и остатках: списание идёт в material-service по событию, в
приложении нет ни одной операции с материалами.

### 1.1. Точка входа в навигации

| Что | Значение |
|---|---|
| Маршрут | `/route/:eventId/room/:roomId?ticketId=…&pointId=…` |
| Кто открывает | [`route_map.md`](./route_map.md) — «Следующая точка», тап по маркеру → «Открыть чек-лист», строка списка точек |
| Что открывает | камера (`image_picker`), bottom sheet фото, возврат на `/route/:eventId` после «Завершить помещение» |
| Предусловие | смена в статусе `CHECKED_IN` **и** у смены есть `ticketId`. Иначе экран открывается read-only или блокируется (см. п. 5, строки «Только просмотр» и «Нет заявки») |

## 3. Состав блоков

### 3.1. Шапка и сводка

| Элемент | Источник | Правило |
|---|---|---|
| Название помещения | `GET /api/rooms/:id` → `name`, `floorId` → `Floor.number`/`name` | «{room.name} · {floor.number} этаж» |
| Прогресс маршрута | локальный `route_points` | `LinearProgressIndicator(value: done/total)` + «Прогресс маршрута: {done} из {total} помещений» |
| Сводка техкарты | `GET /api/tech-cards/:id` | «Техкарта: {name} · {operations.length} операций · ~{totalEstimatedTimeMin} мин» |
| Счётчик очереди | `pending_actions` | `SyncStatusWidget` в `AppBar` |
| SOS | — | `IconButton` в `AppBar` → `/sos` |

### 3.2. Операция техкарты (одна строка = одна `TechOperation`)

| Часть | Источник | Отображение |
|---|---|---|
| Порядковый номер | `orderIndex` (массив приходит отсортированным по `orderIndex`) | круг 24 dp с номером `orderIndex + 1` |
| Название | `name` | `sizeBASE`/`weightMedium`; выполненная — `neutral500` + зачёркивание `TextDecoration.lineThrough` |
| Описание | `description` | `sizeSM`, `neutral500`, `maxLines: 2`; раскрывается тапом по строке |
| Оборудование | `equipment` (JSON, например `{items: ['швабра','ведро'], ppe: ['перчатки']}`) | чипы `sizeXS` в раскрытом виде; JSON рендерится по ключам `items`/`ppe`, если они есть, иначе как `key: value` |
| Таймер | локальный `startedAtLocal`/`completedAtLocal` | `⏱ mm:ss`, моноширинный; > нормы — `warning600` с «+mm:ss сверх нормы» |
| Фото | `requiresPhoto` | чип «📷 Фото обязательно» (`danger600`); после съёмки — миниатюра 56×56 с `AppRadius.md` |
| QR | `requiresQr` | **не реализуется в М6** (нет ни сценария в `ПЛАН.md`, ни эндпоинта проверки QR): чип «Требуется QR» показывается информационно, завершение не блокирует — см. п. 11.5 |
| Материалы | `materials[]` (`materialId`, `consumptionPerOperation`, `unit`) | строка «Материалы: {N} поз.; спишет сервер» — остатки не показываем (их нет в контракте операции) |
| Действия | — | «Начать» (до первого тика), «Сделать фото» (`requiresPhoto`), «Завершить» |
| Заблокировано | `index > 0 && !operations[index - 1].isCompleted` | `IconButton`-замок `Icons.lock_outline` + «Доступно после операции «{название предыдущей}»»; кнопки `onPressed == null` |

### 3.3. Таймер операции

| Правило | Значение |
|---|---|
| Старт | автоматически при открытии чек-листа для **первой незавершённой** операции (`startedAtLocal = now`), если она ещё не начиналась; кнопка «Начать» позволяет перезапустить отсчёт вручную (например, оператор отвлёкся) |
| Тик | `Timer.periodic(1 s)` только для видимого экрана (`WidgetsBindingObserver` → пауза таймера при `AppLifecycleState.paused`, значение считается по wall-clock при возврате) |
| Остановка | при успешной отметке завершения или при уходе в очередь оффлайна (значение фиксируется) |
| Что уходит на сервер | только `completedAt` (ISO 8601, локальное время в UTC-формате) — поле `CompleteOperationDto.completedAt`; сервер время не пересчитывает |
| Норма | `TechOperation.estimatedTimeMin`; превышение — визуальное предупреждение, **не** блокирует завершение |
| Перезапуск приложения | `startedAtLocal` хранится в drift → таймер продолжается с реального времени |

### 3.4. Фото операции

| Шаг | Реализация | Детали |
|---|---|---|
| Съёмка | `image_picker.pickImage(source: ImageSource.camera, maxWidth: 1920, maxHeight: 1920, imageQuality: 85)` | `camera`-разрешение запрашивается в контексте действия |
| Проверка на клиенте | `width >= 1280 && height >= 720` | сервер отклоняет фото меньше (`file-service`, «фото ≥1280×720»); при меньшем размере — «Фото слишком маленькое. Снимите заново» и повтор |
| Превью | `Image.file` 100 % ширины, `AppRadius.md`; под ним время снимка | пользователь видит, что фото не «чёрный кадр» |
| Загрузка | `POST /api/files/upload` (multipart): `file`, `kind: 'photo'`, `userName` = `me.fullName`, `takenAt` = ISO снимка, `lat`/`lng` — последняя известная позиция | ответ `UploadedFileView`: нужен `url` (в него сервер уже положил водяной знак — `watermarked: true`), `thumbnailUrl`, `width`, `height` |
| Водяной знак | **на сервере** (`kind=photo`): имя, дата, координаты | приложение знак не рисует — иначе он разойдётся с серверным |
| Хранение до сети | файл копируется в `photos_dir/{operationId}.jpg`; после успешной загрузки рядом пишется `{operationId}.json` с `fileId`/`url` — повторная отправка не перезагружает фото | |
| Удаление | файл удаляется после успешного завершения операции (или по кнопке «Переснять») | экономия места на устройстве |
| Что передаётся в завершении | `photoUrl` (URL из file-service) **и** `requiresPhoto: true`, если операция требует фото | без `photoUrl` сервер вернёт 400 «Для операции требуется фото (photoUrl)» |

### 3.5. Завершение операции и помещения

| Действие | Запрос | Обработка ответа |
|---|---|---|
| Завершить операцию | `POST /api/tickets/:ticketId/operations/:operationId/complete` с телом `{completedAt, photoUrl?, requiresPhoto?, totalOperations?}` | `CompleteOperationResult`: `alreadyCompleted`, `completedOperations`, `operationsTotal`, `allOperationsCompleted` |
| `alreadyCompleted: true` | повторный вызов (идемпотентность сервера по `@@unique([ticketId, operationId])`) | это **успех**: операция помечается выполненной, из очереди удаляется |
| `totalOperations` | клиент передаёт **общее число операций маршрута смены** (сумма `operations.length` по всем точкам) | сервер запоминает значение при первом вызове и по нему считает `allOperationsCompleted`. Если маршрут пуст (нет техкарт) — поле не передаётся |
| Завершить помещение | локальная операция + `POST` завершений, если что-то не отправлено | все операции помещения должны иметь статус `completed` (локально) ИЛИ `synced`; затем точка маршрута → `done`, возврат на `/route/:eventId` со snackbar «Помещение завершено» |
| Не все операции завершены | кнопка `disabled` + подпись «Завершить помещение (осталось {N})» | серверного запрета нет — порядок обеспечивает клиент (п. 11.2) |

### 3.6. Прогресс маршрута

Источник — локальная таблица `route_points`: точка `done`, когда все `operationId` её техкарты
завершены (или в очереди на отправку). Итог показывается в шапке чек-листа, на маршруте
([`route_map.md`](./route_map.md) §3.4) и в таб-строке «Сегодня {done}/{total}». После «Завершить
помещение» прогресс увеличивается сразу, не дожидаясь ответа сервера (offline-first), а `pending`
синхронизируется отдельно.

| Успех | операция отмечена | строка `success600`, галочка, следующая операция разблокирована (`если это была первая незавершённая` → таймер стартует) |

## 10. Что проверяет widget-тест

1. **Блокировка шагов** (требование М6.4 «виджет-тест блокировки шагов»): техкарта из 2 операций,
   первая не завершена → у `Key('checklist_op_complete_button_op2')` `onPressed == null`, виден текст
   «Доступно после операции «Нанести чистящее средство»»; после мок-ответа на завершение `op1`
   кнопка `op2` активна.
2. **Обязательное фото**: операция с `requiresPhoto: true` → нажатие «Завершить» без фото не
   вызывает `ticketsRepository.completeOperation` и показывает «Сначала сделайте фото»;
   после мок-съёмки и загрузки (`fileRepository.upload` вернул `url`) вызов содержит `photoUrl` и
   `requiresPhoto: true`.
3. **«Завершить помещение» заблокировано неполным чек-листом**: при 1 из 2 завершённых операций
   кнопка `onPressed == null` и текст содержит «осталось 1»; после завершения обеих — активна, а
   после нажатия число «Пройдено» на маршруте увеличивается на 1.
4. **Оффлайн-завершение**: при выключенной сети завершение операции не падает с ошибкой, а
   появляется в `pending_actions` со статусом `pending` и строка операции показывает иконку
   ожидающей отправки («Отправляется…»).

## 11. Ограничения и открытые вопросы

1. **⚠️ «Завершить помещение» не существует на сервере.** API знает только завершение **операции**
   (`POST /api/tickets/:id/operations/:operationId/complete`). Отметка «помещение пройдено» живёт
   локально (drift) и выводится из набора завершённых операций техкарты. Следствия: бригадир не
   видит, что помещение закрыто (только отдельные операции); при переустановке приложения отметка
   восстанавливается только если операции успели уйти на сервер. Требуется учёт прогресса по
   `roomId` (см. также [`route_map.md`](./route_map.md) п. 11.1).
2. **⚠️ Порядок операций держит только клиент.** Сервер принимает завершение любой операции заявки
   в любом порядке (идемпотентность по паре `ticketId+operationId`, без проверки предыдущей). Если
   требование «следующая заблокирована» должно быть непреложным (например, для аудита), нужна
   серверная проверка порядка — сейчас это правило UI, и оно не защищает от подделки запроса.
3. **⚠️ Две комнаты с одной техкартой ломают чек-лист.** Ключ идемпотентности —
   `@@unique([ticketId, operationId])` (`ticket_operation_completions`), а заявка одна на **смену**
   (создаётся по смене, `ScheduleEvent.ticketId`), не на помещение. Значит, если техкарта
   «Влажная уборка санузла» назначена двум санузлам маршрута, второй санузел получит
   `alreadyCompleted: true` на те же `operationId` — прогресс второго помещения будет неверным
   (`done` без реальной работы) и материалы спишутся один раз. Требуется доработка: ключ
   `(ticketId, roomId, operationId)` либо операция-в-комнате как отдельная сущность
   (`TicketOperationCompletion` с `roomId`).
4. **⚠️ `ticketId` может отсутствовать.** Если schedule-service не смог создать заявку при генерации
   («Смена сохранена без ticketId — следующая генерация до-создаст заявку»,
   `schedule.service.ts`), чек-лист не может отправить ни одно завершение. В спецификации это
   блокирующее состояние с текстом для оператора; правильнее — до-создавать заявку при `check-in`
   или запрещать открытие смены без заявки.
5. **`requiresQr` не поддержан.** Поле есть в схеме `TechOperation`, но ни в `ПЛАН.md` М6, ни в
   DS-002 нет сканирования QR и нет эндпоинта проверки кода. Спецификация показывает чип
   «Требуется QR» и **не** блокирует завершение. Нужно решение: включать ли QR в М6.4.
6. **Таймер операции — локальный.** Сервер принимает `completedAt` от клиента и не хранит
   `startedAt`; проверить длительность операции по серверным данным нельзя. Если нужна
   «фактическая длительность» для отчётов, требуется передавать `startedAt` (новое поле в
   `CompleteOperationDto`) или отдельный эндпоинт старта операции.
7. **Фото не привязано к заявке.** `photoUrl` уходит в `TicketOperationCompletion`, но
   `POST /api/files/:id/attach {entityType: 'TICKET', entityId}` приложение не вызывает: файл
   остаётся в бакете без связи с сущностью (в списке вложений заявки `GET /api/files/attachments/
   TICKET/:id` его не будет). Нужно решить: привязывать (`attach`, `entityType: 'TICKET'`) или
   считать `photoUrl` достаточным.
