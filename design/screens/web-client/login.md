# 🔐 Экран: Вход в портал (`login`)

> DS-004 (М5.5) → реализация в М5.4 (`frontend/web-client/src/pages/Login/LoginPage.tsx`,
> каркас — `frontend/web-client/src/layouts/AuthLayout.tsx`).
> Тип артефакта — текстовая спецификация (см. [`README.md`](./README.md)), не бинарный макет.
> Экрана входа **нет** в перечне DS-004 (`dashboard`, `tickets`, `reports`, `chat`), но `ПЛАН.md`
> М5.4 называет вход частью задачи портала: *«роутер: `/login`, … Guard: роль CLIENT»*.
> Поэтому экран описан здесь — иначе первый же экран портала остаётся без спецификации.
> Данные: `POST /api/auth/login`, `GET /api/auth/me` (auth-service, :3001), `POST /api/auth/logout`.
> Источник требований — `docs/agents/FRONTEND_WEB.md` → Acceptance Criteria (Web Client):
> «Авторизация работает».

## 1. Назначение

Впустить заказчика в портал и **не впустить никого другого**. Экран решает три задачи:

1. аутентификация по email и паролю (та же учётная запись, что заводит админка);
2. отсечение ролей, которым портал не предназначен (оператор, бригадир, админ — их место в
   админке; увидев портал, они должны получить понятное объяснение, а не пустой дашборд);
3. запоминание сессии, чтобы телефон не требовал пароль при каждом открытии (refresh-токен).

Регистрации, восстановления пароля и «входа по коду» в портале нет: учётные записи заводит
администратор, а PIN/биометрия — сценарии мобильного приложения оператора (DS-002), не портала.

## 2. Маршрут и доступ

| Параметр | Значение |
|---|---|
| URL | `/login` (вне `ClientLayout`: без таб-бара и шапки объекта — объекта ещё «нет», он появится после входа) |
| Guard | обратный: уже авторизованный пользователь с ролью `CLIENT` редиректится на `/dashboard` (нельзя «застрять» на логине) |
| Запросы | `POST /api/auth/login { email, password }` → `{ accessToken, refreshToken }` → `GET /api/auth/me` |
| Роли | `CLIENT` → `/dashboard`; `OPERATOR`/`SUPERVISOR`/`ADMIN` → сообщение «Портал предназначен для заказчиков. Воспользуйтесь админ-панелью» + `POST /api/auth/logout` (роль приходит в ответе `/auth/me`, поэтому проверка — после получения профиля; токены к этому моменту уже выданы, их нужно погасить) |
| Выход | `POST /api/auth/logout { refreshToken }` → очистка стора → `/login` |
| Неавторизованный доступ | любой маршрут портала → редирект на `/login` с `state.from` (после входа возврат на исходный адрес) |
| Стенд | auth-service :3001; лимиты логина подняты (см. состояние стенда), поэтому счётчик неудачных попыток на UI не показываем |

## 4. Состав блоков

### 4.1. Карточка и шапка

| Элемент | Реализация | Обоснование |
|---|---|---|
| Каркас | копия `frontend/web-admin/src/layouts/AuthLayout.tsx`, но подпись «Портал заказчика» и `min-h-[100dvh]` вместо `min-h-screen` | на телефоне `100vh` даёт «прыжок» при появлении адресной строки |
| Логотип-строка | `🧹 Cleaning Ops` — `text-2xl font-semibold text-primary-600`, `text-center` | тот же текстовый логотип, что в админке (логотипа клиента нет — см. [`overview.md`](./overview.md) п. 8) |
| Подпись | «Портал заказчика» — `text-sm text-neutral-500` | сразу объясняет, куда попал пользователь |
| Карточка | `w-full max-w-md rounded-xl bg-white p-6 shadow-lg` (`p-8` у админки → `p-6`: на 360 px поля карточки заметны) | токены `--radius-xl`, `--shadow-lg` |

### 4.2. Поля формы

Форма — обычный `<form onSubmit>` (как в `LoginPage.tsx` админки), доступна с клавиатуры, кнопка —
`type="submit"` (вход по Enter в любом поле).

| Поле | Контрол | Обяз. | Атрибуты | Валидация на клиенте |
|---|---|---|---|---|
| Email | `Input type="email"` из `components/ui/Input.tsx` (`Field` с подписью) | ✔ | `name="email"`, `autoComplete="email"`, `inputMode="email"`, `autoCapitalize="none"`, `spellCheck={false}` | непустое; базовая проверка «есть `@` и точка после него» — сообщение «Введите корректный email» `text-xs text-danger-600` под полем |
| Пароль | `Input type="password"` | ✔ | `name="password"`, `autoComplete="current-password"` | непустой (≥1 символ); свою политику не навязываем — она может измениться в auth-service |
| Показать пароль | `Button variant="ghost" size="sm"` `min-h-[44px]`, `aria-pressed`, `aria-label` «Показать пароль» / «Скрыть пароль» | — | переключает `type` между `password` и `text` | нужно на телефоне: длинный пароль с телефона вводится с ошибками |

Шрифт ввода — `text-base` (≥16 px): иначе iOS зумит страницу при фокусе (см.
[`overview.md`](./overview.md) п. 7.5). Поля — на всю ширину карточки.

### 4.3. Сообщения об ошибках

| Код/случай | Сообщение | Вид |
|---|---|---|
| 401 (`/auth/login`) | «Неверный email или пароль» | `role="alert"`, `rounded-lg border border-danger-500 bg-white px-3 py-2 text-sm text-danger-600` — как `ErrorBanner`, но без кнопки «Повторить» (повтор = кнопка «Войти») |
| 400 (DTO) | текст из ответа (`errorMessage` из `components/ui/Feedback.tsx`) | там же; поля с ошибкой — `invalid` (`border-danger-500`) |
| 429 (лимит попыток) | «Слишком много попыток. Попробуйте позже» | там же; кнопка «Войти» — `disabled` на время, указанное в `Retry-After` (если заголовок есть) |
| 5xx/сеть | «Не удалось войти. Проверьте соединение с сервером» | там же |
| Роль не CLIENT | «Портал предназначен для заказчиков. Воспользуйтесь админ-панелью» | `SoftWarning` (`bg-neutral-100 text-warning-600`) + автоматический logout; кнопка возврата нет — сессии уже нет |
| Поля пусты | «Введите email и пароль» | тот же блок ошибки (как в админке) |

Сообщение **не** уточняет, что именно неверно (email или пароль) — иначе экран превращается в
инструмент перебора существующих учётных записей.

### 4.4. Нижняя подпись

«Забыли пароль? Обратитесь к менеджеру.» — `text-xs text-neutral-500 text-center`, ссылка на
менеджера отсутствует (телефона в конфигурации портала нет). Сброса пароля в API auth-service нет
(в `FRONTEND_WEB.md` он не заявлен) — обещать в интерфейсе нечего.

## 6. Состояния экрана

| Состояние | Триггер | Отображение |
|---|---|---|
| Ожидание ввода | пустая форма | кнопка «Войти» активна (не блокируем заранее — блокировка «серой» кнопки без объяснения хуже ошибки по нажатию) |
| Отправка | `loading` | кнопка `loading` (`Spinner` внутри, `Button` уже так умеет), поля `disabled`, повторный Enter не отправляет второй запрос |
| Ошибка 401/400 | ответ сервера | блок ошибки, фокус переводится на поле пароля (`ref.focus()`) — пользователь сразу может исправить |
| Успех | 200 + `/auth/me` с ролью `CLIENT` | редирект на `state.from ?? '/dashboard'`, кнопка остаётся в `loading` до перехода (не мигает «Войти» → «Вошли») |
| Успех, но роль не CLIENT | 200 + роль ≠ CLIENT | `SoftWarning` «Портал предназначен для заказчиков…», `POST /auth/logout`, форма остаётся (без токенов) |
| Сессия есть | валидный `accessToken` в сторе | редирект на `/dashboard` без показа формы (`AuthGuard` обратного направления) |
| Истёкший access, живой refresh | 401 на `/auth/me` | интерцептор `api/client.ts` обновляет токен прозрачно (single-flight) — пользователь ничего не замечает |

## 7. Действия пользователя

| Действие | Триггер | Результат |
|---|---|---|
| Войти | «Войти» / Enter | `POST /api/auth/login` → `GET /api/auth/me` → редирект |
| Показать/скрыть пароль | кнопка «показать» | переключение `type` поля |
| Выйти | на других экранах (в меню `?` header) | `POST /api/auth/logout` → `/login` |

## 8. Данные из API

| Запрос | Тело/ответ | Использование |
|---|---|---|
| `POST /api/auth/login` | `{ email, password }` → `{ accessToken, refreshToken }` | токены в `stores/authStore.ts` (`setTokens`) |
| `GET /api/auth/me` | `SessionUser`: `id`, `email`, `fullName`, `role`, `avatarUrl`, `isActive` (`frontend/web-admin/src/types.ts`) | роль для редиректа/отказа, имя — в меню портала |
| `POST /api/auth/logout` | `{ refreshToken }` | гашение сессии при выходе и при отказе по роли |

Файлы `api/client.ts` и `api/auth.ts` переносятся из web-admin **как есть** (см.
[`overview.md`](./overview.md) п. 4): интерцептор refresh обязателен и для портала — иначе
истёкший токен выкидывает клиента на логин посреди работы.

## 9. Мобильная адаптация

| Диапазон | Поведение |
|---|---|
| `320–359 px` | карточка `p-4`, логотип `text-xl`, `px-3` |
| `360–639 px` (**основной**) | карточка `max-w-md p-6`, поля на всю ширину, кнопка `size="lg" w-full min-h-[44px]` |
| `640–1023 px` | карточка по центру, `p-8` (как в админке) |
| `≥1024 px` | то же + `min-h-screen` вместо `100dvh` (десктопная адресная строка не «прыгает») |

Особенности телефона: `100dvh`, `autoComplete` (`email`, `current-password`) — менеджеры паролей
телефона подставляют данные в одно касание; `autoCapitalize="none"` для email; кнопка «показать
пароль» с областью нажатия ≥44 px; после ошибки — фокус в поле пароля, клавиатура открывается
сразу.

## 10. Ограничения и открытые вопросы

1. **Проверка роли только на клиенте.** `POST /api/auth/login` не различает роли: любой
   сотрудник получит токены, и лишь потом портал откажет. Правильнее — отдельная проверка на
   бэкенде (например, `GET /api/auth/me` + политика «портал только для CLIENT»), но это изменение
   auth-service, вне DS-004. До него отказ на UI — не защита, а вежливость (токены гасятся).
2. **Привязка клиента к объекту** — [`overview.md`](./overview.md) п. 10.1: после входа портал
   должен знать, какой объект показывать. Возможно, `/auth/me` придётся расширить полем объекта;
   тогда экран входа получит шаг «выбор объекта» при нескольких объектах у одного клиента.
3. **Восстановление пароля** в API отсутствует. Если бизнес потребует — это auth-service + письмо
   (notification-service), а не правка экрана.
4. **Лимиты логина**: лимиты на стенде подняты; в продакшене экран должен показывать `Retry-After`
   (сейчас описано как «попробуйте позже») — уточнить контракт 429.
5. **Запоминание сессии**: refresh-токен хранится там же, где в админке (`authStore`). Вопрос
   «выход по бездействию» в портале не решён (мобильный сценарий провоцирует долгие паузы);
   предлагается считать сессию живой, пока жив refresh-токен.
6. **Один вход для двух приложений**: клиент и сотрудник входят одним endpoint'ом; портал не
   должен показывать ссылку «перейти в админку» (это разное ПО с разными доменами).

## 11. Критерии приёмки (чек-лист)

- [ ] `/login` — единственный публичный маршрут портала; любой другой адрес без токена редиректит на `/login` с возвратом на исходный после входа.
- [ ] Вход с валидными данными роли `CLIENT` приводит на `/dashboard`; имя/роль в сессии соответствуют `GET /api/auth/me`.
- [ ] Вход под `ADMIN`/`SUPERVISOR`/`OPERATOR` не пускает в портал: показано сообщение про админ-панель, сессия погашена (`logout`), токены не остаются в сторе.
- [ ] Ошибки различаются: 401 — «Неверный email или пароль», 400 — текст DTO, 429 — «Слишком много попыток», 5xx/сеть — «Не удалось войти…».
- [ ] Пустые поля не отправляют запрос: показывается «Введите email и пароль».
- [ ] Во время запроса кнопка в `loading`, поля `disabled`, повторное нажатие/Enter не создаёт второй запрос.
- [ ] Пароль скрыт по умолчанию, кнопка «показать» переключает видимость и имеет `aria-label`/`aria-pressed`.
- [ ] На 360 px карточка занимает ширину без горизонтального скролла, шрифт ввода ≥16 px (нет зума iOS), `100dvh` вместо `100vh`.
- [ ] Менеджеры паролей телефона работают (`autoComplete="email"` / `"current-password"`).
- [ ] Только токены `tokens.css` и компоненты UI-кита из [`overview.md`](./overview.md) п. 4 (в том числе `AuthLayout` и `api/auth.ts` перенесены из web-admin без изменения поведения).
