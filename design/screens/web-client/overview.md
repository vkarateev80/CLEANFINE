# 📱 Обзор портала заказчика (`web-client`) — DS-004 (М5.5)

> Не экран, а общий раздел: каркас, навигация, доступ и правила мобильной адаптации, на которые
> ссылаются [`dashboard.md`](./dashboard.md), [`tickets.md`](./tickets.md), [`reports.md`](./reports.md),
> [`chat.md`](./chat.md) и [`login.md`](./login.md).
> Источник состава экранов — `docs/agents/DESIGN_SYSTEM.md` → «Задача DS-004»; функциональность —
> `ПЛАН.md` М5.4; критерии приёмки — `docs/agents/FRONTEND_WEB.md` → «Acceptance Criteria (Web Client)».

## 1. Назначение портала

Портал закрывает цикл «клиент создал заявку → менеджер ответил → статус виден клиенту»
(DoD фазы М5, `ПЛАН.md`). Это **тонкий клиент**: ни справочников, ни CRUD объектов, ни
редактирования заявок — четыре действия пользователя:

1. посмотреть состояние своего объекта (`/dashboard`);
2. создать заявку и следить за её статусом (`/tickets`);
3. посмотреть отчёты по своему объекту (`/reports`);
4. написать менеджеру в чат (`/chat`).

Всё остальное — ответственность админки (`frontend/web-admin`, DS-003): портал не дублирует её
экраны даже в урезанном виде. Если требование можно решить ссылкой «позвоните менеджеру» или
письмом в чат — оно не становится экраном портала.

## 2. Роль и права

| Что | Значение |
|---|---|
| Роль | `CLIENT` (`shared/types/roles.ts` → `ROLE_LABELS.CLIENT = 'Клиент'`) |
| Вход | `POST /api/auth/login` (email + пароль) → `GET /api/auth/me`; JWT + refresh, как в админке |
| Guard'ы | `AuthGuard` + `RoleGuard roles={['CLIENT']}` на всём дереве маршрутов портала |
| Чтение | объект клиента, заявки объекта, смены объекта, остатки по объекту, отчёт по расходу, свой чат с менеджером |
| Запись | **только** `POST /api/tickets` (обычная/внеплановая заявка), комментарий к своей заявке, сообщение в чат |
| Запрещено | смена статуса заявки, назначение исполнителя, аварийная заявка (SOS), правка объекта, материалы, сотрудники, GPS, разделы админки |

Права **повторяют `@Roles(...)` бэкенда, а не заменяют их**:

| Действие | Endpoint | Роли по контроллеру | Источник |
|---|---|---|---|
| Создать заявку | `POST /api/tickets` | `ADMIN, SUPERVISOR, CLIENT` | `backend/ticket-service/src/tickets/tickets.controller.ts:25` |
| Сменить статус | `PATCH /api/tickets/:id/status` | `ADMIN, SUPERVISOR, OPERATOR` — **у клиента кнопок нет** | там же:64 |
| Назначить исполнителя | `POST /api/tickets/:id/assign` | `ADMIN, SUPERVISOR` — **у клиента кнопок нет** | там же:81 |
| Чтение списка/детали заявки | `GET /api/tickets`, `GET /api/tickets/:id` | без `@Roles` (все авторизованные) | там же |
| Объект | `GET /api/objects/:id` | без ограничения по роли | `backend/core-service/src/objects/objects.controller.ts` |
| Смены объекта | `GET /api/schedule/events?objectId=` | без `@Roles` на `GET` | `frontend/web-admin/src/api/schedule.ts` (шапка файла) |
| Отчёт по расходу | `GET /api/materials/report?objectId=&from=&to=` | без `@Roles` на `GET` | `frontend/web-admin/src/api/materials.ts` |

Портал **не** строит прав на роли внутри страницы (в отличие от админки, где `usePermissions`
прячет кнопки): клиент один, все его права известны заранее. Единственное место с проверкой —
кнопки, которых у клиента быть не должно: их просто не рендерим (не «disabled», а отсутствие —
`disabled` кнопка намекает, что право можно получить).

### 2.1. Scope «только свой объект» — узкое место, требующее решения

`backend/auth-service/prisma/schema.prisma` → `model User` **не содержит ссылки на объект**
(полей `objectId`/`clientId` нет), а контроллер ticket-service на `GET /api/tickets` не фильтрует
заявки по роли. Значит, «клиент видит только свой объект» бэкенд сегодня не обеспечивает: портал
обязан (а) знать `objectId` клиента и (б) всегда передавать его фильтром. Варианты привязки — в
открытых вопросах п. 9.1; до решения портала **нельзя** считать требование М5.4 «доступ только к
своему объекту» выполненным.

Обязательные правила портала при любом варианте привязки:

1. `objectId` берётся **из сессии** (`GET /api/auth/me`, расширенное поле привязки) либо из
   единственного объекта, у которого `Object.clientName` совпадает с клиентом. Никогда — из
   query-строки, введённой пользователем.
2. Все списочные запросы уходят с `objectId=<свой>` (заявки, смены, остатки, отчёт).
3. Любой **403** от бэкенда на чтение — это не «ошибка сети»: показываем отдельный экран
   «Нет доступа к объекту» (`dashboard.md` п. 6), а не баннер «Повторить».
4. Любой URL вида `/tickets/:id` с чужим `id` приводит к 403 → редирект на `/tickets` с
   сообщением «Заявка не найдена или недоступна» (детали — `tickets.md` п. 6).

Портал — **второе React-приложение** (`pnpm create vite web-client`, М5.4): оно не импортирует

| Новое | Почему нет в админке |

## 5. Состояния: единые правила для всех экранов портала

| Состояние | Как выглядит | Компонент |
|---|---|---|
| Первая загрузка | скелетон из 3–5 строк `animate-pulse rounded-md bg-neutral-200 h-4` — держит высоту, чтобы вёрстка не «прыгала» на телефоне | `LoadingBlock` или локальный скелетон |
| Обновление (refetch) | контент `opacity-60`, без подмены скелетоном: на телефоне мигание раздражает | — |
| Пусто (нет данных) | dashed-карточка `rounded-xl border border-dashed border-neutral-300 bg-white p-10 text-center`, заголовок `text-sm font-medium text-neutral-500`, подсказка `text-xs text-neutral-400`, действие — `Button` | `EmptyState` |
| Ошибка сети/5xx | баннер `rounded-lg border border-danger-500 bg-white px-4 py-3 text-sm text-danger-600` + `Button variant="ghost" size="sm"` «Повторить» | `ErrorBanner` |
| **403** | **отдельный экран**, не баннер: «Нет доступа к объекту», подпись «Обратитесь к менеджеру», кнопка «Выйти» | `EmptyState` + логика в п. 2.1 |
| 404 | «Не найдено или удалено» + `Button variant="secondary"` «Назад» | `EmptyState` |
| Частичные данные | `SoftWarning`: данные показаны, но устарели/неполные (`text-warning-600` на `bg-neutral-100`) | `SoftWarning` |
| Offline / нет сети | тот же `SoftWarning` с текстом «Нет соединения — данные могут быть устаревшими» (TanStack Query отдаёт кэш при `refetchOnReconnect`) | `SoftWarning` |

## 6. Данные и API: общие правила

1. **Только чтение + создание заявки + сообщение в чат.** Ни одного `PATCH`/`DELETE` в портале нет.
2. **Пагинация** — серверная, `skip`/`take` (`take` по умолчанию 20 на телефоне вместо 50 в
   админке: меньше трафика на мобильной сети; максимум 100 — соглашение сервисов).
3. **Все запросы с `objectId` клиента** (п. 2.1), список заявок дополнительно с `status`/`type`.
4. **Кэш** — TanStack Query, как в админке: `staleTime` 30 с для списков, `refetchOnWindowFocus`
   включён (пользователь возвращается в браузер телефона — данные должны обновиться).
5. **Инвалидация** после `POST /api/tickets` — ключ `['tickets', objectId, filters]`,
   после отправки сообщения — `['chat', chatId]`.
6. **Границы диапазона дат** (отчёты) проверяются на клиенте: `from ≤ to`, максимум 366 дней —
   иначе сервер вернёт слишком большой набор и телефон «задумается».

## 7. Мобильная адаптация (общая часть)

Портал открывают **с телефона**, поэтому диапазоны описаны от меньшего к большему (зеркально
админке, где база — `≥1280 px`):

| Диапазон | Каркас | Контент |
|---|---|---|
| `320–359 px` (узкие Android) | таб-бар `grid-cols-4`, подписи `text-[10px]` | один столбец, `p-3`; длинные числа и email переносятся, горизонтального скролла нет |
| `360–639 px` (**основной**) | header `h-14` + фиксированный таб-бар `h-16` | один столбец, `p-4`; карточки вместо таблиц |
| `640–1023 px` (планшет, ландшафт телефона) | таб-бар остаётся | 2 колонки (`sm:grid-cols-2`) для KPI и карточек |
| `≥1024 px` (десктоп, редкий сценарий) | таб-бар скрывается, пункты переезжают в header как горизонтальное меню | контент `max-w-screen-md mx-auto`, 2–3 колонки |

Правила, обязательные для всех экранов:

1. **Область нажатия ≥44×44 px.** `Button size="sm"` (`py-1.5`) на телефоне дополняется
   `min-h-[44px]` там, где кнопка — основное действие; иначе `size="md"` (`py-2`, `min-h` ≈ 40 px)
   тоже получает `min-h-[44px]`.
2. **Никаких hover-only действий.** В админке действия живут в dropdown `⋮`; на телефоне
   dropdown заменяется видимыми кнопками в карточке или «шторкой».
3. **Никакого горизонтального скролла.** Таблицы админки превращаются в карточки
   (`rounded-lg border border-neutral-200 bg-white p-4`), а не в `overflow-x-auto`.
4. **Модалки → «шторки».** Ниже `640 px` `Modal` рендерится как bottom sheet: `fixed inset-x-0
   bottom-0 rounded-t-2xl bg-white p-4 shadow-xl`, ручка `mx-auto mb-3 h-1 w-10 rounded-full
   bg-neutral-300`, кнопки — `sticky bottom-0` и на всю ширину. API `Modal` сохраняется.
5. **Формы: контролы на всю ширину**, шрифт ввода ≥16 px (`text-base`) — иначе iOS зумит страницу
   при фокусе. В админке поля `text-sm`, для формы заявки это переопределяется.
6. **Даты и суммы** — `font-mono`, формат `dd.MM.yyyy` (и `HH:mm` для времени).
7. **Touch-жесты**: pull-to-refresh (нативный браузерный `overscroll-behavior` не отключаем),
   «Назад» браузера работает всегда — состояние экрана в query-строке URL (`useSearchParams`),
   как у фильтров в админке (`objects_list.md` п. 4.2).
8. **Клавиатура.** В формах сохраняем `inputMode`/`autoComplete` (`email`, `tel`); после отправки
   формы фокус переносится на заголовок результата (скринридер объявляет изменение).
9. **Производительность.** Целевой LCP < 2 c (`FRONTEND_WEB.md` → Acceptance Criteria):
   скелетоны вместо спиннера на весь экран, изображения планов этажа — `loading="lazy"`,
   `decoding="async"`.

| Цвета клиента (primary-палитра под бренд) | `design/tokens/colors.json` — один брендовый `primary`; переопределение `--color-primary-*` на объект означает **генерацию темы из настроек объекта** (`design/scripts/generate.mjs` работает офлайн, по статическому JSON, а не из БД) плюс контроль контраста для каждого клиента. Это новый механизм тем, а не экран. |
| Название компании клиента в футере, реквизиты, контакты менеджера | Данные без источника: у `Object` нет полей юрлица/ИНН; контакт есть только `clientContact`. Сейчас показывается «менеджер: {ФИО менеджера из чата}» в `chat.md`, остальное — отдельная задача. |
| Кастомный домен/поддомен, `favicon` клиента | Инфраструктурная задача (DevOps), к экранам не относится. |

Правило на будущее: когда branding появится как данные (поле в объекте + бакет файлов), он
добавляется **переопределением токенов у корневого контейнера портала**
(`<div style={{ '--color-primary-500': … }}>`), а не правкой компонентов — иначе цвета
разъедутся по страницам. До этого момента портал использует палитру токенов как есть.

## 9. Доступность (accessibility)

- Все интерактивные элементы — нативные `button`/`a`/`input` (в админке так же: `Button`
  рендерит `<button>`), доступны с клавиатуры и скринридера.
- Контраст текста: `text-neutral-900`/`-800` на белом, `text-neutral-500` — только для
  вторичных подписей; статусные цвета идут в паре «точка + текст semantic-600», а не цветным
  фоном (мягких `*-50` в токенах нет).
- Статусы не передаются **только** цветом: у бейджа всегда есть текстовая подпись.
- `aria-live="polite"` на ленту чата (новое сообщение объявляется) и на баннер ошибки
  (`role="alert"` уже есть в `ErrorBanner`).
- Размер основного текста ≥14 px (`text-sm`), подписи ≥12 px (`text-xs`) — ниже не опускаемся.

## 10. Open questions (общие; частные — в файлах экранов)

1. **Привязка клиента к объекту** — `User` не содержит `objectId`; как определяется «свой
   объект» (новое поле в auth-service / связь через `Object.clientName` / отдельная таблица
   `client_objects`)? Без решения требование М5.4 «только свой объект» не проверяемо (п. 2.1).
2. **Backend не ограничивает выборку по роли** (`GET /api/tickets` без `@Roles` и без фильтра по
   клиенту) — временно защищаемся фильтром `objectId` на клиенте; нужен серверный scope, иначе
   данные защищены только интерфейсом.
3. **Один клиент = один объект?** В `PLAN.md` М5.4 — «свой объект» (единственное число), в
   `Object.clientName` — строка, допускающая несколько объектов на одно имя. Если объектов
   несколько, нужен выбор объекта (селект в header) — сейчас спецификации исходят из одного.
4. **Кто такой «менеджер»** для чата `/chat` и для `DIRECT`-чата: конкретный SUPERVISOR объекта?
   Первый доступный? Требуется правило из М5.3 (см. `chat.md` п. 10).
5. **Уведомления в портале**: только счётчик или полноценный список `/notifications`?
   В DS-004 списка нет, но `NotificationBell` из админки просит страницу — временно счётчик
   ведёт в `/chat`/`/tickets` по типу уведомления.
6. **Иконки**: текстовые глифы или SVG? Отдельная библиотека иконок не заявлена ни в УСТАВЕ,
   ни в DS; до решения используем глифы.
