# 💬 Экран: Чат с менеджером (`chat`)

> DS-004 (М5.5) → реализация в М5.4 (`frontend/web-client/src/pages/Chat/ChatPage.tsx`,
> компоненты `MessageList.tsx` / `MessageComposer.tsx`).
> Тип артефакта — текстовая спецификация (см. [`README.md`](./README.md)), не бинарный макет.
> Роль — `CLIENT`; переписка ведётся только с менеджером своего объекта.
> Данные: chat-service (М5.1/М5.2) — **в `backend/` такого сервиса ещё нет** (на момент М5.5
> существует 8 сервисов без `chat-service`), поэтому контракт ниже описан по
> `docs/agents/BACKEND_CHAT.md` и `docs/agents/FRONTEND_WEB.md` (раздел `useWebSocket`)
> **как ожидаемый**. Источник истины при реализации — Swagger chat-service после М5.1/М5.2.
> Источник требований — `docs/agents/DESIGN_SYSTEM.md` → DS-004 («chat — Чат с менеджером»),
> `ПЛАН.md` М5.4 (`/chat` — с менеджером), М5.3 (чаты в админке), М5.6 (e2e портала).

## 1. Назначение

Единственный канал связи клиента с обслуживающей организацией внутри портала. Заменяет
«позвонить менеджеру» там, где нужен текст, фото-описание или след переписки: уточнение по
заявке, согласование доступа в помещение, вопрос по отчёту.

Экран закрывает последнюю треть цикла DoD М5: «клиент создал заявку → **менеджер ответил** →
статус виден клиенту». До появления М5.3 (чаты в админке) переписка физически невозможна —
спецификация готова заранее и опирается на контракт `BACKEND_CHAT.md`.

## 2. Маршрут и доступ

| Параметр | Значение |
|---|---|
| URL | `/chat` (при необходимости конкретной переписки — `/chat/:chatId`; по умолчанию открывается чат с менеджером) |
| Пункт меню | «Чат» — четвёртый (последний) пункт нижнего таб-бара; при непрочитанных — точка-счётчик |
| Guard | `AuthGuard` + `RoleGuard roles={['CLIENT']}` |
| Транспорт | Socket.io, namespace `chat`, JWT в `auth.token` соединения (`FRONTEND_WEB.md` → `useWebSocket`) |
| Тип чата | `DIRECT` (личный чат клиент ↔ менеджер). `OBJECT`/`TICKET`-чаты клиенту в портале не показываем (в объектный чат пишут все сотрудники — для клиента это шум) |
| Чтение истории | `GET`-эндпоинты chat-service (М5.2: история с пагинацией, поиск по тексту) — точные пути уточняются по Swagger |
| Запись | `message:send` (текст, при М5.2 — вложение), `message:read` |
| Событие оффлайн-получателя | `message:new` не приходит → сервер шлёт push через notification-service (`BACKEND_CHAT.md` п. 1, шаг 3) |
| Чужой чат | `403` при подписке/истории → сообщение «Чат недоступен» и возврат на `/dashboard` (для клиента 403 и 404 не различаем) |
| Недоступен chat-service | WS не подключается → экран переходит в режим «только история» (п. 6, состояние «Сервис чата недоступен») |

### 2.1. Кто такой «менеджер»

В контракте `BACKEND_CHAT.md` чат описывается парой участников, но правила «кто менеджер объекта»
там нет. Спецификация исходит из простейшего варианта и фиксирует его как открытый вопрос (п. 10.1):

1. Backend (М5.1) отдаёт клиенту **его единственный `DIRECT`-чат** с сотрудником: `GET`-список
   чатов текущего пользователя (id берётся из JWT).
2. Заголовок переписки — `ФИО собеседника` из карточки чата (сотрудникский `/api/users` клиенту
   закрыт, поэтому имя приходит **в самом чате**, а не отдельным запросом).
3. Если `DIRECT`-чатов несколько (менеджер сменился) — показываем список переписок, а не
   «склеенный» чат: история разных менеджеров не должна сливаться.

### 4.2. Лента сообщений

| Элемент | Правило |
|---|---|
| Контейнер | `flex flex-1 flex-col gap-2 overflow-y-auto p-4`; при открытии — автоскролл к последнему сообщению (`scrollIntoView({ block: 'end' })`); при подгрузке истории сохраняется позиция (иначе «прыжок» вверх) |

| Время | `text-[10px] text-neutral-400` (внутри пузыря снизу справа) — `font-mono`, `HH:mm`; у исходящих дополнительно галочки прочтения: `✓` — отправлено, `✓✓` — прочитано (`message:read`); цвет `text-white/70` внутри пузыря |
| День | разделитель `mx-auto rounded-full bg-neutral-100 px-3 py-1 text-xs text-neutral-500` с датой «21 сентября» (`dd.MM.yyyy`, если год не текущий) |
| Системное сообщение | по центру, `text-xs text-neutral-500`, без пузыря: «Заявка S-1042 создана», «Исполнитель назначен» (тип `SYSTEM` из `ChatType`) |
| Отправляется (optimistic) | пузырь сразу, `bg-primary-500/70`; при ошибке — рамка `border-danger-500` и подпись «Не отправлено · Повторить» (`Button variant="ghost" size="sm"`), сообщение остаётся в ленте до ретрая или удаления (P2) |
| Вложение (М5.2) | изображение — превью `max-h-60 rounded-lg`, нажатие открывает полноэкранный просмотр; файл — строка `flex items-center gap-2 rounded-lg border border-neutral-200 bg-white px-3 py-2` с именем и размером |
| Новое сообщение при открытом экране | автоскролл, если пользователь у нижней границы ленты; если он выше — показываем плашку «↓ Новое сообщение» (`Button variant="primary" size="sm"`, `sticky bottom-2`), тап ведёт вниз |

Максимальная ширина пузыря 80 % — чтобы на узком экране всегда были видны обе стороны диалога.

### 4.3. Поле ввода («composer»)

Во всю ширину, `sticky bottom-0` над таб-баром, но с учётом клавиатуры
(`100dvh` вместо `100vh` для контейнера экрана, `pb-[env(safe-area-inset-bottom)]`):

| Элемент | Реализация |
|---|---|
| Поле текста | `Textarea` с автоувеличением высоты (`rows=1`, максимум 5 строк, далее скролл), `text-base` (≥16 px — iOS не зумит), `placeholder` «Написать сообщение…» |
| Кнопка вложения | `Button variant="ghost" size="sm"`, `min-h-[44px]`; доступна при М5.2 (иначе скрыта) |
| Кнопка отправки | круглая `h-11 w-11 rounded-full bg-primary-500 text-white` с иконкой `➤`; `disabled`, пока текст пуст; `aria-label="Отправить сообщение"` |
| Поведение Enter | на телефоне Enter — перенос строки (отправка кнопкой); на `≥1024 px` — `Enter` отправляет, `Shift+Enter` переносит |
| Черновик | текст сохраняется в `localStorage` по ключу `chat-draft:{chatId}` — закрытие клавиатуры или уход на другую вкладку не теряет набранное |
| Индикатор набора | «печатает…» рядом с заголовком (если chat-service отдаёт `typing`-событие; в `BACKEND_CHAT.md` его нет — P2, открытый вопрос п. 10.4) |

Таб-бар при открытой клавиатуре **скрывается** (`visualViewport` API / `focus`/`blur`): иначе
composer упирается в нижнюю навигацию и поле ввода уходит под неё.

| Ошибка истории | 5xx/сеть | `ErrorBanner` «Не удалось загрузить переписку» + «Повторить»; composer остаётся активным (история подтянется) |

| **Сервис чата недоступен** | chat-service не поднят (М5.1 не сделана) или 5xx на истории | экран переходит в режим «только история»: лента из кэша (если есть), `SoftWarning` «Чат временно недоступен. | Офлайн (браузер) | `navigator.onLine = false` | тот же `SoftWarning` + сообщения складываются в очередь (п. 7.3) и уходят при восстановлении |
| Прочитано | входящее попало в видимую область | отправляем `message:read`; у собеседника появляется `✓✓` (`message:read` → отправителю) |

## 7. Действия пользователя

| Действие | Триггер | Результат |
|---|---|---|
| Отправить сообщение | кнопка `➤` (или Enter на десктопе) | `message:send { chatId, text, clientMessageId }`; optimistic-пузырь; очистка поля и черновика |
| Прочитать | сообщение в видимой области | `message:read { messageId }` (один раз на сообщение) |
| Прикрепить файл | `📎` (М5.2) | выбор файла → загрузка в file-service → отправка сообщения со ссылкой; прогресс `Spinner` в пузыре |
| Подгрузить историю | скролл вверх до начала ленты | запрос предыдущей страницы (М5.2: пагинация), позиция скролла сохраняется |
| Открыть заявку | пилюля «Заявка S-…» / системное сообщение | `/tickets/:id` |
| Начать заявку | ссылка в состоянии «сервис недоступен» | `/tickets` (шторка создания) |
| Переключить чат | «← Все чаты» (если переписок несколько) | список `DIRECT`-чатов (п. 2.1) |

### 7.1. Подключение (одно на экран)

```
только при наличии accessToken и только с экрана /chat:
io(`${VITE_WS_URL}/chat`, { auth: { token }, transports: ['websocket'], reconnection: true })
  on 'connect'        → статус «онлайн», досылка очереди
  on 'message:new'    → в лента (если chatId совпадает), инкремент непрочитанных, автоскролл
  on 'message:read'   → у своих сообщений ✓ → ✓✓
  on 'disconnect'     → SoftWarning, статус «нет соединения»
  cleanup при размонтировании → socket.disconnect()  (иначе утечка соединений на телефоне)
```

Приём из `FRONTEND_WEB.md` (раздел `useWebSocket`) сохранён дословно: тот же namespace, то же
имя события `message:new`, тот же `auth.token`. Хук выносится в `hooks/useChatSocket.ts`.

### 7.2. Прочтение

Сообщение считается прочитанным, когда пузырь попал в видимую область (`IntersectionObserver`)
**и** окно в фокусе (`document.visibilityState === 'visible'`) — иначе сообщение «прочитается»
фоном, когда телефон в кармане, и менеджер получит ложный сигнал.

### 7.3. Очередь офлайн-сообщений

Отправленное без соединения сообщение не теряется: хранится в памяти (и в `localStorage` до
перезагрузки) с `clientMessageId`, показывается как «отправляется», и уходит `message:send` при
`connect`. `clientMessageId` даёт идемпотентность: сервер (М5.1) должен отбрасывать повтор с тем
же id — открытый вопрос п. 10.3.

### 8.2. Формат сообщения (по `BACKEND_CHAT.md`)

| Поле | Тип | Использование |
|---|---|---|
| `id` | string | ключ пузыря, `message:read` |

| `640–1023 px` | лента `max-w-2xl mx-auto`; composer той же ширины; поле ввода растёт до 6 строк |
| `≥1024 px` | двухпанельный вид (как в мессенджерах): слева список чатов `w-72`, справа лента; таб-бар → меню в header; Enter отправляет |

Особенности телефона (обязательные):

1. Контейнер экрана — `h-[100dvh]` (не `100vh`): иначе на iOS при открытой клавиатуре лента
   «уезжает» за экран.
2. Composer — `sticky bottom-0` с `pb-[env(safe-area-inset-bottom)]`; таб-бар не перекрывает поле.
3. Автоскролл **только** если пользователь у нижней границы ленты; иначе — плашка «↓ Новое сообщение».
4. Никакого `position: fixed` для всей ленты: на мобильных браузерах с динамической адресной
   строкой это даёт «дрожание»; используем flex-контейнер на всю высоту.
5. Фокус в поле ввода не зуммит страницу: шрифт ввода `text-base` (16 px).
6. Размонтирование экрана закрывает WS-соединение (иначе после нескольких переходов таб-бар
   покажет неверный счётчик непрочитанных).

## 10. Ограничения и открытые вопросы

1. **Кто менеджер клиента** (п. 2.1): правила привязки нет ни в `BACKEND_CHAT.md`, ни в `ПЛАН.md`
   М5.3. Варианты: единственный SUPERVISOR объекта; назначенный в админке менеджер; первый
   сотрудник, создавший `DIRECT`-чат. Требуется решение Backend/архитектора — без него экран не
   знает, с кем открывать переписку.
2. **Человекочитаемый номер заявки** в системных сообщениях и пилюле — та же проблема, что в
   [`tickets.md`](./tickets.md) п. 10.2 (номера в схеме нет).
3. **Идемпотентность `message:send` — закрыта (М6, 26.09.2026).** Клиент генерирует
   `clientMessageId` на одну попытку пользователя; WS-отправка и REST-фолбэк после таймаута
   шлют один и тот же ключ, сервер возвращает уже сохранённое сообщение вместо создания
   дубля (уникальный индекс `(authorId, clientMessageId)`).
4. **Событие «печатает»** (`typing`) в `BACKEND_CHAT.md` отсутствует — индикатор набора описан как
   P2 и включается только после появления события в сервисе.
5. **Вложения** — М5.2 (файлы и история). До неё кнопка `📎` скрыта; после — нужен бакет
   (`documents`, по `ПЛАН.md` М5.2) и лимит размера.
6. **Пуш-уведомления оффлайн-получателю** идут через notification-service; портал ничего не
   делает, кроме подписки на счётчик непрочитанных (`/dashboard`).
7. **Модерация/удаление сообщений** клиентом не предусмотрены (нет в DS-004 и в контракте).
8. **Один чат или несколько.** Если менеджеров несколько, нужен список переписок (п. 2.1 п. 3);
   в М5.4 заявлен один `/chat` без параметров — спецификация покрывает оба варианта.

## 11. Критерии приёмки (чек-лист)

- [ ] `/chat` доступен только роли `CLIENT`; WS-соединение открывается с JWT из сессии и закрывается при уходе с экрана.
- [ ] Переписка ведётся только с менеджером (`DIRECT`); доступа к `OBJECT`/`TICKET`-чатам и к чужому `chatId` нет (403 → «Чат недоступен»).
- [ ] Отправка текста: сообщение появляется в ленте оптимистично, собеседник получает его через `message:new` (проверяется двумя клиентами, как в e2e М5.6), при ошибке — «Не отправлено · Повторить».
- [ ] `message:read` отправляется только для видимых сообщений в активном окне; у отправителя `✓` меняется на `✓✓`.
- [ ] Состояния: подключение, загрузка истории (скелетоны), пустая переписка (подсказки), ошибка истории, разрыв соединения, «сервис недоступен» (composer скрыт + ссылка на создание заявки).
- [ ] Enter/кнопка: на телефоне Enter переносит строку, отправка — кнопкой `➤`; на десктопе Enter отправляет.
- [ ] На 360 px: composer виден над клавиатурой, таб-бар скрыт, горизонтального скролла нет, пузыри не выходят за `80 %` ширины, `100dvh` использован вместо `100vh`.
- [ ] Черновик сообщения сохраняется и восстанавливается после случайного закрытия вкладки.
- [ ] Новое сообщение при прокрученной вверх ленте не «дёргает» скролл: показывается плашка «↓ Новое сообщение».
- [ ] Счётчик непрочитанных в таб-баре увеличивается на новое сообщение и обнуляется после прочтения.
- [ ] Только токены `tokens.css` и компоненты из [`overview.md`](./overview.md) п. 4; библиотек для чата (эмодзи-пикеры, markdown) не добавлено.
