# 🎫 Экран: Заявки (`tickets`) — список и создание

> DS-004 (М5.5) → реализация в М5.4 (`frontend/web-client/src/pages/Tickets/TicketsPage.tsx`,
> форма — `TicketFormSheet.tsx`). Тип артефакта — текстовая спецификация (см. [`README.md`](./README.md)).
> Роль — `CLIENT`; данные — только по своему объекту (см. [`overview.md`](./overview.md) п. 2.1).
> Данные: `GET /api/tickets?objectId=&skip=&take=` (ticket-service, М3.7),
> `GET /api/tickets/:id`, `POST /api/tickets`, `POST /api/tickets/:id/comments`.
> Источник требований — `docs/agents/DESIGN_SYSTEM.md` → DS-004 («tickets — Создание заявки»),
> `ПЛАН.md` М5.4: *«`/tickets` (создание заявки — тип UNSCHEDULED/EMERGENCY? Для клиента: обычная
> заявка + описание)»*.

## 1. Назначение

Два сценария на одном экране:

1. **Сообщить о проблеме** — создать заявку: тип, помещение (если известно), описание.
   Это главное действие клиента в портале: альтернатива звонку менеджеру.
2. **Узнать, что с моими заявками** — список заявок объекта со статусами и переход в карточку
   заявки, где видно, кто работает и что уже сделано.

Клиент **не** управляет заявкой: он не меняет статус, не назначает исполнителя, не закрывает и не
отклоняет её. Единственное действие после создания — уточнить детали комментарием (п. 7.3).

## 2. Маршрут и доступ

| Параметр | Значение |
|---|---|
| URL | `/tickets`; карточка заявки — `/tickets/:id` (см. README: в М5.4 не заявлена, но без неё клиент не увидит статус своей заявки — предложение) |
| Форма создания | «шторка» (bottom sheet) поверх списка, **не** отдельный маршрут: на телефоне закрытие возвращает к списку без потери позиции скролла |
| Пункт меню | «Заявки» — второй пункт нижнего таб-бара |
| Guard | `AuthGuard` + `RoleGuard roles={['CLIENT']}` |
| Чтение | `GET /api/tickets` (без `@Roles`) — но **всегда** с `objectId` своего объекта |
| Создание | `POST /api/tickets` — `@Roles('ADMIN','SUPERVISOR','CLIENT')` (`tickets.controller.ts:25`) |
| Комментарий | `POST /api/tickets/:id/comments` (в контроллере без `@Roles` для создания? — проверяется в М5.4; если роли ограничат, кнопка скрывается) |
| Запрещено | `PATCH /api/tickets/:id/status` (`ADMIN/SUPERVISOR/OPERATOR`, строка 64), `POST /api/tickets/:id/assign` (`ADMIN/SUPERVISOR`, строка 81), `POST /api/tickets/emergency` (аварийная — удел оператора/админки, `EmergencyTicketModal`) |
| Чужая заявка | `403`/`404` → сообщение и возврат в список (п. 6) |

### 2.1. Типы заявок, доступные клиенту

| Тип | Метка (`TICKET_TYPE_LABELS`) | Клиент может создать | Обоснование |
|---|---|---|---|
| `planned` | Плановая | ✔ | клиент заказывает уборку/работу заранее |
| `unscheduled` | Внеплановая | ✔ (**основной** вариант) | «нужно сделать, но не по графику» — типовой запрос клиента |
| `emergency` | Аварийная (SOS) | ✘ | SOS создаётся на месте с координатами оператора (`EmergencyTicketPayload` требует `lat`/`lng`); у клиента в портале координат нет, а ложный SOS поднимает всех ближайших операторов |

Приоритет (`priority`) в форме клиента **не показываем**: приоритет — внутренняя договорённость
(в админке его ставит диспетчер). `POST /api/tickets` принимает `priority` как необязательное
поле, поэтому это решение не ломает API (открытый вопрос п. 10.3).

## 4. Состав блоков

### 4.1. Шапка страницы

| Элемент | Описание |
|---|---|
| Заголовок | «Заявки» — `h1`, `text-xl font-semibold text-neutral-900 sm:text-2xl` |
| Счётчик | `total` из ответа, `text-sm text-neutral-500` рядом с заголовком |
| Кнопка «Создать» | `Button variant="primary" size="md"` `min-h-[44px]`, открывает шторку п. 7.1; на `320–359 px` превращается в круглую `+` с `aria-label="Создать заявку"` |

### 4.2. Фильтр-чипы

Горизонтальная прокрутка (`overflow-x-auto` + `scrollbar-none`), чипы — `rounded-full border
border-neutral-200 bg-white px-3 py-1.5 text-sm text-neutral-700`, активный — `border-primary-500
bg-primary-50 text-primary-700`. Значение синхронизируется с query-строкой (`?status=open`),
чтобы «назад» браузера восстанавливал фильтр (приём `objects_list.md` п. 4.2).

| Чип | Query | Статусы (`TicketStatus`) |
|---|---|---|
| Все | — | все |
| Открытые | `status=open` | `new`, `assigned`, `in_progress`, `paused`, `overdue` |
| Выполненные | `status=done` | `completed`, `verified`, `closed` |
| Отклонённые | `status=rejected` | `rejected` |

`ListTicketsQuery` принимает **один** `status`, поэтому «Открытые» собираются либо
последовательными запросами, либо (предпочтительно) добавлением в API фильтра `status` списком
(открытый вопрос п. 10.4). До этого — 5 параллельных запросов и слияние на клиенте; в этом случае
пагинация «Показать ещё» работает по каждому статусу отдельно (см. п. 8).

### 4.3. Карточка заявки (мобильная замена таблицы)

Табличный вид админки (`TicketsPage.tsx`) на телефоне не используется. Карточка:
`rounded-xl border border-neutral-200 bg-white p-4 shadow-sm`, `flex flex-col gap-2`.

| Строка | API | Формат |
|---|---|---|
| Номер + статус + дата | `id`, `status`, `createdAt` | `flex items-center justify-between`: номер `font-mono text-xs text-neutral-400` (первые 8 символов UUID — человекочитаемого номера в схеме нет, п. 10.2), `Badge` статуса, дата `font-mono text-xs text-neutral-500` (`dd.MM HH:mm`) |
| Описание | `description` | `text-sm text-neutral-900`, `line-clamp-2` + `title` с полным текстом |
| Мета | `type`, `_count.comments`, `operationsTotal` / `operationsCompleted` | `text-xs text-neutral-500`: «Внеплановая · 3 комментария · 2 из 4 операций»; части, которых нет в ответе, опускаются |
| Просрочка | `overdueAt != null` | дополнительная строка `text-xs text-danger-600` «Просрочена с 20.09» |
| Назначен | `assigneeId` | на телефоне **не выводим**: это UUID сотрудника, а справочник `/api/users` — `ADMIN/SUPERVISOR` (`usePermissions.ts`). Вместо ФИО — «Исполнитель назначен» (`text-xs text-neutral-400`) |

Клик по карточке (кроме ссылок) → `/tickets/:id`.
Строки-разделители между карточками — `gap-3` (карточки, а не таблица: `border-b` не используем).

### 4.4. Пагинация

Кнопка «Показать ещё» (`Button variant="secondary"`, `w-full min-h-[44px]`), а не номера страниц:
на телефоне инкрементальная догрузка удобнее. `take=20`, `skip = items.length`; когда
`items.length >= total`, кнопка исчезает и показывается подпись «Показано все 12 заявок»
(`text-xs text-neutral-400 text-center`). Максимум `take` — 100 (соглашение сервисов).

### 7.1. Шторка «Новая заявка» (создание)

Ниже `640 px` — bottom sheet (см. [`overview.md`](./overview.md) п. 7.4), выше — обычная `Modal`
(`components/ui/Modal.tsx`, API сохраняется: `open`, `title`, `onClose`, `footer`, `busy`).

| Поле | Контрол | Обяз. | Валидация | Поле API |
|---|---|---|---|---|
| Что случилось | `Textarea` `min-h-[96px]`, `text-base` (≥16 px — iOS не зумит), `placeholder` «Опишите проблему: где, что, когда заметили» | ✔ | 10–2000 символов, счётчик `{n}/2000` `text-xs text-neutral-400` справа | `description` |
| Где (этаж) | `Select` — этажи объекта (`GET /api/objects/:id/detail` → `floors[].number/.name`), первый пункт «Не знаю / не важно» | ✖ | — | используется только для выбора помещения |
| Где (помещение) | `Select` — помещения выбранного этажа (`floors[].rooms[].name`), появляется после выбора этажа | ✖ | — | `roomId` |
| Вид заявки | радио-группа: «Внеплановая» (по умолчанию) / «Плановая» | ✔ | `unscheduled` \| `planned` | `type` |
| Объект | — (скрытое поле) | ✔ | всегда `objectId` клиента из сессии; **пользователь не может его изменить** | `objectId` |
| Координаты | — | ✖ | не отправляем: у клиента нет геопозиции в этом сценарии | `lat`, `lng` |

Кнопки: «Отмена» (`secondary`) / «Отправить заявку» (`primary`, `loading` во время запроса,
заблокирована до ответа — защита от двойного создания). Шторка **не** закрывается по клику на
оверлей, если описание непустое — иначе на телефоне случайный тап стирает набранный текст
(подтверждение «Отменить заявку?» через `ConfirmDialog`, как в админке).

Тексты: заголовок «Новая заявка», подпись под описанием «Чем точнее опишете, тем быстрее
приедет исполнитель». При успехе — закрытие и перезапрос списка (см. таблицу состояний).

### 7.2. Карточка заявки `/tickets/:id`

Отдельный экран (не шторка): клиент открывает её по ссылке из чата или уведомления.

| Блок | Содержимое |
|---|---|
| Шапка | Крошка «← Заявки» (`Breadcrumbs`), заголовок «Заявка {короткий id}», `Badge` статуса и приоритета, дата создания `font-mono text-xs` |
| Описание | `Card` с полным `description` (`text-sm text-neutral-900`, пробелы и переносы сохранены: `whitespace-pre-wrap`) |
| Ход работы | `Card` «Ход работы»: список `operationsCompleted`/`operationsTotal` и тайминги жизненного цикла (`assignedAt`, `arrivedAt`, `completedAt`, `closedAt`) в виде вертикального таймлайна: точка `h-2 w-2 rounded-full bg-success-500` + подпись `text-sm` + время `font-mono text-xs text-neutral-500`. Шаги без времени не показываются |
| Комментарии | `Card` «Переписка»: список `comments` (`authorId` → «Вы»/«Менеджер» без ФИО: справочник сотрудников клиенту недоступен), время `font-mono text-xs`; новые снизу |
| Поле комментария | `Textarea` + `Button variant="primary"` «Отправить» (`sticky bottom-0` над таб-баром) |
| Действия, которых **нет** | смена статуса, назначение исполнителя, закрытие, отмена — у клиента их не существует (`@Roles` на бэкенде) |

Таймлайн-статусы: `new` → `assigned` → `in_progress` → `completed` → `verified` → `closed`;
боковые ветки `paused`, `rejected`, `overdue` показываются отдельной строкой с тоном
`warning`/`danger`. Подписи — `TICKET_STATUS_LABELS` (`types/tickets.ts`), не строки в коде.

## 8. Данные из API

### 8.1. Список

`GET /api/tickets?objectId=<свой>&skip=&take=20[&status=…]` → `{ items: TicketListItem[], total }`.

| Поле | Использование |
|---|---|
| `id` | ключ карточки, короткий номер, ссылка `/tickets/:id` |
| `type`, `priority`, `status` | метка типа, бейдж статуса (приоритет в карточке не выводим) |
| `description` | текст описания (обрезается до 2 строк) |
| `createdAt`, `updatedAt` | дата карточки |
| `overdueAt` | предупреждение о просрочке |
| `assigneeId` | только факт «исполнитель назначен» (UUID не показываем) |
| `operationsTotal`, `operationsCompleted` (если сервис отдаёт счётчики) | «2 из 4 операций» |
| `_count.comments`, `_count.operations` | «3 комментария» / «4 операции» |
| `total` | счётчик в шапке и условие «Показано все N» |

### 8.2. Мутации

| Действие | Запрос | Тело |
|---|---|---|
| Создание заявки | `POST /api/tickets` | `{ type, objectId, roomId?, description }` (`CreateTicketPayload`, `priority` не отправляем) |
| Комментарий | `POST /api/tickets/:id/comments` | `{ text }` |

Обновление — инвалидация ключей `['tickets', objectId, filters]` и `['ticket', id]` (TanStack
Query), без перезагрузки страницы.

| `360–639 px` (**основной**) | как на схеме: карточки `p-4`, форма — bottom sheet во всю ширину, поле описания `text-base` |
| `640–1023 px` | карточки в 2 колонки (`sm:grid-cols-2`), форма — центрированная `Modal` `max-w-lg`, чипы без прокрутки |
| `≥1024 px` | контент `max-w-screen-md mx-auto`; при желании — таблица как в админке (`Table.tsx`), но **не обязательна**: DS-004 требует упрощённый интерфейс, дублировать админку не нужно |

Особенности телефона: шторка поднимается над клавиатурой (`max-h-[85vh] overflow-y-auto`,
`bottom-0`), футер с кнопкой — `sticky bottom-0 bg-white border-t border-neutral-200`;
таб-бар скрывается, пока шторка открыта; при закрытии шторки скролл списка сохраняется
(`body` не скроллится, скроллится только шторка).

## 10. Ограничения и открытые вопросы

1. **Только свой объект.** Все запросы — с `objectId` из сессии; чужая заявка по прямому URL →
   одно сообщение «Заявка не найдена или недоступна» (403 и 404 не различаем для клиента).
   Напоминание: серверного scope у `GET /api/tickets` сейчас нет (см. [`overview.md`](./overview.md) п. 2.1).
2. **Аварийная заявка (SOS) клиенту недоступна** (п. 2.1) — требуется подтверждение решения:
   если владелец ждёт от клиента возможность SOS, нужен отдельный сценарий с координатами
   (геолокация браузера) и изменением `EmergencyTicketPayload` (сейчас `lat`/`lng` обязательны).
3. **Приоритет и сроки** клиент не задаёт: `priority` не отправляем, `reactionDeadline` и т.п.
   назначает бэкенд. Если бизнес хочет «срочно» от клиента — нужен отдельный флаг и решение
   по SLA (иначе все заявки станут «срочными»).
4. **Фильтр «Открытые»** требует `status` списком или N запросов (п. 4.2) — уточнить контракт в
   ticket-service (`ListTicketsQueryDto`).
5. **Двойная отправка формы**: `POST /api/tickets` не идемпотентен (нет ключа идемпотентности),
   поэтому кнопка блокируется до ответа, а таймаут axios (10 c) сопровождается подсказкой
   «Проверьте список заявок перед повторной отправкой».
6. **Вложения (фото проблемы)** в М5.4 не заявлены, хотя file-service умеет `kind=photo`.
   Предложение на потом: одна фотография в форме заявки (`multipart` в file-service → `photoUrl`
   в описании), но это изменение контракта ticket-service, а не экрана.
7. **Кто видит заявку из сотрудников** — вне портала; клиенту в карточке не показываем ФИО
   исполнителя, потому что справочник `/api/users` закрыт для роли CLIENT.

## 11. Критерии приёмки (чек-лист)

- [ ] `/tickets` доступен только под ролью `CLIENT`; список содержит **только** заявки своего объекта (`objectId` из сессии во всех запросах).
- [ ] Прямой заход на `/tickets/:id` чужой заявки не показывает данные и не различает 403/404 (сообщение «не найдена или недоступна»).
- [ ] Создание заявки: `POST /api/tickets` уходит с `type` ∈ {`planned`, `unscheduled`}, `objectId` клиента и непустым описанием; аварийный тип в форме отсутствует.
- [ ] Валидация описания (10–2000 символов) с сообщением под полем; ошибка сервера показывается текстом DTO.
- [ ] Кнопок смены статуса, назначения исполнителя, закрытия/отклонения на экране нет ни в каком виде.
- [ ] После создания новая заявка появляется в списке первой и имеет статус «Новая»; `total` увеличился на 1.
- [ ] Состояния: скелетон, пусто (нет заявок / фильтр пуст), ошибка сети с «Повторить», 403 без «Повторить», догрузка «Показать ещё».
- [ ] Фильтр-чипы синхронизированы с URL; «назад» браузера возвращает прежний фильтр.
- [ ] Форма на 360 px открывается как шторка, футер с кнопкой виден над клавиатурой, случайный тап по оверлею не стирает текст без подтверждения.
- [ ] Горизонтального скролла нет; область нажатия кнопок ≥44 px; поле описания `text-base` (≥16 px).
- [ ] Используются только токены `tokens.css` и компоненты UI-кита из [`overview.md`](./overview.md) п. 4; новых hex нет.
