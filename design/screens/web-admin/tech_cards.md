# 🧾 Экран: Техкарты и операции (`tech_cards`)

> DS-003 (М2.8) → реализация в М2.7 (`frontend/web-admin/src/pages/TechCards/`).
> Тип артефакта — текстовая спецификация (см. [`README.md`](./README.md)).
> Данные: `tech-cards` CRUD и операции (М2.6), помещения с привязкой `Room.techCardId` (М2.4/М2.6),
> материалы операций `TechOperationMaterial` (справочник материалов — М4).

## 1. Назначение

Библиотека технологических карт: что именно и в каком порядке делает уборщик в помещении, сколько
это занимает времени, требуется ли фото- и QR-подтверждение, какие материалы расходуются.
Техкарта привязывается к помещениям (экран [`floor_plan.md`](./floor_plan.md)) и определяет состав
операций для мобильного чек-листа (М6) и веб-карточки заявки (М3.7).

Требование М2.7: «TechCards (редактор операций)». Требование DS-003: desktop-first, таблицы,
drag-and-drop интерфейсы, модальные окна.

### 7.2. Модальное окно «Операция» (создание)

Поля — как в аккордеоне 4.5 (без таблицы материалов; материалы добавляются после создания операции).
Обяз.: `name`, `estimatedTimeMin` (целое ≥ 1). `orderIndex` при создании = `operations.length`.
Кнопки: «Отмена» / «Добавить».

### 7.3. Сохранение порядка операций

`POST /api/tech-cards/:id/reorder` в М2.6 **не заявлен** (в отличие от `POST /api/routes/:id/reorder`
в М2.5). Поэтому спецификация фиксирует два варианта:

| Вариант | Механика | Риск |
|---|---|---|
| A (рекомендуется) | Добавить симметричный endpoint `POST /api/tech-cards/:id/reorder { operationIds: [...] }` (транзакция, обновление `orderIndex`), как для маршрутов | Требует решения Backend Core и расширения М2.6 |
| B (обходной) | Последовательные `PATCH .../operations/:id { orderIndex }` в порядке топологической сортировки (временно использовать свободные индексы) | `@@unique([techCardId, orderIndex])` делает последовательность хрупкой: часть запросов может упасть 409, порядок станет несогласованным |

До реализации варианта A **drag-and-drop операций считается P1**: в UI показываются кнопки
«↑/↓» (перемещение на одну позицию), а drag-and-drop включается после появления endpoint'а.
Это единственное место в DS-003, где требование «drag-and-drop интерфейсы» не обеспечено API.

## 8. Данные из API

### 8.1. Техкарта

`GET /api/tech-cards?skip=&take=&search=` → `{ items: TechCard[], total }`; `GET /api/tech-cards/:id` → `TechCard` + `operations` + `rooms`.

| Поле | Тип | Использование |
|---|---|---|
| `id` | uuid | выбор карточки, маршрут `/tech-cards/:id` |
| `name` | string | список, заголовок редактора |
| `operations[]` | `TechOperation[]` | список операций (сортировка по `orderIndex`) |
| `rooms[]` | `Room[]` | блок «Где используется», метрика «{m} помещений» |
| `createdAt`, `updatedAt` | ISO 8601 | сортировка «по дате изменения», метаданные (`text-xs text-neutral-400`) |

### 8.2. Операция

| Поле | Тип | Использование |
|---|---|---|
| `id` | uuid | ключ строки, `operationIds` при reorder |
| `techCardId` | uuid | принадлежность карточке |
| `name` | string | название в списке |
| `orderIndex` | number | номер `orderIndex + 1`; `@@unique([techCardId, orderIndex])` |
| `description` | string \| null | краткое описание (1 строка), поле в аккордеоне |
| `equipment` | Json \| null | бейдж «Оборудование», редактор JSON |
| `estimatedTimeMin` | number | колонка «Время», Σ в футере |
| `requiresPhoto` | boolean | иконка 📷 |
| `requiresQr` | boolean | иконка ▣ |
| `materials[]` | `TechOperationMaterial[]` | счётчик и таблица 4.6 |
| `createdAt`, `updatedAt` | ISO 8601 | метаданные (P2) |

### 8.4. Запросы

| Действие | Запрос |
|---|---|
| Список техкарт | `GET /api/tech-cards?skip=0&take=50&search=` |
| Карточка | `GET /api/tech-cards/:id` (include `operations`, `rooms`) |
| Создание / переименование / удаление | `POST /api/tech-cards`, `PATCH /api/tech-cards/:id`, `DELETE /api/tech-cards/:id` |

Swagger core-service после реализации М2.6 и при необходимости скорректировать эту спецификацию.

## 9. Адаптивность (desktop-first)

Диапазоны — из System Design v1 (§2.2): <768 px (phone, `max-md:`), 768–1023 px (tablet,
`md:max-lg:`), ≥1024 px (desktop, `lg:`). Desktop ≥1024 px визуально не меняется.

| Диапазон | Поведение |
|---|---|
| ≥1024 px (desktop) | как сейчас: список `w-80` + редактор `flex-1`, таблица операций, сайдбар `w-60` |
| 768–1023 px (tablet) | одна колонка; список техкарт остаётся списком (карточки — только на телефоне), редактор открывается поверх; строка операции — карточка (имя, время, иконки, действия); reorder операций — кнопками «↑/↓»; сайдбар — иконочная рейка `w-16` (64 px) |
| <768 px (phone) | список техкарт → карточки через `ResponsiveTable`; редактор открывается полноэкранно; строка операции → карточка (имя, время, иконки, действия); reorder операций кнопками «↑/↓» (drag — после появления `POST /api/tech-cards/:id/reorder`, см. п. 7.3); навигация — бургер/drawer + нижняя навигация (5 слотов: Заявки, Доска действий, Объекты, Сообщения + «Ещё»); модалки fullscreen |

## 10. Открытые вопросы

1. **Endpoint переупорядочивания операций отсутствует в М2.6** — центральный пробел этого экрана
   (см. 7.3). Требуется решение Backend Core: добавить `POST /api/tech-cards/:id/reorder`
   (симметрично маршрутам) или согласиться на вариант B.
2. **Маршрут `/tech-cards` и пункт меню «Техкарты»** отсутствуют в `router/index.tsx` и
   `AdminLayout.NAV` — добавить в М2.7 (см. п. 2).
3. **Структура `equipment` (Json) не определена** — в схеме это `Json?` без описания. В
   спецификации: textarea с JSON + проверка парсинга (P0), key-value редактор (P2, после
   согласования формы: списком строк, объектом с ключами или ссылками на инвентарь).
4. **Роли.** Доступ к техкартам не задан в `ПЛАН.md`/роутере; предложение — ADMIN/SUPERVISOR,
   чтение OPERATOR (для мобильного чек-листа техкарта нужна оператору в М6).
5. **Конкретные URL операций и материалов** не зафиксированы в `API_SPECIFICATION.md` — уточнить
   по Swagger после М2.6.
6. **Фильтр «где используется»** (`GET /api/rooms?techCardId=`) в спецификации API не заявлен;
   альтернатива — поле `rooms` в ответе техкарты (схема `TechCard.rooms` существует).
7. **Дублирование техкарт** реализуется клиентом (последовательные POST) — серверного
   `duplicate`-endpoint нет; при большом числе операций возможна частичная копия (нужен либо
   транзакционный endpoint, либо отказ от функции в М2).
8. **Мягкая заливка бейджей/плашек** ограничена доступными токенами (`*-50` есть только у `primary`
   и `neutral`) — см. README, пробел 1.
