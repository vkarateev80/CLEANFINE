# Доступы к демонстрационному стенду `prj-cleanfine`

Точка входа по доступам: здесь только то, что нужно, чтобы **войти** — адреса, учётные
записи, готовый пример запроса и ловушки среды. Процедуры (развёртывание, миграции,
приёмка AC-1…AC-8, откат) — в `deploy/vps/README.md`; этот документ их не повторяет
и не заменяет.

**Статус данных.** Учётные записи ниже проверены входом **22.09.2026** на стенде из
актуального кода ветки `develop`; все пять входов отвечают `201`.

---

## 1. Назначение и границы

Это доступы к **демонстрационному стенду для разработки и приёмки**, а не к продакшену:
пароли здесь демонстрационного уровня, прод-контура у стенда нет.

Стенд опубликован **только в tailnet** — на адресе `100.109.185.14`; из публичного
интернета он **недоступен**. Чтобы адреса из §3 открывались, машина клиента должна быть
в том же tailnet: без этого `curl` и браузер получат таймаут, и это не поломка стенда,
а ожидаемое поведение изоляции (NFR-2).

## 2. Учётные записи

|---|---|---|---|---|
| ADMIN | админка `:8090` | `admin@cleaning-ops.com` | `admin123` | полный доступ, 11 пунктов меню; она же служебная для проверки привязок объектов |
| SUPERVISOR | админка `:8090` | `supervisor@cleaning-ops.com` | `super123` | те же 11 пунктов, что у ADMIN, включая «Сотрудники» |
| OPERATOR | админка `:8090` | `operator@cleaning-ops.com` | `oper123` | 8 пунктов — без «Маршрутов», «Техкарт» и «Сотрудников» |
| CLIENT (владелец объекта) | портал `:8091` | `owner@cleanfine.ru` | `owner123` | привязан к объекту «БЦ «Ромашка»» — видит его |
| CLIENT (без привязки) | портал `:8091` | `client@example.com` | `client123` | не привязан ни к чему — видит пустой список |

Учётные записи ADMIN/SUPERVISOR/OPERATOR/CLIENT(`client@example.com`) создаёт
`scripts/seed/seed-users.mjs` из фикстур `test/fixtures/users.json`; владельца
`owner@cleanfine.ru` и объект «БЦ «Ромашка»» — `scripts/seed/seed-demo-object.mjs`.
Повторный seed пересоздаёт пароли и приводит стенд к этому состоянию, поэтому пароли
в таблице — не «текущие на удачу», а воспроизводимые.

**Про последние две строки: это не дубль, а проверочная пара.** Обе учётки — роль CLIENT
на одном и том же портале `:8091`, и различаются они ровно одним: у `owner@cleanfine.ru`
есть **явная привязка** объекта к аккаунту (`Object.ownerClientId = id владельца`),
у `client@example.com` привязки нет. Портал определяет «свой объект» только по
`ownerClientId === id сессии`, поэтому владелец видит «БЦ «Ромашка»», а непривязанный
клиент — пустой список. Расхождение между этими двумя учётками (обе видят объект или
обе не видят) и есть признак поломки привязки, а не «особенности прав»: проверяйте пару
целиком, а не по одной.

> **Проверено живым входом 23.09.2026** (стенд, ширина 1366 px): ADMIN — **11** пунктов,
> SUPERVISOR — **те же 11** (пункт «Сотрудники» объявлен с `roles: ['ADMIN','SUPERVISOR']`),
> OPERATOR — **8** (нет «Маршруты», «Техкарты», «Сотрудники»). Источник истины — код
> `frontend/web-admin/src/layouts/AdminLayout.tsx` (`NAV`/`navForRole`); состав меню выше
> приведён по этому замеру. Ранее в PRD проекта адаптива (`prd` v1, §3) было указано, что
> SUPERVISOR не видит «Сотрудников» — **это утверждение неверно**, здесь исправлено;
> сама неточность PRD оставлена в силе как исторический документ.

Дополнительно существуют PIN мобильного входа (нужны только мобильному приложению,

catch-all `auth:3001` и получают 404) — для этих двух сервисов используйте `:8112`/`:8114`.

## 4. Готовый пример входа

```bash
# 1) Токен администратора. Логин отвечает 201, а не 200 — это норма.
TOKEN=$(curl -s -X POST http://100.109.185.14:8090/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@cleaning-ops.com","password":"admin123"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["accessToken"])')

# 2) Кто мы (role=ADMIN) и список объектов стенда
curl -s -H "Authorization: Bearer $TOKEN" http://100.109.185.14:8090/api/auth/me
curl -s -H "Authorization: Bearer $TOKEN" 'http://100.109.185.14:8090/api/objects?take=100'
```

```bash
# 3) Проверка привязки владельца через портал (:8091) — ожидается ровно 1 объект
OWNER=$(curl -s -X POST http://100.109.185.14:8091/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"owner@cleanfine.ru","password":"owner123"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["accessToken"])')
OWNER_ID=$(curl -s -H "Authorization: Bearer $OWNER" http://100.109.185.14:8091/api/auth/me \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')
curl -s -H "Authorization: Bearer $OWNER" \
  "http://100.109.185.14:8091/api/objects?ownerClientId=$OWNER_ID&take=100"
# → { "items": [ { "name": "БЦ «Ромашка»", ... } ], "total": 1 }
```

Пустой список у владельца или `total: 0` — признак сломанной привязки `ownerClientId`,
а не ошибки входа (диагностика — `deploy/vps/README.md` §5.1–§5.2).

**Граница доступа — читать буквально.** Серверного scope у объектов нет: `GET /api/objects`
отдаёт объекты **любому аутентифицированному** пользователю, `?ownerClientId=` — фильтр
списка, а не авторизация. То есть токеном клиента можно запросить чужой объект по id.

## 5. Секретов MinIO и базы в этом файле нет — и не будет

**Решение:** пароли MinIO и БД в эту спеку **не копируются**. Это не забывчивость, а
следствие того, как стенд создаётся: `deploy/vps/gen-env.sh` генерирует секреты
(`openssl rand -hex`) **заново для каждого стенда** и пишет их в `deploy/vps/.env.vps`,
который намеренно **не в git**. Любое значение, вписанное сюда, устареет в тот же день,
когда стенд пересоздадут, — а документ в git продолжит его показывать как действующее.
Это ровно тот случай, когда «удобно скопировать» превращается в источник ложных данных.

**Где искать.** Имя пользователя MinIO — `admin` (`MINIO_ROOT_USER` и `MINIO_ACCESS_KEY`
равны ему); значение пароля — в `deploy/vps/.env.vps` на хосте стенда. Переменные, которые
там лежат (чтобы не гадать, что искать):

| Переменная | Что это |
|---|---|
| `MINIO_ROOT_PASSWORD` | пароль пользователя `admin` для консоли MinIO (`:8121`) |
| `MINIO_SECRET_KEY` | тот же пароль в роли S3-секрета; `gen-env.sh` держит его равным `MINIO_ROOT_PASSWORD` |
| `DB_PASSWORD` | пароль Postgres для пользователя `admin` (он же подставлен внутрь всех `*_DATABASE_URL`) |
| `RABBITMQ_PASSWORD` | пароль RabbitMQ для пользователя `admin` (он же внутри `RABBITMQ_URL`) |

Посмотреть, не печатая лишнего:

```bash
# на хосте стенда, из корня репозитория
grep -E '^(MINIO_ROOT_PASSWORD|MINIO_SECRET_KEY|DB_PASSWORD|RABBITMQ_PASSWORD)=' deploy/vps/.env.vps
```

Заодно: `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` тоже генерируются в `.env.vps` и тоже
здесь не приводятся. Единственный «секрет», который не генерируется, —
`SERVICE_AUTH_PASSWORD`: он равен паролю seed-администратора (`admin123`), решение O4;
на этом пароле держится проверка аккаунта заказчика при записи `ownerClientId`.

## 6. Ограничения, о которые спотыкаются

- **Частота входов — 5 попыток в минуту на логин.** Дефолт auth-service
  (`DEFAULT_LOGIN_THROTTLE_LIMIT = 5`, окно `60 000` мс; глобальный пресет — 100/мин).
  При массовых прогонах (e2e, скрипты, повторные `curl` в цикле) приходит `429 Too Many
  Requests` — это **работающий лимит, а не поломка стенда**: подождите минуту или
  переиспользуйте уже полученный токен вместо нового входа. Поднимать лимиты —
  осознанное решение по стенду (`THROTTLE_LOGIN_LIMIT`/`THROTTLE_GLOBAL_LIMIT`), см.
  `deploy/vps/README.md` §10 и `docs/FACTS.md` §8.
- **На той же машине живёт другой стенд — `cleaning-ops-vps`** (`0.0.0.0:{80,8080,3001–3009}`,
  это демонстрационный стенд с другими данными, в нём 0 объектов). Учётки из §2 относятся
  **только** к `prj-cleanfine`. При работе со стендом `cleaning-ops-vps` не трогать:
  свои сеть, тома, имена контейнеров и порты — пересечений нет, но и команд против него
  подавать не нужно (`docker compose` адресует только свой проект).
- **`vite dev` по умолчанию проксирует `/api` в ЧУЖОЙ стенд.** `frontend/web-admin/vite.config.ts`
  отправляет `/api/*` на `localhost:3001–3009`, а там слушает демонстрационный
  `cleaning-ops-vps` (сервисы `prj-cleanfine` на `localhost` не отвечают: они опубликованы
  только в tailnet). Признак: локальная проверка молча показывает данные чужого стенда.
  Лечится переменными окружения (дефолты прежние, CI не затронут):
  `VITE_SERVICE_HOST=100.109.185.14 VITE_SERVICE_PORT_OFFSET=5110 pnpm dev`
  (смещение переводит штатные порты в порты стенда: 3001 → 8111 … 3009 → 8119).
  Контроль правильности: через прокси `GET /api/objects` должен вернуть 1 объект, а не 0.
  Подробности — `docs/FACTS.md` §5.

## 7. Что переделать перед любым публичным доступом

Стенд честно демонстрационный: пароли из §2 лежат в git (фикстуры и seed-скрипты) и
заведомо слабые. Перед публикацией за пределы tailnet как минимум:

1. **Сменить пароли всех seed-учёток** (`admin@cleaning-ops.com`, `supervisor@…`,
   `operator@…`, `client@example.com`, `owner@cleanfine.ru`) — и не оставлять их в
   фикстурах/seed как «документированные».
2. **Сгенерировать секреты заново** (`bash deploy/vps/gen-env.sh --force`) и убедиться,
   что `.env.vps` не попал в git. При смене пароля seed-администратора **синхронно
   обновить `SERVICE_AUTH_PASSWORD`**: иначе привязка объектов начнёт отказывать
   fail-closed с `503`.
3. **Ввести серверный scope на объекты**: сейчас `GET /api/objects` и
   `GET /api/objects/:id` доступны любому аутентифицированному пользователю, а
   `?ownerClientId=` — фильтр списка, а не авторизация. Портал — UI-механика поверх API
   и **не является границей доступа**.
4. **Снять публикацию с tailnet-адреса и заменить её внешним входом** (домен, TLS,
   gateway) — иначе «публичный доступ» означает либо ничего, либо HTTP в tailnet.
5. **Заменить служебную учётку seed-админа отдельной сервисной ролью** — она тянет за
   собой права ADMIN в межсервисных вызовах и в проверке аккаунта заказчика.
6. **Дозаполнить прод-контур**, которого у стенда нет: бэкапы с проверенным
   восстановлением, мониторинг, отдельные лимиты частоты, ротация секретов.
