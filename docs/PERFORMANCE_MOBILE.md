# Мобильное приложение: производительность кадров и GPS (М7.4)

Документ закрывает два пункта, перенесённых в М7.4 из М6.8:

1. **60 FPS** — профилирование карты маршрута и чек-листа (в М6.8 не выполнялось:
   «инструментальная работа на устройстве»);
2. **расход батареи GPS** — измерение того, что измеримо, и явное описание того,
   что измерить нечем (ограничение зафиксировано ещё в М6.6).

Образец оформления — `docs/PERFORMANCE_REPORT.md` (М7.2): методика → сырые числа →
вывод → ограничения стенда, отдельно от дефектов продукта.

---

## 1. Стенд измерений

| Что | Значение |
|---|---|
| Устройство | **эмулятор Android** (AVD `co-test`), `abi.type = arm64-v8a`, Android 36 (`google_apis`) |
| Экран AVD «как есть» | 320×640, плотность 160 dpi (**DPR 1.0**, логически 320×640) |
| Экран «как телефон» | `wm size 1080x2340` → фактически 1080×1920, `wm density 440` (**DPR 2.75**, логически 393×698) |
| Рендеринг: профиль «программный» | `-gpu swiftshader_indirect`, в `config.ini` AVD `hw.gpu.enabled = no` |
| Рендеринг: профиль «GPU хоста» | эмулятор запущен с `-gpu auto`; `dumpsys SurfaceFlinger` → `Android Emulator OpenGL ES Translator (Apple M5), OpenGL ES 3.0 (4.1 Metal)` |
| Сборка | `flutter build apk --debug` (profile/release-режим на эмуляторе не даёт номеров без DevTools; см. §5 «Ограничения») |
| Стенд приложения | nginx `http://127.0.0.1:8080/api`, из эмулятора — `10.0.2.2` |

**Три конфигурации измерений** (разные вопросы — разные числа):

- **A. Программная растеризация, 320×640** — состояние AVD «как выдан»; консервативная
  оценка: GPU нет вовсе, всё растеризует CPU.
- **B. GPU хоста, 320×640** — та же площадь экрана, но растеризация на GPU.
- **C. GPU хоста, 1080×1920 (DPR 2.75)** — ближе всего к настоящему телефону по
  площади и плотности; **два прогона подряд** (воспроизводимость).

## 2. Методика

Предпочтительный вариант из задания вехи: `integration_test` на эмуляторе.

- Файл: `mobile/cleaning-ops-app/integration_test/fps_measure_test.dart`.
- Сбор времён кадров: `SchedulerBinding.instance.addTimingsCallback` → `FrameTiming`
  **реального движка** (не fake-async тестового биндинга). Собираются
  `buildDuration` и `rasterDuration` — те же величины, что показывает DevTools timeline.
- Бюджет кадра — **16 мс на `build + raster`**: при 60 Гц это и есть 60 FPS.
  `buildDuration` и `rasterDuration` выполняются на разных потоках, поэтому их сумма —
  мера «сколько работы в бюджете кадра», а не задержка одного кадра; так и требует
  формулировка М6.8 («build + raster duration»).
- Приложение **настоящее** (`CleaningOpsApp` целиком), вход оператором, переходы —
  реальными нажатиями. Интерактив — настоящие жесты: панорама и «щипок» по плану
  этажа (`TestGesture`), прокрутка списка операций.
- Окна измерения разделены: **загрузка** (первый показ экрана: сеть + первая
  отрисовка) и **интерактив** (работа пользователя). Смешивать их нельзя — один
  сетевой кадр «съедает» весь бюджет маленькой выборки.
- Эмулятор перед измерениями прогревается: геозона на стенде создана, смена оператора
  отмечена приходом (иначе главная не покажет кнопку маршрута).

Сырые числа печатаются строками `FPS …` и `FPS_JSON […]`.

таком профиле не выполняется и выполнен быть не может — это свойство профиля, а
не приложения (см. §5).

## 4. Вывод

**Интерактив (то, ради чего мерили) — в бюджете.** На обеих проверяемых площадках —
карте маршрута с планом этажа и чек-листе с операциями — при прокрутке, панораме и
масштабировании 94–100 % кадров укладываются в 16 мс; медиана кадра 1,2–2,0 мс,
то есть **пяти-восьмикратный запас**. Это и есть ответ на вопрос М6.8: 60 FPS на
маршрутной карте и чек-листе обеспечивается, узкого места в вёрстке нет.

**Порог 95 % выполняется не всегда — и это не скрывается.** При включении в выборку
окон ПЕРВОГО ПОКАЗА экранов доля падает до 93,9–96,6 % (в зависимости от прогона).
Причина не в интерактиве: в окнах загрузки `build` достигает 40–104 мс на 5–7 кадрах
(первая сборка дерева, компиляция шейдеров, декодирование плана), и на выборке из
8–21 кадра эти кадры дают сразу 10–60 %. Это **рывок при открытии экрана, а не
просадка под нагрузкой**; в абсолютных числах — 5–7 кадров из ~590 за прогон.

**Что не подтвердилось как проблема.** Тяжёлая вёрстка, лишние перерисовки и
синхронный ввод-вывод на кадре: `build` в интерактиве 1,2–3,4 мс в среднем и 2,7–9,1 мс
по p95 при бюджете 16 мс. Синхронного диска/сети на кадре не видно: точки плана
берутся из кэша, план — из файлового кэша (`Image.file`), сеть работает фоном
(`unawaited(_warmFloorPlan)`). Оптимизировать нечего, поэтому правок «под цифры» не
делалось: подгонять результат запрещено условием вехи.

## 5. Ограничения измерений (обязательно к учёту)

1. **Это эмулятор, а не реальное устройство.** Частоты и планировщик эмулятора не
   совпадают с телефоном; `worst`-кадры (36–94 мс) почти целиком относятся к
   выбросам планировщика/GC на хосте, а не к приложению.
2. **Профиль сборки — `debug`.** На эмуляторе `--profile`/`--release` не дают номеров
   без подключённого DevTools, поэтому измерялось в debug: это **пессимистичная**
   оценка для `build` (AOT в release быстрее), но `raster` от режима сборки почти не
   зависит.
3. **Профиль рендеринга меняет вывод радикально** (A против B: 58 % против 100 % на
   одной и той же сборке). Профиль A — это CPU-растеризация SwiftShader; числа из
   него **нельзя** переносить на телефон с GPU. Именно поэтому приведены оба профиля.
4. **Площадь экрана AVD «как выдан» вдвое меньше телефона** (320×640 против
   1080×1920). Осознанно измерены обе: конфигурация C ближе к реальности, но и она
   не телефон (другой GPU-стек, другая плотность, DPCM отсутствует).
5. **Мобильная сборка на стенде — `--dart-define=API_HOST` не задавался**, адрес по
   умолчанию `10.0.2.2`; на реальном устройстве адрес другой, на кадры это не влияет.
6. Приложение работает **без фонового сервиса Android** (ограничение М6.6), поэтому
   измерения сняты с приложением на переднем плане; расход в фоне не измерялся.

## 6. GPS: что измерено и что измерить нечем

### 6.1 Чего измерить нельзя (и почему)

**Процент расхода батареи GPS измерить нечем.** В стеке устава нет плагина уровня
заряда (`battery_plus` и подобных), плагин батареи не добавлялся и в М7.4: условие
вехи — «новых зависимостей не добавлять сверх необходимого для измерений», а одна
лишь цифра заряда без профилировщика энергии всё равно не даёт расхода в мА·ч.
Дополнительно: `GpsTrackingService` пишет точку без поля `battery` вовсе
(`GpsPointsCompanion.insert` в `lib/services/gps_tracking_service.dart` не содержит
`battery`) — то есть в БД это поле всегда `null`, что и подтверждено выгрузкой точек.

**Фонового сервиса Android нет** (зафиксировано в М6.6): трекинг живёт в интервале
таймера приложения, и при уходе приложения в фон периодичность не гарантируется.
Расход «в фоне» поэтому не измерялся — измерять было бы нечего.

**Что нужно для полноценного замера расхода батареи:**

1. плагин уровня заряда (`battery_plus`) — чтобы писать `battery` в точку и видеть
   кривую разряда;
2. **реальное устройство** (эмулятор не имеет батареи в смысле расхода) и выключенный
   заряд, сценарий «смена 8 часов с трекингом»;
3. для расхода в фоне — foreground service (`FOREGROUND_SERVICE` +
   `ACCESS_BACKGROUND_LOCATION`), которого сейчас нет по решению М6.6;
4. профилировщик энергии (`adb shell dumpsys batterystats`, Battery Historian) —
   он даёт мА·ч по подсистемам, включая GPS.

### 6.2 Что измерено фактически

Методика: приложение запущено на эмуляторе оператором со **открытой сменой**;
`integration_test/gps_intervals_test.dart` держит его живым и каждые 15 с печатает
состояние трекера (интервал, скорость, отправлено, буфер, ошибка); координаты
подаёт `test/uat/gps-intervals-driver.sh` через `adb emu geo fix` вместе со
**скоростью** (интервал выбирается по последней известной скорости: порог 0,5 м/с,
`GpsTrackingConfig`); фазы — статично → движение → сеть выключена → сеть включена.
Интервалы считаются по меткам времени, которые **принял сервер**
(`GET /api/gps/tracks`), а не по обещаниям кода.

## 7. Дефекты, найденные измерениями

Измерения на устройстве нашли то, что не могли найти ни widget-тесты (они подменяют
геолокацию и адреса), ни e2e-наборы (они ходят по HTTP с хост-машины):

| Дефект | Как найден | Статус |
|---|---|---|
| **Нет разрешений геолокации в манифесте** — `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` не запрашивались приложением вовсе; GPS-вертикаль на устройстве не работала | `dumpsys package … requested permissions` (их нет) + состояние трекера «точек 0» на прогоне GPS | исправлено: `android/app/src/main/AndroidManifest.xml` |
| **Адрес плана этажа недоступен устройству** — `planImageUrl` приходил с хостом `localhost:9000`; на эмуляторе `localhost` — это сам эмулятор, карта маршрута показывала заглушку «План этажа недоступен» | `integration_test/probe_plan_url_test.dart`: контракт → `Connection refused`, тот же путь с `10.0.2.2` → HTTP 200 | исправлено: `ApiConstants.deviceUrl` + разбор адресов в моделях |
| Первый фикс GPS на эмуляторе приходит за 110–430 с | `integration_test/probe_location_test.dart` (два прогона) | ограничение стенда, не продукта: подан непрерывной петлёй `geo fix`, измерение удлинено |

Подробности и остальные дефекты UAT — `docs/UAT_PROTOCOL.md`.
