# Систематический разбор репозитория DOMCLEAR
## Детальная ревизия перед ребилдом

> Цель разбора: собрать всю интеллектуальную ценность репозитория в одном месте, оценить состояние и сформировать рекомендации для ребилда. Разбор основан на чтении документации, контрактов API, UAT-протоколов и отчёта по производительности — код не запускался заново, всё, что ниже, взято из документов и фактов, проверённых предыдущими прогонами.

## 1. Git-история и состояние репозитория

### 1.1 Ветки

- **`main`** — bootstrap-ветка, содержит минимальную заготовку репозитория. Не является производственной.
- **`develop`** — интеграционная ветка, активно развивается. Вся работа идёт здесь.
- **Веток вида `feature/*`, `bugfix/*`, `release/*` в репозитории нет** в том виде, в котором описывает Устав. Git-операции (коммиты, пуш, ветки) в процессе работы orch
estrate были запрещены условием задачи — всё оставалось в рабочем дереве и фиксировалось отдельно в документах оркестра.
- **Ветка `release/1.0.0` не создавалась** — М7.6 (финальный смоук и релиз) не стартовала.

### 1.2 Статус зависимостей

Репозиторий использует pnpm 10.34.5. Контракты shared собираются отдельной командой `pnpm build:shared` (или напрямую через `tsc -b shared/tsconfig.json --force` при проблемах с песочницей pnpm). Node 24, Jest 29, Playwright для e2e, k6 v2.2.0 для нагрузочного тестирования.

### 1.3 GitHub Actions / CI

**CI не настроен.** Устав заявляет «Все PR должны проходить CI», «Code review обязателен для merge в main», «Тесты должны проходить перед merge» — но в репозитории нет workflow-файлов, и в ходе всех вех правок workflow не требовалось. Разрешение токена GitHub не имеет scope `workflow`, поэтому правки workflow через API невозможны — только через веб-интерфейс или Contents API.

### 2.2 Структура бэкенда (9 сервисов)

Каждый сервис — самостоятельный NestJS-проект с собственной `prisma/schema.prisma`, собственной БД (`cleaning_ops_*`) и Dockerfile. Сервисы общаются через HTTP (REST) и RabbitMQ (события).

| Сервис | Порт | БД | Ответственность |
|---|---|---|---|
| auth-service | 3001 | `cleaning_ops` | Аутентификация, JWT, RBAC, пользователи |
| file-service | 3002 | `cleaning_ops_files` | Хранение файлов (MinIO), привязки, thumbnails |
| core-service | 3003 | `cleaning_ops_core` | Объекты, этажи, помещения, маршруты, техкарты |
| gps-service | 3004 | `cleaning_ops_gps` | GPS-треки, геозоны, SOS-поиск ближних |
| ticket-service | 3005 | `cleaning_ops_tickets` | Заявки, статусы (state machine), назначения, комментарии |
| notification-service | 3006 | `cleaning_ops_notifications` | Push/in-app уведомления, FCM-токены |
| material-service | 3007 | `cleaning_ops_materials` | Справочник материалов, движения, остатки, автосписание |
| schedule-service | 3008 | `cleaning_ops_schedule` | Графики, смены, check-in/out, генерация |
| chat-service | 3009 | `cleaning_ops_chat` | Чаты (DIRECT/OBJECT/TICKET/SYSTEM), сообщения, WebSocket |

Фронтенд-сервисы: web-admin (React) и web-client/портал (React) — статические сборки за nginx.

### 2.3 Подvez**:

Порт 8080 — единая точка входа nginx (админка + API под префиксом `/api`). Портал — порт 8081. Dev-режим: Vite проксирует `/api/*` на сервисы 3001–3009.

### 4.2 Рассинхроны Устава с реальностью

Устав содержит несколько рассинхронов, которые важно знать перед ребилдом:

1. **Статус проекта (раздел 10)**: все компоненты отмечены "🔴 Не начат 0%". Это состояние на момент создания устава (М0.3, начало проекта). Реальный статус: значительная часть реализована (смотри FACTS.md и ПЛАН.md).

2. **Структура репозитория (раздел 6)**: описана структура на момент М0.3. В реальности добавлена директория `design/` (решение №1 в SYSTEM_ARCHITECTURE.md), файлы экрана в `design/screens/`. Также в корне появился файл `ПЛАН.md` (живой план), которого нет в структуре устава.

3. **Файл `PLAN.md`**: в уставе упоминается как `PLAN.md`, но в репозитории лежит `ПЛАН.md` (кириллица). Это не ошибка — просто разные имена. При ребилде имя нужно выбрать одно.

4. **"Дизайн-система — 🔴 Не начата"**: в `design/` есть экран-спекы (`design/screens/web-admin/`, `design/screens/web-client/`), но дизайн-система как таковая (токены, Storybook, Figma-компоненты) не создана. В Уставe указано, что директория `design/` — рабочая директория агента Design System.

5. **Firebase/Mapbox**: в уставе указаны как зависимости, но в реальности используются мок-адаптеры (заглушки). Реальные ключи не подключены.

6. **CI**: в уставе «Все PR должны проходить CI», но CI не настроен.

### 6.3 Дефекты с механизмом (раздел 4 FACTS.md)

10 дефектов, каждый с описанием механизма:

1. **Chat `POST /api/chat/chats` → 500** — глобальный уникальный индекс `Chat.objectId`, ticket-чат писал туда объект заявки, вторая заявка того же объекта → `P2002` → ветка гонки → `NotFoundError` → 500. **Исправлено**: ticket-чат не заполняет `objectId`, CHECK-ограничение, миграция.
2. **Мобильное приложение не запрашивало разрешение геолокации** — в `AndroidManifest` не было `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`. Итог: диалог не появляется, точки не пишутся, check-in не работает. **Критичный, исправлено**.
3. **Адреса файлов с localhost** — `planImageUrl` и ссылки отдавались с `localhost`, на телефоне `localhost` — само устройство. Итог: план этажа не грузился. **Исправлено**: `ApiConstants.deviceUrl` приводит петлевой хост к хосту API.
4. **GIST-индексы М3.1 не использовались** — индексы по `geometry`, предикаты приводили к `::geography` → условие в `Filter`. "Сотрудники поблизости" — 2400 мс с отбрасыванием 35 468 строк. **Исправлено**: индексы по выражению `((location)::geography)`.
5. **Мёртвый консьюмер RabbitMQ в material-service** — 18 необработанных событий, 0 подписчиков, тишина в логе. Не работало автосписание материалов. **Исправлено**: `AmqpConnectionService.onChannelLost` перерегистрирует подписку.
6. **Композер портала под фиксированной панелью навигации** — сообщение нельзя было отправить. **Исправлено**.
7. **OOM-kill Postgres под эмуляцией** — JIT давал 14,7 с вместо 9 мс на тяжёлом агрегате. **Исправлено**: `jit=off`.
8. **Причина пятисекундных таймаутов — ретранслятор nginx, а не сервис** — nginx открывал новое TCP-соединение на каждый запрос, при 100 rps переставал принимать новые. **Исправлено**: keepalive + `Connection` без `close`.
9. **Контракты `@cleaning-ops/shared` не резолвились в рантайме образов** — две независимые причины: `tsc` не переписывает `paths` в эмите commonjs + `exports` без `require`/`default`. 23 рантайм-импорта в 7 сервисах. **Исправлено**: реальная копия пакета в `node_modules/@cleaning-ops/shared` в каждом образе.
10. **Доступ заказчика по совпадению строк** — `Object.clientName` сравнивался с `user.fullName`/`email` эвристически. Тёзки смешивались, переименование ломало портал. **Исправлено 21.09.2026**: явная привязка `ownerClientId`.

## 9. Архитектура: полный разбор

### 9.1 Слои

```
CLIENT LAYER
  Flutter App (iOS/Android, offline-first) | React Admin (Web) | React Client Portal (тонкий)
        │  HTTPS / REST / WebSocket
        ▼
API GATEWAY (Traefik / Kong — планируется, сейчас: nginx)
        ▼
SERVICE LAYER (микросервисы NestJS, 9 штук)
  auth │ core │ tickets │ gps │ files │ materials │ schedule │ chat │ notification
        ▼
DATA LAYER
  PostgreSQL 16 + PostGIS (8 отдельных БД) │ Redis 7 (пустышка) │ MinIO (файлы)
  Message Broker: RabbitMQ (exchange cleaning-ops.events)
```

### 9.2 Ключевые архитектурные решения

**Микросервисы с изолированными БД.** Каждый сервис — своя БД, своя Prisma-схема, своя миграция. Никаких FK между БД — связи только на уровне бизнес-логики (сервис-клиент ходит в сервис-провайдер по API). Это даёт независимость деплоя и масштабирования, но усложняет транзакционность (автосписание материалов — событийная модель через RabbitMQ).

**Event-Driven через RabbitMQ.** Exchange `cleaning-ops.events` (topic), DLQ `cleaning-ops.events.dlq`. События: `ticket.created`, `ticket.assigned`, `ticket.emergency`, `ticket.overdue`, `ticket.operation.completed`, `geofence.exit`, `material.low`, `schedule.missed_checkin`. Важно: delivery guarantee — consumers подтверждают сообщения (`ack`), при потере соединения подписка перерегистрируется (исправлено в М7.3).

**CQRS-облегчённый для отчётов.** Read-модели — SQL views в БД сервиса-владельца данных. Нет единого view сквозь сервисы — дашборд админки собирает ответы отдельных сервисов.

**State machine для заявок.** Статусы заявок — state machine из `shared/types/tickets.ts`. Невалидный переход → 400 `Invalid status transition`.

**Привязка "объект → аккаунт заказчика" (явная, с 21.09.2026).** `Object.ownerClientId` — id пользователя auth-service. Проверка идёт под служебной учёткой. Fail-closed: при недоступности auth — 503 и запись не создаётся.

- 10 исправленных дефектов с задокументированными механизмами (полезно для избегания их в новой системе)
- Рабочая инфраструктура стенда, воспроизводимая из репозитория
- Отсутствие CI/CD, k8s, мониторинга, SSL как открытые точки для ребилда
- Серверный scope объектов — critical security gap, который нужно закрыть с самого начала новой системы

Ребилд допускает и даже рекомендуется — накопленная база полностью пригодна для использования как основа нового продукта или новой реализации того же продукта.
