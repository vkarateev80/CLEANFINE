## 2. Сценарии и методика

| Сценарий | Профиль | Что проверяется |
|---|---|---|
| `tickets.js` | `ramping-arrival-rate` 50→100 rps (30 с → 1 мин → 30 с) **плюс** `constant-arrival-rate` 100 rps 60 с | План М7.2: листинг заявок 50→100 rps, p95 < 500 мс, ошибок < 1 % |
| `gps-track.js` | `constant-arrival-rate` 5 зап/с × 250 точек = 1250 точек/с, 30 с | Чек-лист GPS: batch-приём 1000 точек/с |
| `schedule-gen.js` | 100 временных графиков; фаза `individual` — 100 триггеров при 20 VU; фаза `sweep` — один проход по всем графикам (как cron в 00:00) | ПЛАН.md М7.2: «пик генерации в 00:00» |
| `auth.js` | 10 параллельных входов с одного IP | ПЛАН.md М7.2: «burst-логин с rate-limit» (5 входов/мин на IP) |

Три решения методики, которые важно знать при чтении цифр:

1. **`tickets.js`: ступени устава переведены в arrival-rate.** Устав задавал ступени в VU
   (`30s→50`, `1m→100`, `30s→0`), но цель плана — 50→100 **запросов в секунду**. Сценарий держит
   именно скорость, а не число виртуальных пользователей: со `sleep(1)` из каркаса один VU даёт
   максимум 1 зап/с, и 100 rps недостижимы ни при каком числе VU.
2. **`tickets.js`: полка 100 rps отдельным сценарием.** Средняя скорость профиля 50→100→0 по
   построению равна `(50·30 + 75·60 + 50·30)/120 = 62,5 rps`, поэтому средний rps не может быть
   доказательством «выдержали 100 rps». Отсюда два независимых утверждения: `dropped_iterations == 0`
   на разгоне (k6 не отложил ни одной итерации) и полка 100 rps 60 с с порогом `iterations >= 5700`.
3. **`schedule-gen.js`: между фазами смены удаляются.** `individual` создаёт смены на дату
   генерации; если их не снять, `sweep` видит их и проходит по пути идемпотентности («всё
   пропущено»), измеряя не генерацию. Сценарий сам ждёт, пока API покажет 0 смен у тестовых
   графиков (`waitForEventsDrop`), а удаляет их внешняя команда из лога:
   `bash test/performance/cleanup-stand.sh events --ids <из лога setup>`.

## 4. Что исправлено в `tickets.js` и как это изменило цифры

| № | Дефект каркаса М0.8 | Исправление | Наблюдаемый эффект |
|---|---|---|---|
| 1 | Дефолт `BASE_URL = http://localhost:3000` — такого порта на стенде нет | дефолт `http://127.0.0.1:8080`, прод-адрес через `K6_BASE_URL` | без правки прогон не доходил до замера вообще |
| 2 | `login()` внутри итерации: bcrypt на каждый запрос + упор в лимит входа | логин один раз в `setup()`, токен передаётся через `data` | снят источник массовых 429/401; латентность листинга перестала включать bcrypt |
| 3 | Ожидался `200`, а `POST /api/auth/login` отвечает **201** | ожидание 201 (и явный `http.expectedStatuses`) | проверка логина перестала врать: было `login status is 200` — **0 ✓ / 3 885 ✗** |
| 4 | `sleep(1)` в конце итерации — 1 зап/с на VU | убран; профиль переведён в arrival-rate | появилась возможность держать 50→100 rps как скорость, а не как число VU |

Цифры «до/после» (одна и та же машина, один и тот же входной контур):

|---|---|---|---|---|

| Сценарий исправлен, ретранслятор без keepalive, `relay-before.json` | 6 002 | 5 002 мс | **15,96 %** | ✗ оба порога |

Отдельно про ошибку в моём собственном пороге. В первой редакции сценария стояло
`http_reqs{scenario:list} rate>=95`, и прогон давал «62,4 rps — порог нарушен». Это была ошибка

итерация = 100,00 rps.

## 5. Почему `auth.js` меряется на отдельном экземпляре auth-service

Дев-стенд поднимает auth-service с `THROTTLE_LOGIN_LIMIT=1000` (`~/.cleaning-ops/stand.sh`), иначе
e2e-набор упирается в лимит логинов (`test/README.md`). На этом экземпляре лимит входа
не воспроизводится: 10 параллельных входов проходят все 10. Поэтому сценарий целится в
**второй экземпляр того же кода и той же БД** на `:3101` с боевыми значениями
(`THROTTLE_LOGIN_LIMIT=5`, `THROTTLE_GLOBAL_LIMIT=100`) — `test/performance/auth-prod-throttle.sh start`.
Основной стенд (nginx :8080, сервисы :3001–:3009) при этом не трогается, а после прогона
экземпляр снимается (`… stop`). Перед прогоном окно лимита должно быть чистым: ключ троттлинга —
`ip+endpoint`, поэтому проверка «жив ли порт» через `POST /api/auth/login` уже расходует слот
(в сценарии есть явное предупреждение в teardown).

## 6. Профилирование PostGIS: GIST-индексы М3.1 не работали

Команда плана: «Профилирование PostGIS-запросов (EXPLAIN на GIST-индексах М3.1)».
Результат: **индексы М3.1 в двух «горячих» пространственных запросах не используются вообще.**

```
-- gps.service.ts → findNearbyEmployees (SOS-вертикаль: ближние операторы 500 м)
ST_DWithin(gps.location::geography, ST_SetSRID(ST_MakePoint($lng,$lat),4326)::geography, $r)
-- geofence.service.ts → check (валидация check-in)
ST_DWithin(g.boundary::geography, ST_SetSRID(ST_MakePoint($lng,$lat),4326)::geography, 1000)
```

Причина: индексы `idx_gps_tracks_location` и `idx_geofences_boundary` созданы по **geometry**-колонке
(М3.1), а предикаты приводят колонку к **geography** (`location::geography`). Выражение не совпадает
с индексируемым, поэтому планировщик оставляет предикат в `Filter`:

| Запрос | План ДО (`results/explain/*-before.txt`) | План ПОСЛЕ (`*-after.txt`) |
|---|---|---|
| `employees/nearby` (100 000 точек, все в окне 5 мин — профиль чек-листа «1000 точек/с») | `Parallel Index Scan using idx_gps_tracks_user_time` + **Filter**, `Rows Removed by Filter: 35 468`, **2400 мс** | `Bitmap Index Scan on idx_gps_tracks_location_geography` + timestamp-индекс, `Rows Removed by Filter: 964`, **378 мс** |
| `geofences/check` (501 геозона) | `Seq Scan on geofences`, `Rows Removed by Filter: 500`, **223 мс** | `Index Scan using idx_geofences_boundary_geography`, **151 мс** |

**Исправление:** миграция `gps-service/prisma/migrations/20261002100000_m72_gist_geography_indexes/`
— GIST-индексы по выражению:

```sql
CREATE INDEX IF NOT EXISTS "idx_gps_tracks_location_geography" ON "gps_tracks" USING GIST ((("location")::geography));
CREATE INDEX IF NOT EXISTS "idx_geofences_boundary_geography"  ON "geofences"  USING GIST ((("boundary")::geography));
```

Геометрия-индексы М3.1 **оставлены**: их использует `ST_Contains(boundary, point)` в том же
`geofence.service.ts`, где предикат идёт по geometry. «После» — 6,4× на SOS-запросе и уход
Seq Scan у `check`.

Побочный эффект, зафиксирован честно: каждый `INSERT` в `gps_tracks` теперь обновляет два
GIST-индекса вместо одного. В сценарии `gps-track.js` p95 вырос с ~61 мс (смоук-прогон до
миграции) до 91,6 мс — при пороге 500 мс и требовании 1000 точек/с (достигнуто 1242 точек/с).

## 7. Узкое место №1: ретранслятор nginx → хост (satурация NAT ВМ colima)

**Симптом.** Через единую точку входа `:8080` листинг заявок под нагрузкой давал
`p(95) = 5 001 мс` и **18,14 %** ошибок при порогах 500 мс / 1 %. Ровно 5 001 мс — это
`proxy_connect_timeout 5s` из `~/.cleaning-ops/nginx/proxy.conf`.
В логе nginx — 1 967 строк за прогон:

```
[error] upstream timed out (110: Operation timed out) while connecting to upstream,
        request: "GET /api/tickets?take=50", upstream: "http://192.168.5.2:3005/api/tickets?take=50"
```

**Что исключено измерениями (а не рассуждением):**

* **Сервис здоров.** Тот же сценарий напрямую на `:3005` (host-loopback, минуя контейнер):
  p95 6,73 мс, 0 % ошибок, 100 rps держатся (`results/tickets-direct.json` и серия прогонов
  75/100/125 rps — p95 7,3/6,7/6,9 мс, 0 ошибок).
* **Не пул соединений Prisma.** Во время отказов в `pg_stat_activity` не было ни одного
  активного запроса, а сами запросы до Postgres не доходили: nginx не мог установить TCP-соединение.
* **Не Postgres.** `EXPLAIN (ANALYZE)` листинга на текущем объёме — 2,4 мс (`results/explain/tickets-listing-*.txt`).
* **Перезапуск контейнера nginx мгновенно возвращал работоспособность** — то есть отказывал не
  сервис, а именно путь «контейнер → хост».

**Причина.** Ретранслятор открывал **новое TCP-соединение к хост-машине на каждый запрос**:
в `proxy.conf` не было пула, а `map` отдавал `Connection: close` для обычных (не-WebSocket)
запросов, что заведомо запрещает keepalive. При 100 rps это ~100 новых соединений в секунду
сквозь NAT ВМ colima (2 vCPU / 2 ГиБ), который под нагрузкой перестал принимать новые соединения.

**Исправление** (машинная обвязка, `~/.cleaning-ops/nginx/nginx.conf`; в репозитории — описание в
этом отчёте и в `test/performance/README.md`):

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' ''; }   # было: '' close
upstream tickets_upstream { server host.docker.internal:3005; keepalive 16; }
location ~ ^/api/tickets(/|$) { proxy_pass http://tickets_upstream; include /etc/nginx/proxy.conf; }
```

**Подтверждение повторным замером** — один и тот же сценарий (100 rps, 60 с), одна машина,
разные ретрансляторы (второй поднят как временный контейнер `nginx-before-relay` со старой
конфигурацией, `results/relay-before-nginx-errors.txt` — 958 строк connect-timeout):

| | ДО (без keepalive) | ПОСЛЕ (keepalive) |
|---|---|---|
| p(95) | **5 002 мс** | **20,66 мс** |
| p(99) | 5 005 мс | 343 мс |
| Ошибок | **15,96 %** (958 × 504) | **0,00 %** |
| Выполнено итераций | 6 001 (958 не обслужено) | 6 000 (100,00 rps) |
| `upstream timed out … while connecting` | 958 | 0 |

Для WebSocket путь сохранён: при наличии `Upgrade` map по-прежнему отдаёт `upgrade`
(конфигурация проверена `nginx -t`, чат-вертикаль e2e зелёная).

## 8. Узкое место №2: запрос листинга заявок (код) — и №3: пул соединений

### 8.1 Листинг: агрегаты по всей дочерней таблице + отсутствие индекса сортировки

Профиль: реплика схемы `cleaning_ops_tickets` в отдельной БД `cleaning_ops_perf_tickets`
(200 000 заявок, 200 000 назначений, 300 000 комментариев, 200 000 операций — создана и удалена
скриптом проверки; демо-БД не затрагивалась).

`include: { _count: … }` в Prisma разворачивается в три `LEFT JOIN` с `GROUP BY` **по всей**
дочерней таблице. `EXPLAIN (ANALYZE, BUFFERS)` (`results/explain/tickets-listing-before.txt`):

```
Parallel Seq Scan on tickets t → Sort (external merge Disk: 3440kB)
  → Merge Left Join (loops=3) ← GroupAggregate over ticket_comments (300 000 строк, loops=3)
  → Merge Left Join (loops=3) ← Index Only Scan on ticket_assignments (200 000 строк, loops=3)
  → Merge Left Join (loops=3) ← Index Only Scan on ticket_operation_completions (200 000)
Execution Time: 9 917 мс          ← стоимость одного запроса листинга
```

То есть стоимость листинга росла не с размером страницы, а с **общим числом** комментариев,
назначений и операций.

**Что исправлено:**

1. `GET /api/tickets` больше не тянет `_count` через `include`. Счётчики считаются отдельными
   `groupBy` **только по id текущей страницы** (`≤ 100` значений) — `TicketsService.relationCounts`
   в `backend/ticket-service/src/tickets/tickets.service.ts`. Форма ответа сохранена
   (`item._count.{assignments,comments,operations}` — её читает `TicketsPage.tsx`), зафиксировано
   юнит-тестом.
2. Индекс под сортировку листинга — миграция
   `ticket-service/prisma/migrations/20261002100000_m72_tickets_createdat_index/`:
   `CREATE INDEX "tickets_createdAt_idx" ON "tickets"("createdAt" DESC);`
   Существующий `tickets_status_createdAt_idx` начинается со `status`, поэтому при листинге без
   фильтра по статусу (штатный экран админки) планировщик его не применяет.

**Подтверждение повторным замером** (`results/explain/tickets-listing-after.txt`):

| Часть запроса | До | После |
|---|---|---|
| Страница: `ORDER BY createdAt DESC LIMIT 50` | `Parallel Seq Scan` + `Sort (external merge Disk)` | `Index Scan using "tickets_createdAt_idx"` — **3,2 мс** |
| Счётчики связей | `GroupAggregate` по 300 000 строк × 3, `loops=3` | `Index Only Scan … loops=50` — **9,0 мс** |
| **Запрос листинга целиком** | **9 917 мс** | **≈ 0,46 с** (страница 3,2 мс + счётчики 9,0 мс + точный `COUNT` 448 мс) |

Остаётся честно назвать остаток: `total` для пагинации Prisma считает точным `COUNT(*)`
(448 мс на 200 000 строк эмулированного Postgres) — семантика ответа не менялась, поэтому это
осознанный остаток с рекомендацией на будущее (приблизительный счётчик или материализованный
агрегат), а не забытый дефект. На объёме стенда (21 заявка) он равен долям миллисекунды.

### 8.2 Пул соединений Prisma vs `max_connections` Postgres

Проверка, которую требовал разбор: **упор в лимит соединений был реальным риском, но не причиной
пятисекундных таймаутов**.

* `max_connections = 100`; Prisma по умолчанию берёт `num_cpus·2+1 = 21` соединение **на каждый
  из девяти сервисов** → до 189 соединений против 100.
* Замер на простаивающем стенде: **84 соединения заняты пулами, все `idle`** (tickets 21,
  schedule 21, auth 14 …). В логах М7.3 уже был отказ `Server has closed the connection`.
* При этом во время пятисекундных таймаутов активных запросов в Postgres не было — то есть
  в тот момент пул не был лимитером.

**Исправление:** пул задан явно в `.env` и `.env.example` — `connection_limit=8` во всех девяти
`*_DATABASE_URL` (9 × 8 = 72 при лимите 100, с запасом на psql, e2e и обслуживание). После
перезапуска стенда занято **12 соединений** вместо 84.

Отдельно проверена гипотеза «пул — причина хвоста у schedule-gen»: поднятие пула
schedule-service до 16 сделало хвост **хуже** (p95 0,6 с → 1,2 с при 20 параллельных триггерах),
то есть лимитер — не пул, а эмулированный Postgres. Конфигурация возвращена к 8.

## 9. Ограничения стенда (отделено от дефектов кода)

| Ограничение | Доказательство | Следствие для цифр |
|---|---|---|
| Postgres-образ **x86_64** (`postgis/postgis:16-3.4`) работает на **aarch64**-ВМ | `docker exec cleaning-ops-postgres uname -m` → `x86_64`; `colima status` → `arch: aarch64` | абсолютные времена планов завышены в разы: `COUNT(*)` по 200 000 строк — 448 мс, планирование простого запроса — 92–117 мс |
| ВМ colima: **2 vCPU, 2 ГиБ** | `colima list` → `CPUS 2, MEMORY 2GiB` | 20 параллельных генераций упираются в CPU БД (p95 0,6–1,2 с), а не в пул и не в код |
| Ретранслятор «контейнер → хост» — user-space NAT ВМ | §7 | до исправления — 5-секундные 504 и 16–18 % ошибок; после — 0 % |
| k6 и стенд делят одну машину | `uptime`, `ps aux` перед прогонами | фоновая нагрузка (осиротевшие Chromium, `appstoreagent`) снята перед эталоном; порядок проверки описан в §1 |

Что из этого важно для прода: ретранслятор и эмуляция — свойства **этого** дев-стенда. В проде
(М7.5: K8s, отдельный Postgres на сервис, нативный x86_64) этих ограничений нет, а исправления
§6 и §8.1 — свойства **кода** и переносятся в прод как есть.

## 10. Расхождения между планом и фактическим поведением системы

1. **План: «50→100 rps».** Ступени устава заданы в VU (`30s→50…100`). Буквальное исполнение даёт
   ~62 rps (один VU = 1 зап/с из-за `sleep(1)`) и недостижимую цель. Сценарий переведён на
   arrival-rate; `sleep(1)` из каркаса убран.
2. **План: «порог p95 < 500 мс».** Задан только для `tickets.js`; у `auth.js`/`gps-track.js`/
   `schedule-gen.js` требований по латентности план не содержит. Для `gps-track` это чек-лист
   «1000 точек/с», для `schedule-gen` — «пик генерации в 00:00». Пороги расставлены ровно по
   плану; собственные (не плановые) пороги помечены в коде сценариев.
3. **GIST-индексы М3.1 не обслуживают geography-предикаты** своих же сервисов — индексы есть,
   эффекта нет (§6). Требовало отдельной миграции; план этого не предполагал.
4. **`POST /api/auth/login` отвечает 201, а не 200.** Каркас устава ждал 200 — проверка не
   проходила никогда. План/устав этого не фиксировали.
5. **Лимит входа не воспроизводится на дев-стенде** (`THROTTLE_LOGIN_LIMIT=1000`), а сценарий
   `auth.js` по плану — «burst-логин с rate-limit». Потребовался второй экземпляр auth-service с
   боевыми лимитами (§5).
6. **Прогон «через единую точку входа» упирается в стенд, а не в систему** (§7): при 100 rps
   ретранслятор nginx→хост насыщается. Без его исправления пороги плана невыполнимы ни при
   каком состоянии кода.
7. **Замер «средним rps» некорректен** для профиля 50→100→0: среднее по построению ≈ 62,5 rps.
   Форма проверки — `dropped_iterations == 0` + явная полка 100 rps.
8. **Уборка данных.** Демо-среда не является каноном проекта (`test/README.md`), при этом её
   требуется сохранять: для сценариев созданы свои данные (треки оператора, 100 временных
   графиков) и добавлен `test/performance/cleanup-stand.sh`, который удаляет только их. Побочный
   эффект прохода `sweep` без `scheduleId` — он идёт и по демо-графикам (идемпотентно); созданные
   при этом демо-смена и заявка после прогонов сняты, состояние сверено с исходным (§1).
