# Проверенные факты проекта Cleaning Ops

Единая спека фактического состояния системы. Собрана по итогам М6 и М7 и содержит только то,
что **проверено запуском, измерением или чтением кода** — не пересказ спецификаций. Там, где
утверждение взято из документации, а не из наблюдения, это помечено.

Как пользоваться: перед работой с сервисом или экраном сверяйтесь с разделом 3 (контракты API)
и разделом 5 (ловушки среды). Большинство этих фактов стоило часов отладки; они собраны здесь,
чтобы не стоило их дважды.

## 3. Контракты API — фактические, снятые с кода и живыми запросами

| Эндпоинт | Факт |
|---|---|
| `POST /api/auth/login` | отвечает **201**, а не 200 |
| `GET /api/chat/chats` | отдаёт **голый массив**, а не `{ items }` — единственная такая асимметрия в проекте |
| Поля чата | `id, type, title, objectId, ticketId, createdAt, lastMessage, unreadCount`. **`title` бывает `null`**; **поля участников нет вовсе** |
| Поля сообщения | `id, chatId, authorId, text, attachmentIds, createdAt` — **имени автора нет**, только id |
| Чат по WebSocket | namespace **`chat`**, токен в **`auth.token`** handshake (основной путь), `?token=` — запасной; события клиента `message:send`, `message:read`; при невалидном токене соединение отклоняется с `unauthorized` |
| `POST /api/notifications/device` | тело `{ token, platform }`, где `platform` строго `android` \| `ios` \| `web`; отвечает **200**, не 201 |
| `GET /api/notifications` | `{ items, total, page, limit, unreadCount }` |
| `PATCH /api/notifications/settings` | тело `{ disabledTypes: [...] }` — типы, от которых пользователь **отказывается**. Семантика **обратная** состоянию тумблера: инвертировать и при чтении, и при записи |
| Аварийная заявка | только `POST /api/tickets/emergency`; через `POST /api/tickets` её создать нельзя |
| `POST /api/users` | обязательны `email`, `password`, `fullName`; `role` из `OPERATOR`\|`SUPERVISOR`\|`ADMIN`\|`CLIENT` |
| `POST /api/objects` | обязательны `name`, `address`, `lat`, `lng`, `type`, `totalArea`, `floorsCount`, `clientName`, `clientContact` |
| `ownerClientId` в объекте | `string \| null` в ответах `GET /api/objects`, `GET /api/objects/:id`, `GET /api/objects/:id/detail`, `POST`/`PATCH`. `null` = «привязки нет» (проверено запуском) |
| Три состояния в `POST`/`PATCH /api/objects` | различаются по `'ownerClientId' in dto`: **поля нет** → привязка не меняется (в `data` ключа нет); **`null`** → снять привязку (валидации нет); **непустая строка** → проверить аккаунт в auth-service и записать. Пустая строка `""` защитно нормализуется в `null`. Проверка по значению (`dto.ownerClientId === undefined`) этот случай НЕ различает — именно на этом держится «`PATCH` названия не затирает привязку» |
| Фильтр `GET /api/objects?ownerClientId=<id>` | точное совпадение, комбинируется с `status`/`type`/`search` через AND; индексирован (`objects_ownerClientId_idx`). **Это фильтр списка, а не авторизация** (раздел 4.10) |
| Коды валидации `ownerClientId` | несуществующий id → **400** «Аккаунт заказчика не найден»; аккаунт не `CLIENT` → **400** «Аккаунт не является клиентом»; деактивированный CLIENT → **400** «Аккаунт клиента деактивирован»; недоступен auth-service (сеть/таймаут/5xx/401-после-повтора/нет `SERVICE_AUTH_*`) → **503** «Не удалось проверить аккаунт заказчика», запись НЕ выполняется; `ownerClientId` не строка → **400** от `ValidationPipe` (всё проверено запуском) |
| Отчёты (М7.1) | `/api/{materials,tickets,schedule,gps}/reports/<отчёт>`; представления живут **внутри** сервисов-владельцев данных |

**Пуш:** в разработке при пустых `FIREBASE_*` поднимается `MockPushSender`, поэтому весь путь
push проверяется без реальных ключей. Заводить их не нужно.

## 4. Дефекты, найденные и исправленные (с механизмом)

1. **`POST /api/chat/chats` → 500.** У `Chat.objectId` глобальный уникальный индекс, а ticket-чат
   писал туда объект заявки. Вторая заявка того же объекта давала `P2002`, `isUniqueViolation`
   уводил в ветку «гонки», где чат по `ticketId` не находился → `NotFoundError` → 500.
   Исправлено: ticket-чат не заполняет `objectId`, ветки гонки используют `findUnique` с rethrow,
   миграция + CHECK-ограничение.
2. **Приложение не запрашивало разрешения геолокации.** В `AndroidManifest` не было
   `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`, а `geolocator_android` их намеренно не
   декларирует. Итог на устройстве: диалог не появляется, точки не пишутся, геозона при
   `check-in` не проверяется — **смена оператора не открывалась вообще**. Автотесты не видели,
   потому что работают на подменах.
3. **Адреса файлов с петлевым хостом.** `planImageUrl` и ссылки фото/аватара/вложений отдавались
   с `localhost`, что верно в браузере на той же машине, но на телефоне `localhost` — само
   устройство. Итог: карта маршрута показывала заглушку вместо плана этажа. Исправлено
   приведением петлевого хоста к хосту API (`ApiConstants.deviceUrl`).
4. **GIST-индексы М3.1 не использовались вообще.** Предикаты приводили колонку к `::geography`,
   а индексы были по geometry → условие уходило в `Filter`: «сотрудники поблизости» 2400 мс
   с отбрасыванием 35 468 строк. После индексов по выражению — 378 мс. **Дефект функциональный,
   а не только производительный:** страдали SOS-вертикаль и валидация входа на объект.
5. **Мёртвый консьюмер RabbitMQ** в material-service: 18 необработанных событий, ноль
   подписчиков, в логе тишина — не работало сквозное автосписание материалов.
6. **Композер портала под фиксированной панелью навигации** — сообщение нельзя было отправить.
7. **OOM-kill Postgres под эмуляцией:** JIT давал 14,7 с вместо 9 мс на тяжёлом агрегате.
   Закрыто `jit=off`.
8. **Причина пятисекундных таймаутов под нагрузкой — ретранслятор, а не сервис.** nginx открывал
   новое TCP-соединение на каждый запрос; при 100 rps он переставал принимать новые. Исключено
   измерениями: сервис напрямую давал p95 6,7 мс и 0 ошибок. **Урок: убедись, что меряешь
   систему, а не транспорт перед ней.**
9. **Контракты `@cleaning-ops/shared` не резолвились в рантайме образов** (найдено и исправлено
   21.09.2026 при сборке VPS-стенда, коммит `d746ee0`). Симптом: `Cannot find module
   '@cleaning-ops/shared/…'`, а после правки `exports` — `ERR_PACKAGE_PATH_NOT_EXPORTED`.
   **Две независимые причины**, обе проверены запуском:

   | Причина | Механизм | Где видно |
   |---|---|---|
   | `tsc` не переписывает `paths` | Эмит commonjs оставляет bare-спецификатор `require("@cleaning-ops/shared/types/core")`; Node резолвит bare-спецификаторы **только через `node_modules`**, а `backend/*/Dockerfile` клали контракты лишь в `/repo/shared/dist` | комментарий в `backend/core-service/Dockerfile` («tsc резолвит в относительный путь»), grep по эмиту |
   | `exports` без `require`/`default` | Объявлены были только `types` и `import`; `require()` отказывал даже при корректно положенном пакете | `shared/package.json`; воспроизведено на `node:20-alpine` |

   Масштаб: **23 рантайм-импорта** (не `import type`) в семи сервисах — chat 1, core 4, gps 2,
   materials 5, notification 3, schedule 3, ticket 5; `auth` и `files` импортируют только типы.
   Дополнительно chat и material падали на сборке: шаг `cd shared && npm run build` давал
   `tsc: not found` (exit 127). Исправление: `require`/`default` + `"./package.json"` в `exports`
   и единый паттерн всех девяти `backend/*/Dockerfile` — реальная копия пакета (`package.json` +
   `dist`) в `node_modules/@cleaning-ops/shared` уезжает в финальный образ. **Доказательство:**
   11 образов собраны, `deploy/vps/verify-images.sh` — 14/14, старт без обеих ошибок,
   негативный контроль `require('@cleaning-ops/shared/nope/nope')` → `ERR_PACKAGE_PATH_NOT_EXPORTED`.
   **Урок:** «работает в dev» здесь ничего не значит — в dev алиас держит `tsconfig paths`, а в
   собранном commonjs остаётся голый спецификатор.

10. **Доступ заказчика к объекту определялся совпадением строк — заменено явной привязкой**
    (21.09.2026, проект оркестра `prj-cleanfine-yavnaya-privyazka-obekta-k-akkauntu-za`,
    проверено запуском на стенде `prj-cleanfine`). Дефект: у `Object` не было связи с
    аккаунтом, и портал (`useObjectScope`) выводил «свой объект» эвристикой
    `normalizeName(Object.clientName)` ↔ `fullName`/`email` из `/api/auth/me`, а при
    нескольких кандидатах брал первый по возрастанию `id`. Последствия: доступ выдавался
    **по совпадению отображаемой строки**, а не по правам; **тёзки смешивались**; переименование
    заказчика или иное написание ломало портал («Объект не подключён»), а «правильное»
    написание, наоборот, открывало чужой объект.

    | Что | Как сделано |
    |---|---|
    | Хранение | `Object.ownerClientId String?` + `@@index([ownerClientId])`; миграция `20260921190000_add_owner_client_id_to_object` — аддитивная (`ADD COLUMN TEXT` + `CREATE INDEX`), SQL сгенерирован `prisma migrate diff`, не написан руками |
    | Валидация записи | новый `AuthServiceClient` (`backend/core-service/src/objects/auth-service.client.ts`): логин `POST {AUTH_SERVICE_URL}/api/auth/login` под служебной учёткой → `GET /api/users/:id`; из `SafeUser` берутся **только** `id`/`role`/`isActive`; таймаут 5 с (`AUTH_SERVICE_TIMEOUT_MS`); кэш токена по `exp` со skew 30 с, дедупликация параллельных логинов, сброс и один повтор при 401/403; **fail-closed** — при недоступности auth запись не выполняется (503) |
    | Админка | селект «Аккаунт заказчика» из `GET /api/users?role=CLIENT`, опция «— Без привязки —», автоподстановка `clientName`/`clientContact`; в списке и карточке — резолв аккаунта и метки «Без привязки» / «аккаунт деактивирован» / «аккаунт недоступен» |
    | Портал | scope только по `ownerClientId === sessionUser.id` (`listObjects({ ownerClientId })`), результат сортируется по `id`; эвристика (`normalizeName`, `identityCandidates`, `matchObject`, `findOwnObjects`) удалена начисто — 0 вхождений в исходниках; текст экрана «Ваша учётная запись ещё не связана с объектом обслуживания…» |
    | Данные | `scripts/seed/seed-demo-object.mjs` создаёт объект с `ownerClientId`; новый `scripts/seed/backfill-owner-client.mjs` — разовый идемпотентный backfill (dry-run по умолчанию, `--commit`, только единственное точное совпадение, при неоднозначности не меняет; 3 прогона → 2 PATCH) |

    **Приёмка (проверено запуском):** портал владельца видит объект (1 объект); непривязанный
    `client@example.com` — 0 объектов; объект с `clientName`, совпадающим с ФИО клиента, но без
    привязки, клиенту **не виден** (главный регресс); создание с привязкой → 201; `PATCH` без поля
    привязку сохраняет, `PATCH` с `null` снимает; 400 на несуществующий и на не-CLIENT аккаунт;
    fail-closed — одноразовый контейнер core с недоступным `AUTH_SERVICE_URL` → POST **503** и
    отсутствие записи, контрольный POST без привязки → **201**. Юнит-тесты core — **320 зелёных**;
    блок `ownerClientId` в `test/e2e/api/core.api.spec.ts` (9 тестов) **фактически прогнан** против
    стенда — passed; UI-спеки портала (AC-04/05/06) в браузере **на момент приёмки исполнить не
    удалось** (chromium не стартовал в той среде). **Обновлено 22.09.2026: ограничение снято** —
    браузер установлен и проверен запуском, см. §5 «Локальный фронтенд и браузерная проверка».
    Кейсы остаются закрытыми на уровне API и проверкой текста в бандле, но теперь их можно
    перепроверить в браузере.

    **Главное ограничение, читать буквально:** **серверного scope НЕТ и в этом объёме не
    вводился.** `GET /api/objects` по-прежнему отдаёт объекты **любому аутентифицированному**
    пользователю (эндпоинт без `@Roles`), а `?ownerClientId=` — **фильтр списка, а не
    авторизация**: клиент может запросить `GET /api/objects?ownerClientId=<чужой id>` или
    `GET /api/objects/:id` и получить чужой объект напрямую. Портал — UI-механика поверх
    существующего API, а **не граница доступа**; нельзя принимать его за разграничение прав.
    Остальное: у клиента с несколькими объектами портал открывает первый по возрастанию `id`
    (многообъектный UX — вне объёма); `take ≤ 100`, поэтому выбор идёт по первой сотне.
    Реестр изменённых файлов и эксплуатация — `changelog` проекта оркестра (действующая версия —
    последняя зарегистрированная), `deploy/vps/README.md` (§5.1, §5.2, §10) и `КОНТЕКСТ.md`

## 5. Ловушки среды и кода — читать до начала работы

### Стенд и инфраструктура

- **Сервисы умирают вместе с процессом-родителем.** Запускать их нужно управляемой фоновой
  задачей (`stand.sh serve`), иначе через время стенд молча ложится и все проверки дают ложный
  результат.
- **Vite слушает `localhost` (IPv6) и недоступен по `127.0.0.1`.** Веб-набору e2e Vite
  обязателен: без него прогон даёт ложную картину (2 из 45 вместо 45).
- **Prisma и IPv6.** Серверные адреса в `.env` используют `127.0.0.1`, а не `localhost`
  (исключения: `MINIO_ENDPOINT`, `VITE_WS_URL`).
- **`docker exec` в контейнер Postgres.** Образ amd64 под эмуляцией; если в VM не зарегистрирован
  `qemu-x86_64`, любой `docker exec` падает с `exec format error`, уборка тестов пропускается
  (8 наборов вместо 1), и мусор прошлых прогонов роняет соседние тесты. Лечение — `colima restart`;
  проверка — `colima ssh -- ls /proc/sys/fs/binfmt_misc/`.
- **`scripts/reset-stand.sh` стирает и демонстрационные данные.** После него восстанавливать
  строго в порядке: аккаунты (`POST /api/users`) → объект (`POST /api/objects`) → `seed.mjs`.
  Сам сид объекта не создаёт и падает, если его нет.
- **В macOS нет `timeout`.** Для ограничения времени команды: `perl -e 'alarm shift; exec @ARGV' N <команда>`.

### Prisma и миграции

- **Живую базу нельзя передавать в `--shadow-database-url`** (проверено запуском, 21.09.2026;
  потеря данных на стенде). `prisma migrate diff` поднимает shadow-базу, **пересоздаёт в ней схему
  и в конце удаляет историю миграций**. Если туда передана рабочая БД, всё это происходит в ней.
  Симптом: пропала таблица `_prisma_migrations`, «обнулились» таблицы, при этом сервисы
  отвечают — схема осталась, утрачены история миграций и содержимое (на стенде
  `cleaning_ops_core`: `objects` 1 → 0 строк, демонстрационный объект потерян). Как обнаружить:
  журнал postgres —
  `docker compose ... logs postgres | grep -n 'DROP TABLE'`; в разборе инцидента видно
  дословно `DROP TABLE _prisma_migrations;`, а через полчаса — `SELECT … FROM
  "_prisma_migrations"` с `relation does not exist`. Правило: опыты с миграциями — **только**
  на одноразовом контейнере postgres или на базе `cf_*`, и перед каждой командой проверять
  `select current_database()`. Базу стенда руками не трогать; после инцидента восемь остальных
  баз были целы — потери ограничились одной.
- **`P3005`: база без `_prisma_migrations` валит `migrate deploy`.** Если схема создана в обход
  Prisma (`db push`, ручной SQL, восстановление из дампа), `prisma migrate deploy` отказывается
  работать: «The database schema is not empty». Лечение — **baseline**: `prisma migrate resolve
  --applied <миграция>` для каждой уже применённой миграции, затем `migrate deploy` накатит
  только новые (проверено на стенде: две миграции отмечены применёнными, третья накатилась, в
  `_prisma_migrations` три записи, ошибка больше не воспроизводится). **В `deploy/vps/redeploy.sh`
  это НЕ автоматизировано:** шаг «миграции (9 сервисов)» на базе без `_prisma_migrations` упадёт
  с `P3005` и остановит выкат (скрипт идёт с `set -euo pipefail`), лечится вручную до прогона.

### Сборка образов и контракты

- **`tsc` не переписывает алиасы `paths` в эмите** (проверено запуском, 21.09.2026). Собранный
  commonjs содержит литерал `require("@cleaning-ops/shared/types/core")`, и Node резолвит его
  **только через `node_modules`**. Копия контрактов в `/repo/shared/dist` помогает лишь
  компиляции. Значит, любой образ, чей код значимо импортирует `shared`, обязан положить
  **реальную копию пакета** в `node_modules/@cleaning-ops/shared` — см. раздел 4, дефект 9.
  Следствие: оговорка «tsc компилирует shared в относительный `require`» верна только для
  **type-only** импортов (их эмит стирается или превращается в относительный путь), для значимых
  — нет.
- **`pnpm build:shared` не работает, когда песочница находится вне воркспейса** — pnpm требует
  каталог вне воркспейса и падает с permission denied. Обход, встроенный в `bootstrap.sh` и
  `redeploy.sh`: собрать контракты напрямую —
  `( unset NODE_ENV; ./shared/node_modules/.bin/tsc -b shared/tsconfig.json --force )`.
  На macOS-стенде (раздел 5.2 `КОНТЕКСТ.md`) `pnpm build:shared` работает, поэтому обход нужен
  только там, где песочница ограничивает запись вне репозитория.
- **`NODE_ENV=production` в сессии ломает host-сборку `shared`**: npm/pnpm пропускают
  devDependencies, а `shared` собирается `typescript` из devDeps. Перед host-шагами — `unset NODE_ENV`.
- **Сборка 11 образов на хосте, разделённом с демо-стендом, роняет его healthcheck'и.** Замер:
  одна команда `docker compose build` поднимает load average до ~16, и `rabbitmq` демо-стенда
  уходит в транзиентный `unhealthy` (сам возвращается). Лечится сборкой группами по 1–2 сервиса
  с ожиданием снижения load — `deploy/vps/build-vps.sh`. `COMPOSE_PARALLEL_LIMIT` ограничивает
  только сервисы compose, но **не** параллельные `npm install` внутри BuildKit.

## 7. Процесс и инструменты

- **Один тип — один документ в реестре оркестра.** Новая версия того же типа **вытесняет**
  предыдущую: писать «отдельный task_spec на каждую веху» нельзя, иначе действующей останется
  только последняя. Остаток плана ведётся одним живым документом.
- **Разрешения токена.** У используемого токена нет scope `workflow`: `git push` с изменениями
  в `.github/workflows/**` отклоняется. Файлы workflow правятся через Contents API или веб-интерфейс;
  в этом репозитории правок workflow не потребовалось ни для одной вехи.
- **Git-операции — только у оркестратора.** Исполнителям запрещено коммитить, пушить и создавать
  ветки: изменения остаются в рабочем дереве и фиксируются отдельно.
- **Проверка результата — лично оркестратором**, а не по отчёту исполнителя. За проект трижды
  случалось, что исполнитель сдавал работу с неработающим кодом или без требуемых тестов; в одном
  случае он сообщил об успехе, не выполнив главного требования вехи.
- **Смена исполнителя после двух провалов себя оправдывает:** свежий контекст находил корневую
  причину там, где предыдущий дважды латал симптомы.
