### Дефект рантайм-резолва `shared` — главная находка

Собранные сервисы падали на старте: `Cannot find module '@cleaning-ops/shared/…'`, а после
правки `exports` — `ERR_PACKAGE_PATH_NOT_EXPORTED`. Две независимые причины, обе подтверждены
запуском:

1. **`tsc` не переписывает алиасы `paths`.** Эмит commonjs оставляет литерал
   `require("@cleaning-ops/shared/types/core")`; Node резолвит bare-спецификаторы **только через
   `node_modules`**, а прежние `backend/*/Dockerfile` клали контракты лишь в `/repo/shared/dist`.
   Комментарий в `backend/core-service/Dockerfile` («tsc резолвит в относительный путь
   `../../../../shared/dist`») был **ошибочен** — он и удерживал неверную схему доставки.
   Кстати, это отменяет оговорку раздела 0.7 («tsc компилирует `@cleaning-ops/shared/*`
   в относительный `require`»): относительный путь получается только у **type-only** импортов,
   а значимые импорты остаются bare-спецификаторами.
2. **В `shared/package.json` в `exports` не было условий `require`/`default`** (только `types` и
   `import`), поэтому даже корректно положенный пакет отказывал; воспроизведено на
   `node:20-alpine`.

**Масштаб:** 23 рантайм-импорта (не `import type`) из `@cleaning-ops/shared/*` в семи сервисах —
chat 1, core 4, gps 2, materials 5, notification 3, schedule 4, ticket 5; `auth` и `files`
импортируют только типы. Дополнительно `backend/chat-service` и `backend/material-service`
падали на сборке: шаг `cd shared && npm run build` давал `tsc: not found` (exit 127).

**Исправление.** В `shared/package.json` добавлены `require` и `default` (плюс `"./package.json"`,
условие `import` сохранено); все девять `backend/*/Dockerfile` приведены к **единому паттерну**
(ADR-8/D-3): `shared/dist` в `/repo/shared/dist` — только для компиляции (его требует `paths`),
а для рантайма пакет копируется **реальной копией** (`package.json` + `dist`) в
`node_modules/@cleaning-ops/shared` и уезжает в финальный образ; из chat и material убран
нерабочий шаг `cd shared && npm run build`.

**Доказательство:** 11 образов собраны; `deploy/vps/verify-images.sh` — **14/14** проверок
резолва; старт без `Cannot find module` и `ERR_PACKAGE_PATH_NOT_EXPORTED` (в логах проекта
0 совпадений); негативный контроль (`require('@cleaning-ops/shared/nope/nope')` →
`ERR_PACKAGE_PATH_NOT_EXPORTED`), то есть `exports` не открыт настежь.

## 0. Изменения 2026-09-14: сборка `shared` вынесена в `dist` (вариант B)

**Почему.** Аудит вскрыл блокер: `nest build` в auth-service завершался с exit 0, но складывал
вывод в `dist/backend/auth-service/src/main.js` вместо `dist/main.js` → `CMD ["node","dist/main.js"]`
в Dockerfile и `nest start` падали с MODULE_NOT_FOUND. Причина: tsconfig маппил
`@cleaning-ops/shared/*` на **исходники** `../../shared/*`, а `incremental: true` заставлял
`nest build` считать `commonSourceDirectory` по всему program'у — файлы вне `src/` поднимали
корень вывода. `tsc --noEmit` этого не ловил (именно поэтому баг дожил до М1.7).

**Что сделано (решение №6 из раздела 4 переведено в исполнение):**

- `shared/` теперь собирается: `composite: true`, `outDir: ./dist`, `rootDir: .` →
  `shared/dist/{types,constants}/*.{js,d.ts}` + `exports` с условиями `types`/`import`.
  Скрипты: `build` = `tsc -b --force`, `typecheck` = `tsc -b --noEmit`.
- `paths` в `backend/auth-service/tsconfig.json` и `frontend/web-admin/tsconfig.json`
  переключены на `../../shared/dist/*`.
- Порядок сборки зафиксирован: **сначала `shared`, потом сервисы**. Корень:
  `build:shared` + `build` (= shared → всё остальное), `typecheck` (shared → всё).
  CI: добавлен шаг `Build shared contracts` и `pnpm build` в цикле по `backend/*`.
- Побочно вычищено: дубль `baseUrl` в tsconfig сервиса; `*.spec.ts` больше не компилируются
  в `dist` (`exclude`); `test/**/*` убран из `include` (jest-e2e использует собственный конфиг
  и пока пуст; при появлении `test/**/*.e2e-spec.ts` — вернуть `include` **вместе** с
  `rootDir: "src"`, иначе вывод снова уедет).
- `Dockerfile` (**контекст сборки теперь корень репозитория**, было — `backend/auth-service`):
  копирует `shared/dist` на ожидаемое `paths` место. Команда:
  `docker build -f backend/auth-service/Dockerfile -t cleaning-ops/auth-service .` (сначала `pnpm build:shared`).
- `.env`/`.env.example`: `VITE_API_URL`/`VITE_WS_URL` исправлены с несуществующего `:3000` на `:3001`.

**Проверено (2026-09-14, холодный старт — `shared/dist` и `backend/dist` удалены):**
`shared build` → exit 0; `nest build` → exit 0, **`dist/main.js` существует**; jest 23/23;
`tsc --noEmit` shared и web-admin → exit 0; `node dist/main.js` реально поднимает Nest
(все модули инициализируются, падает только на `P1001` — нет PostgreSQL); симуляция
builder-стадии Dockerfile (раскладка монорепо + реальный `shared/dist`) → `dist/main.js`.

**Правило на будущее:** любой пакет, импортирующий `shared`, обязан собираться после
`pnpm build:shared`. Все текущие импорты — `import type`, поэтому в рантайме `shared` не нужен
(проверено: `require('@cleaning-ops/shared/*')` в `dist` отсутствует). При появлении первого
**runtime**-импорта `shared` потребуется отдельная проверка доставки `shared/dist` в рантайм-образ.

**Найдены и исправлены ДВА бага, которые блокировали все эндпоинты с телом и список:**

1. **DTO импортировались как `import type`** (`auth.controller.ts`, `users.controller.ts`).
   Класс не существует в рантайме → Nest получает метатип `Object` → `ValidationPipe` с
   `whitelist: true` **вырезает все поля тела**. `POST /api/auth/login` отвечал **500**
   (`Cannot read properties of undefined (reading 'trim')`) на любой корректный запрос.
   Ломались ВСЕ эндпоинты с `@Body()`-DTO: login, pin, biometric, refresh, change-password,
   change-pin, register, update. Исправлено на значимые импорты DTO — в комментариях обоих
   контроллеров оставлено предупреждение. **Правило: DTO для `@Body()` нельзя импортировать
   через `import type`.**
2. **`new ParseIntPipe({ optional: true })` в Nest 10 не делает параметр опциональным**
   (`users.controller.ts`). `GET /api/users` без query → **400** «Validation failed
   (numeric string is expected)»; с `?skip=0&take=50` → 200. Исправлено на
   `new DefaultValuePipe(...), ParseIntPipe`.

Оба бага не ловились юнит-тестами (мокают сервис, тестируют только бизнес-логику) —
нужны интеграционные тесты HTTP-слоя.

**Корректировка аудита:** предполагавшийся TypeError в `pinLogin` при `pinCode = null`
**не воспроизводится** — короткое замыкание `!user?.pinCode ||` не доходит до `bcrypt.compare`.
Подтверждено: `/api/auth/pin` и `/api/auth/biometric` отдают корректный **401**.
Остаётся в силе факт: seed не заполняет `pinCode`/`biometricKey`, поэтому PIN и биометрия
неработоспособны «из коробки» (в БД у всех 4 пользователей эти поля NULL).

**Что осталось незакрытым по М1:** e2e-вертикаль (М1.8), активация e2e-джобы в CI,
покрытие auth > 80 % (сейчас ~26 %), `validateEnv` не подключён, `VITE_API_URL` для прод-сборки.

## 0.6. М2.7 — фундамент web-admin (прокси на три сервиса, API-слой, UI-кит)

М2.7 разбита на 5 потоков: фундамент сделан в основной сессии (это критический путь — от него

субагентами, каждый владеет только своим каталогом `src/pages/<Экран>/`.

**Главная проблема: фронт ходил в один сервис.** `.env` содержал
`VITE_API_URL=http://localhost:3001/api`, а `vite.config.ts` проксировал `/api` только на
auth-service. После появления file-service (:3002) и core-service (:3003) запрос `/api/objects`
уходил бы в auth-service и возвращал 404.

- `vite.config.ts`: прокси маршрутизируется по префиксам (`SERVICE_ROUTES`) — `/api/auth`,
  `/api/users` → :3001; `/api/files` → :3002; `/api/objects|floors|rooms|routes|route-points|`
  `tech-cards|tech-operations` → :3003. Записи «лови всё на auth» сознательно нет: неизвестный
  путь должен давать честный 404 от Vite, а не 404 от чужого сервиса, который потом ищут в
  контроллерах.
- `.env`/`.env.example`: `VITE_API_URL=/api` (относительный). Для прод-сборки одной переменной
  недостаточно — нужен reverse-proxy, повторяющий эту маршрутизацию; прямое
  `http://host:3001/api` сломает вызовы core-service. Это зафиксированный дефер.
- `src/api/config.ts`: `API_BASE_URL = import.meta.env.VITE_API_URL || '/api'`. Именно `||`, а не
  `??`: пустая строка (`VITE_API_URL=` — частый способ «выключить» переменную в .env) дала бы
  baseURL `''`, axios потерял бы префикс `/api` и все запросы ушли бы в корень домена.
- **Алиас `shared` для Vite.** tsconfig `paths` Vite не читает. Пока из `shared` импортировались
  только типы, это не проявлялось (типы стирает компилятор), но словари статусов и правила
  переходов — рантайм-значения. Добавлен `resolve.alias: '@cleaning-ops/shared' → shared/dist`.
  Проверено: dev отдаёт модуль по `/@fs/.../shared/dist/types/core.js` (200, `text/javascript`) —
  кириллица в пути сборке не мешает; прод-сборка также проходит.

(`type=planned`, `status=assigned`) с сохранением `ticketId`; повторный проход идемпотентен,
при недоступности ticket-service — backfill при следующем проходе. Неявка → `MISSED` +
`schedule.missed_checkin` (ровно один раз за счёт условия в `updateMany`); авто check-out после
`SCHEDULE_AUTO_CHECKOUT_MINUTES`. Cron — идемпотентные `setInterval` без Bull/Redis
(`SCHEDULE_CRON_ENABLED=false` для тестов). Unit: **172 теста**, покрытие 98.76 %.
Dockerfile добавлен; CI-джоба расширена обоими сервисами.

**Фронт М4 (web-admin).**
Экран «Материалы» (М4.3, `src/pages/Materials/**`): четыре вкладки в query-строке
(`catalog`/`stocks`/`movements`/`report`), серверный поиск в справочнике (`search` по названию и
поставщику), сортировка в пределах страницы, CRUD-модалка, движения IN/OUT/TRANSFER/WRITE_OFF с

предупреждает и **не подменяет** бэкенд), остатки с серверным признаком `belowThreshold`, история
материала с «Показать ещё» (в API нет `skip`, только `limit` ≤ 500), отчёт по расходу с

сохраняются без подмены — иначе существующие техкарты нельзя было бы пересохранить. Списание можно
связать с заявкой: у расходных типов (`OUT`/`WRITE_OFF`) в модалке движения есть необязательное
поле «Заявка», для `IN`/`TRANSFER` оно скрыто и `ticketId` в payload не попадает. Межсервисного FK
`tech_operation_materials.materialId → Material` при этом нет: core хранит строку и существование
не проверяет, списание выполняет material-service.

прихода/ухода (геолокация браузера, при отказе — ручной ввод координат, серверные тексты 403 вне
зоны и 400 «смена не открыта» показываются как есть; отметка возможна только **за себя** — сервис
берёт пользователя из JWT).

ключи TanStack `['materials', …]` и `['schedule', …]` с инвалидацией родительским ключом; модалки
монтируются заново по `key`, чтобы не тащить прошлое состояние формы.

**Фронтовые деферы М4:**
- Словарь статусов смены и частот повторения продублирован в `src/types/schedule.ts`: модуля

- Выбор маршрута в форме графика не сделан: `listRoutes` требует `floorId`, общего списка маршрутов

- `GET /api/schedule` не поддерживает поиск и пагинацию (список отдаётся целиком) — фильтр по

- В смене нет поля «окончание» (`plannedEnd`): колонка «Окончание» показывает факт `checkOutAt`.

**Решения и деферы М4:**
- Периодические проходы schedule-service в e2e **выключены** (`SCHEDULE_CRON_ENABLED: 'false'` в

  добавлены в notification-service отдельной задачей (см. историю М4).
- Межсервисные ссылки (`objectId`, `ticketId`, `materialId`) — строковые id без FK (границы
  сервисов); целостность не гарантируется, только лог/warning.
- Сервисная учётка для внутренних вызовов — dev-админ из `.env`; в проде нужна отдельная

## 0.10. М5 — Коммуникации: chat-service и портал заказчика

справочника сотрудников объекта — задокументировано в README сервиса).
Unit: **150 тестов**, покрытие 97 %+. Живая проверка: 13/13 REST и 10/10 WebSocket; при ней найден и
исправлен баг `JwtModule` без секрета, из-за которого handshake отклонял все соединения.

**web-admin (М5.3).** Страница «Сообщения» (`src/pages/Messages/**`): список своих чатов с последним

- **М6.7 (часть 1) — оффлайн-очередь и синхронизация.** Drift-БД `lib/database/app_database.dart`
  (`pending_actions`, `gps_points`; `.g.dart` коммитится — CI не запускает `build_runner`),
  `DriftPendingActionQueue` вместо очереди в памяти, ключи идемпотентности у чек-листа и SOS.
  `SyncService` (приоритет вида → FIFO, backoff 1→2→5→10→30→60→300 с ±20 %, временная ошибка →
  `pending` с `nextAttemptAt`, 4xx и лимит 10 попыток → `failed`), `QueueActionSender` (повторяет те же
  запросы: фото → заявка → attach; завершение операции, `alreadyCompleted` = успех), экран `/offline`
  со списком, «Синхронизировать сейчас», «Повторить» и «Удалить». Сеть — `connectivity_plus`
  (`ConnectivityService`, `onlineProvider`). Хост-тесты drift берут нативную sqlite3 через
  `test/flutter_test_config.dart` (Windows — `winsqlite3.dll`), поэтому очередь проверяется и локально,
  и в CI. Тесты: 33 новых, всего **117**.
- **М6.6 — GPS-трекинг.** Точка сначала идёт в буфер `gps_points`, затем буфер уходит батчами до
  1000 точек в `POST /api/gps/track`; отправленными помечаются ровно принятые сервером точки
  (`accepted`), точки старше суток удаляются без отправки. `GpsTrackerController` планирует следующую
  точку с адаптивным интервалом (12 с в движении, 60 с статично) и запускается из `AppShell`; вне
  смены `CHECKED_IN` — пауза, а если статус смены неизвестен (нет сети и кэша) — точки продолжают
  копиться. Профиль показывает разрешение, состояние трекинга и счётчики точек. Ограничения: заряд
  батареи в точке остаётся `null` (в стеке устава нет плагина батареи) и нет фонового сервиса Android
  (`flutter_foreground_task` в зависимостях не значится) — трекинг идёт, пока приложение на экране.
- **Внешнее ограничение.** Агенты, которым были розданы М6.3–М6.8, упали с `Insufficient Balance`
  (402, QUOTA) провайдера `deepseek-official`; провайдер Google отдаёт `400 User location is not
  supported` / неподдерживаемый thinking level. Поэтому М6.3–М6.7 сделаны основной сессией.
  Нерабочий каркас оффлайна от упавшего агента (`lib/database/**` той версии) удалён и написан заново.
- **Осталось по М6:** вторая часть М6.7 (кэш чтения: `shift_events`, `cached_rooms`, `cached_tech_cards`,
  `route_points`, `chat_messages` и оффлайн-баннеры на `/today`, `/route`, `/chats`, `/profile`),

## 4. Ключевые решения (rulings) — с ценой ошибки

1. **Корень репозитория = папка проекта** (ДОМКЛИР). `УСТАВ.md`/`ПЛАН.md` остаются каноном в корне; `docs/` — рабочие копии разделов. *Цена: если нужен отдельный репозиторий/remote — перенос тривиален.*
2. **`design/` добавлена в корень монорепо** (в уставе она отсутствует в структуре) — правку внести в устав при первой возможности.
3. **Страница «Сообщения» (Inbox) в web-admin** — решение для direct-чатов менеджера (устав не описывает чат в админке).
4. **Firebase в dev = мок** (лог+in-app) до появления ключей.
5. **Отчёты (М7) — read-модели PostgreSQL (SQL views)** — «облегчённый CQRS».
6. **`shared/` — только type-импорты в backend до М2/3**, пока у shared нет сборки в dist: `"type": "module"` + TS-исходники = runtime `require()` упадёт. Роль-литералы продублированы в DTO с комментарием. Исключение появится вместе со сборкой shared (tsc dist) при первом runtime-потребителе (события, М3).
7. **Локально зависимости ставятся npm-ом** (не pnpm): pnpm на PATH = 8.0.0 несовместим с Node 24 (`ERR_INVALID_THIS`); bootstrap pnpm@11 давал phantom-версию 8.0.0 — не тратить время. Команда: `node "C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js" install --no-package-lock --no-audit --no-fund` (по каталогам: корень, shared, backend/auth-service, frontend/web-admin). `pnpm-lock.yaml` отсутствует; CI использует `--no-frozen-lockfile` — lockfile создастся на Linux/CI.
8. **NestJS-спеки импортируют сервисы с `../`** из каталога спека (не `../../`).
9. **`biometricKey` не уникален в схеме** — поиск `findFirst` (не findUnique).
10. **Дизайн-токены: значения отступов/теней/радиусов приняты архитектором** (устав задаёт только уровни: «4px base», «4 уровня») — см. `note` в JSON.
11. **Flutter ThemeData собирается в М6** (в М1 генератор выдаёт только константы Dart).
12. **`docker compose` плагин** вызывать при необходимости напрямую: `"%LOCALAPPDATA%\Programs\DockerDesktop\resources\cli-plugins\docker-compose.exe" -f infra/docker/docker-compose.yml up -d` (CLI на PATH не настроен; `docker compose` может не найти плагин).

**Отличия macOS-стенда от Windows-стенда (обязательны к учёту):**

1. **pnpm 10 вместо 8: флаг `--if-present` идёт ПЕРЕД именем скрипта.** Правильно —
   `pnpm -r --if-present build`. В корневом `package.json` записано `pnpm -r build --if-present`,
   и pnpm 10 передаёт флаг **в сам скрипт**: получается `nest build "--if-present"` → корневой
   `pnpm build` падает. Это **расхождение CLI pnpm 8 → 10, а не дефект проекта**: канон
   (`package.json`, CI на pnpm 8) не менялся, обход — вызывать `pnpm build:shared`, затем
   `pnpm -r --if-present build` явно. Здесь же снимается расхождение с решением №7 (там «ставить
   зависимости npm-CLI» — это про Windows, где на PATH лежал несовместимый pnpm 8 и Node 24):
   на macOS рабочий pnpm 10, и обход через npm-CLI не нужен. Дополнительно `stand.sh` глушит
   попытку pnpm переключиться на версию из поля `packageManager` (`npm_config_manage_package_manager_versions=false`).
2. **pnpm 10 не запускает build-скрипты зависимостей.** Разрешение `only-built-dependencies[]`
   живёт в **`~/.npmrc`** — вне репозитория (машинная настройка). Без него не работают движки
   prisma, `bcrypt` (нативный модуль) и `sharp` (libvips). Если `~/.npmrc` потеряется, bcrypt
   лечится вручную: `node node_modules/.bin/node-pre-gyp install --fallback-to-build`
   в `node_modules/.pnpm/bcrypt@5.1.1/node_modules/bcrypt`.
3. **`localhost` → `127.0.0.1` в серверных адресах `.env`.** Rust-движок Prisma резолвит
   `localhost` в IPv6 (`::1`), а проброс портов colima слушает только IPv4 → `P1001 Can't reach
   database server`. Поэтому в локальном `.env` переведены серверные адреса: `*_DATABASE_URL`
   (9 БД), `REDIS_URL`, `RABBITMQ_URL`, `*_SERVICE_URL`.
   **Исключения — там `localhost` остаётся осознанно:** `MINIO_ENDPOINT` (JS-клиент работает,
   и набор `core.api` ждёт `localhost:9000` в URL файла) и `VITE_WS_URL` (читается браузером).
   `.env.example` в репозитории по-прежнему с `localhost` — это **не противоречие**, а
   Linux/CI-вариант: правится только локальный gitignored `.env`.
4. **`SERVICE_AUTH_PASSWORD` = пароль фикстуры `admin@cleaning-ops.com`** из
   `test/fixtures/users.json` (в CI ровно так — `.github/workflows/ci.yml`). Служебный логин
   сервис-к-сервису обязан совпадать с ней; со случайным паролем 16 тестов набора `api` падают:
   schedule/material/chat получают 401 от auth-service и отдают 502. Это пароль тестовой
   фикстуры, не секрет стенда (значение — в `.env.example` и CI).
5. **Postgres работает под эмуляцией amd64** — `postgis/postgis:16-3.4` не публикуется под arm64.
   Работает, но медленнее нативного. Влияние этого на UI-тест М2.7 (см. «находку» ниже) —
   **недоказанная версия**, а не установленная причина: сам дефект воспроизводится детерминированно
   запросом к БД, а в CI тест зелёный.
6. **Flutter — только arm64-архив** `flutter_macos_arm64_3.19.6-stable.zip`: обычный
   `flutter_macos_3.19.6-stable.zip` — x86_64 и без Rosetta падает с `Bad CPU type in executable`.
   Хост-тесты drift на macOS ничего не переопределяют: `test/flutter_test_config.dart` правит путь
   к sqlite3 только для Windows (`winsqlite3.dll`) и Linux, на macOS библиотеку даёт платформа.
7. **vite слушает IPv6** (`[::1]:5173`) — проверять `http://localhost:5173`, а не
   `http://127.0.0.1:5173` (последний не отвечает). Сервисы наоборот — на IPv4
   (`127.0.0.1:3001…3009`), поэтому в `.env` и в e2e-адресах они записаны как `127.0.0.1`.
   Нюанс: `stand.sh web` в своём выводе печатает `http://127.0.0.1:5173` — это только текст
   сообщения, открывать в браузере всё равно `http://localhost:5173`.

## 8. Чек-лист переезда на новый компьютер

1. **Скопировать папку целиком** (включая скрытые: `.git`, `.env`, `.superpowers/` — если нужны логи/скрипты нарезки). Достаточно `.git` + файлов; `node_modules` можно НЕ копировать (переустановить, п.3).
2. **Установить на новой машине:** Node ≥18 (цель 20 LTS; на старой было 24), git, Docker Desktop + WSL2 (`wsl --install --no-distribution` + перезагрузка), позднее Flutter ≥3.16 (М6). pnpm не обязателен локально (см. п.4/7); в CI — pnpm.
3. **Переустановить зависимости** (npm-CLI напрямую, по каталогам; порядок важен — shared/backend ссылаются на workspace через tsconfig-paths, node_modules перекрёстно не нужны, т.к. runtime-импортов shared нет):
   ```powershell
   $npm = "C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js"
   Push-Location <root>;            node $npm install --no-package-lock --no-audit --no-fund
   Push-Location <root>\shared;     node $npm install --no-package-lock --no-audit --no-fund
   Push-Location <root>\backend\auth-service; node $npm install …; node node_modules\prisma\build\index.js generate
   Push-Location <root>\frontend\web-admin;   node $npm install …
   ```
   Если используется pnpm ≥10 (Linux/WSL): `pnpm install` в корне покроет workspace (shared/test/backend/*/frontend/*).
4. **git safe.directory под новый путь** (путь сменится!): `git -c safe.directory='<новый-путь>' …` на каждую команду, либо исправить владельца папки, либо (админ) `git config --global --add safe.directory '<новый-путь>'`.
5. **Проверка после переезда:** `git status` чист; `node_modules/typescript/bin/tsc --noEmit` в shared и backend/auth-service — exit 0; `node_modules\vite\bin\vite.js build` в web-admin — OK; jest в auth-service — 23/23.
6. **`.env`:** либо скопировать со старой машины (в нём пароли), либо заново: `scripts/setup/setup.ps1` + сгенерировать пароли.
7. **Docker на новой машине:** запустить Docker Desktop, дождаться «Engine running», затем `docker compose --env-file .env -f infra/docker/docker-compose.yml up -d`.

**Ветка macOS (Apple Silicon / arm64) — текущий стенд.** Пункты 1–7 выше описывают Windows-путь и
сохраняются как есть; при переезде **на macOS** вместо пп. 2, 3, 4, 7 выполняются пп. 8–13:

8. **Инструменты:** Node 24 (системный), git, Xcode (к М6). Docker Desktop **не ставить** — нужны
   rootless **colima 0.10.3** (+ lima 2.2.0), docker CLI 29.8.1 и плагин compose v5.5.1
   (`~/.docker/cli-plugins`). pnpm 10.34.5 — локально в `~/.local/node_modules/.bin` (в `/usr/local`
   без sudo прав нет); каталоги `~/.local/node_modules/.bin`, `~/.local/bin`, `~/.local/lima/bin`,
   `~/flutter/bin` прописать в `PATH` (`~/.zshrc`).
9. **Flutter — только arm64-архив:** `flutter_macos_arm64_3.19.6-stable.zip` в `~/flutter`.
   Обычный `flutter_macos_3.19.6-stable.zip` — x86_64 и без Rosetta падает с
   `Bad CPU type in executable`.
10. **`~/.npmrc`:** список `only-built-dependencies[]` — иначе не собираются движки prisma,
    `bcrypt`, `sharp` (см. 5.2, отличие 2). Настройка машинная, в репозиторий не переносится.
11. **`.env`:** либо скопировать со старой машины, либо сгенерировать секреты (DB/RabbitMQ/MinIO/JWT)
    как в п.6 — на macOS скрипт `scripts/setup/setup.sh` (вместо `setup.ps1`). Затем: серверные
    адреса перевести с `localhost` на `127.0.0.1` (исключения — `MINIO_ENDPOINT`, `VITE_WS_URL`),
    а `SERVICE_AUTH_PASSWORD` задать равным паролю фикстуры `admin@cleaning-ops.com` — иначе
    16 тестов набора `api` падают (см. 5.2, отличия 3–4).
12. **Docker-стенд:** `colima start --vm-type vz --cpu 4 --memory 6 --disk 60`, затем
    `~/.cleaning-ops/stand.sh start` (контейнеры + 9 сервисов) и `stand.sh migrate`. Скрипт `stand.sh`
    живёт **вне репозитория** — при переезде его нужно воссоздать (образец: `~/.cleaning-ops/README.md`
    вместе со скриптом) либо поднимать сервисы вручную по разделу 7. После каждой перезагрузки
    colima поднимать заново.
13. **Проверка после переезда (macOS):** `pnpm build:shared` + `pnpm -r --if-present build`;
    `stand.sh migrate`; `pnpm -r --if-present test` (unit 9 сервисов); `flutter analyze` + `flutter test`
    (138 тестов); `stand.sh e2e-api` (эталон: 99 passed / 1 skipped / 0 failed) и `stand.sh web` +
    `stand.sh e2e-web` (эталон: 37 passed / 1 failed — известный дефект М2.7).
